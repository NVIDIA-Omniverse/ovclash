ovclash Overview#

ovclash is a standalone clash-detection library for USD stages, usable outside Omniverse Kit. It ships as a Python wheel and as a C/C++ SDK archive. Both drive the same native runtime.

ovclash is pre-1.0. A minor or patch release can carry a breaking change, and the changelog calls out each one. compatibility.md gives the version policy.

This page ships as docs/consumer/overview.md in the SDK archive. Paths on this page without a link are relative to the package root:

  • In the wheel, the package root is the installed ovclash package directory, <site-packages>/ovclash/. python -m pip show ovclash prints <site-packages> as Location.

  • In the SDK archive, the package root is the ovclash/ directory that the archive unpacks to.

What it does#

  • Opens a USD stage from a local file, or borrows a live ovstage stage that your application owns (attach_ovstage(), an attached stage). Given the borrowed stage’s composition, the USD sources it was opened and merged from, it evaluates time samples in private ovstage populations of its own and never moves your stage.

  • Runs mesh-vs-mesh queries, static or over a time-sampled range (dynamic), with an optional clearance tolerance.

  • Runs point-vs-mesh queries against UsdGeomPoints prims when you enable them. They are off by default, and they ignore the tolerance.

  • Finds duplicate meshes in a static query.

  • Scopes each side of a query to selected prim paths, or queries the whole stage.

  • Runs the pipeline synchronously, or asynchronously with progress and cancellation.

  • Reports overlap records, overlap details, query statistics and detailed overlap reports with face, outline and point buffers. The ovclash Python package hands those buffers to NumPy, Warp or any DLPack consumer without copying.

  • With the Suite API, saves results in SQLite or JSON-directory stores, exports HTML and JSON reports, and reads, writes and migrates legacy .clashDetection containers.

concepts.md defines the terms that the rest of the documentation uses.

  • Python. The wheel and the SDK archive’s Python packages need Python 3.10 or newer.

  • ovstage. Released packages read USD through ovstage, and neither package bundles it. The wheel depends on the exact ovstage version pinned in its metadata, so pip installs it with ovclash.   • OpenUSD. The ovstage runtime supplies the USD runtime, a namespaced build of OpenUSD, so ovclash needs no usd-core of its own.

  • Windows MSVC runtime. ovclash does not bundle the MSVC runtime (MSVCP140.dll, VCRUNTIME140.dll, VCRUNTIME140_1.dll), although its Windows binaries import it. Install the Microsoft Visual C++ Redistributable (x64) on the target machine. Without it, the Python import raises an OSError that names the DLLs that the machine cannot load.

  • SQLite. The SQLite store neither links nor bundles SQLite. It loads the operating system’s library once per process: on Windows only winsqlite3.dll from System32, on Linux libsqlite3.so.0, else libsqlite3.so. Only .ovclashdb databases and legacy .clashDetection containers need it; sqlite_serializer.md describes the store.

Wheel layout#

The wheel installs three Python packages:

  • ovclash;

  • the top-level ovclash_suite module, an import alias of ovclash.python.suite;

  • the omni.physxclashdetectioncore compatibility package.

The ovclash package directory also holds:

  • the native payload: bin/ovclash.dll and bin/config.toml on Windows; lib/libovclash.so, its SONAME copy lib/libovclash.so.<major> and lib/config.toml on Linux. The SONAME is the versioned library name that the Linux dynamic linker records in the binaries that link it, and <major> is the major version of ovclash;

  • the Python samples and their launchers under samples/, with the stage they open in samples/data/;

  • skills/, with its catalog skills/README.md;

  • README.md, the package readme, and ovclash-build-provenance.json, which names the source revision, the backend, the ovclash version and the pinned ovstage version.

The wheel has no ovclash/plugins tree: the ovstage runtime, the USD runtime and the plugin registry come from the pinned ovstage wheel. It omits headers, CMake and pkg-config files, import libraries, the C++ sample sources and their launchers.

pip cannot restore symbolic links from a wheel. The SDK archive keeps the full Linux libovclash.so.<version>, .so.<major> and .so chain, where <version> is the full ovclash version. The wheel ships two copies: libovclash.so for the ctypes loader, and the libovclash.so.<major> SONAME that linked binaries record.

SDK archive layout#

The “What is in this archive” section of the README.md at the root of the SDK archive lists every path in the archive. In short: include/ holds the public headers, lib/ and bin/ the library and its CMake and pkg-config files, python/ the Python packages, samples/ the samples, and docs/consumer/ this documentation. The root also holds requirements.txt, the dependency declarations, the license files and ovclash-build-provenance.json.

  • The C entry points need no context and are safe to call concurrently.

  • They fail on a null pointer and inside an owner-operation callback; see ovstage_integration.md.

This script, run with the Python that has ovclash installed, prints the library version, the backend name and the loaded library:

import ovclash

info = ovclash.backend_info()
print(ovclash.version_string(), info.backend_name, info.native_library_path)

Python API#

The wheel installs three Python packages. ovclash and ovclash_suite are the two APIs. Each binds its own C ABI. Both share one loader, so the native library loads once. Neither package wraps the other.

  • ovclash is a thin ctypes binding of the canonical C ABI and stays close to it: ClashRuntime, RunSettings, OverlapReport, AsyncPipeline. Use it to drive the clash engine directly.

  • ovclash_suite binds the Suite C ABI and keeps the legacy clash object model: ClashDetection, ClashQuery, ClashInfo. It adds persistence through ClashDataSerializerSqlite or ClashDataSerializerDirectory, and HTML and JSON export through export_to_html() and export_to_json(). Use it when you need named queries, stored results or exported reports.

Both packages define classes and functions with the same names, such as RunSettings, OverlapType and backend_info, and they differ. Import from one package and stay in it. Choosing an API lists every difference.

A third package, omni.physxclashdetectioncore, re-exports the Suite API under the Kit extension’s module names. Use it only for code that you migrate from Kit; see kit_compatibility.md. New code imports ovclash_suite.

python -m ovclash runs one query from the command line and prints a JSON summary. README.md describes it.

The SDK archive carries the same three packages under python/. Only the wheel finds its native library on its own. Before you begin: extract the SDK archive, and use a Python 3.10 or newer interpreter. Then, from the package root:

  1. Install the SDK archive’s requirements.txt into the interpreter: python -m pip install -r requirements.txt.

  2. Add the absolute path of python/ to PYTHONPATH.

  3. Set OVCLASH_LIB to the absolute path of the native library that the table names for your operating system.

To check the setup, run python -c "import ovclash; print(ovclash.version_string())". It prints the version of the loaded library, <major>.<minor>.<patch>. When it fails instead, its message leads to the fix in one of these entries:

  • No native library found;

  • Library override is not an absolute path;

  • ovstage dependency missing from the environment.

README.md is the Python guide. It covers installation, a first query, the command line, both Python packages, and the native-library lookup.

C / C++ API#

C and C++ consumers use the SDK archive. The wheel ships no headers, CMake or pkg-config files, import library or C++ samples. One shared library exports both C ABIs:

  • the canonical C ABI, include/ovclash/ovclash.h, which the ovclash package binds;

  • the Suite C ABI, include/ovclash_suite/*.h, which the ovclash_suite package binds. It is built on the canonical C ABI.

include/ovclash/ovclash_ovstage.h and include/ovclash_suite/ovclash_suite_ovstage.h add the ovstage-only entry points, such as borrowing a live ovstage stage. ovclash.h needs ovx/string_types.h, which comes from the installed ovstage package, not from ovclash. Start with C/C++ Quickstart. C API Conventions describes results, error text and strings.

Samples#

The wheel and the SDK archive both ship the runnable Python samples under samples/. The SDK archive adds their C++ versions and samples/build_samples.sh (samples/build_samples.bat on Windows), which builds them.

Sample

Covers

samples/clash_api/

The canonical API: static, dynamic, duplicate-search and point-cloud queries.

samples/clash_suite_api/

The Suite API: object model, persistence and export. Its run_custom_clash launchers run queries on your own stages without code.

samples/legacy_clash_detection/

Reading and writing the legacy .clashDetection container, including saving it as an .ovclashdb database.

For example, on Linux, from the package root:

./samples/clash_api/run_clash_api_python.sh

On Windows, from the package root, run samples\clash_api\run_clash_api_python.bat. samples.md describes every sample, its launchers, their runtime selection and their output. When a launcher fails while it prepares Python or builds a sample, Building and running the shipped samples lists the messages and fixes.
