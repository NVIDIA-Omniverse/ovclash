Local Development#

This page is the reference for building, testing, packaging and documenting ovclash from a source checkout. Run every command on this page from ovclash/.

If you use a released package instead, start with the consumer pages: the Python package guide, the C/C++ Quickstart and Samples. Contributing describes how to propose a change and which validation each kind of change needs.

Building ovclash from a source checkout#

ovclash has its own CMake-script build system. Do not use the build commands of the other projects of this repository on it: the PhysX SDK, NVIDIA’s physics SDK, or Omni PhysX, the PhysX integration of Kit.

The engine sources are under source/usdclash/, and ovclash does not modify them. The explicit inventory in scripts/usdclash_sources.cmake lists the compiled inputs.

Prerequisites#

  • A Windows x86-64 host, or a Linux x86-64 or aarch64 host.

  • Network access for the first build. It downloads the build dependencies, including CMake and Python, into _build/deps/; see Dependency sources. No system CMake is needed.

  • On Windows, a build from the public source needs the installed Visual Studio 2022, or its Build Tools with the x64 C++ tools, and a Windows SDK. “Public source builds” in the repository README.md describes the toolchain selection. The wrappers use the packaged vswhere and Ninja.

  • On Linux, a public source export builds on the host with the system’s GCC, and its output must meet the ELF baseline; see Wrapper flags.

Both backends (the scene-reading implementation that a build compiles in; Backends and trees) stage the ovstage wheel: the ovstage backend builds against the ovstage SDK and runtime in it, and the OpenUSD backend takes its ovx/ headers from it. The wrappers never look for a sibling source checkout of ovstage or of any other project.

Unless an override names a wheel, the build runs pip download --no-input --no-cache-dir --no-deps --only-binary=:all: --platform <tag> ovstage==<OVSTAGE_VERSION> against the index pip is configured to use: public PyPI unless PIP_INDEX_URL, PIP_EXTRA_INDEX_URL or a pip configuration file name another. The download is anonymous and noninteractive: a credential, Poetry configuration or account is not required. pip keeps no copy in its own cache: the build caches the wheel in the project-local _build/deps/downloads/ovstage directory and stops unless the wheel matches its SHA-256 pin in OVSTAGE_SHA256SUMS. A failed download stops the build with pip’s exit code and the variables that select the index. To build offline, download the wheel yourself and set OVSTAGE_WHEEL_PATH to it, or put it in the directory that OVCLASH_PIP_OVERRIDE_DIR names.

The ovRTX sample viewer setup installs the same pin: the wheel that an ovstage build downloaded and verified, or else ovstage==<OVSTAGE_VERSION> from the same index. It installs the pinned ovRTX wheel from NVIDIA’s public package index, which the PyPI ovrtx release also installs from, and pip checks it against its SHA-256 pin. It is anonymous too; no credential is required.

Dependency overrides lists every override and how the scripts read it. Dependency staging gives the order in which the build selects the ovstage wheel, and the checks of the include tree of the ovx headers.

Backends and trees#

ovclash builds one backend per build tree. Each backend owns its own trees, so both can exist side by side for comparison.

On Linux:

./build_ovstage.sh --release      # the product backend
./build_openusd.sh --release      # the unpublished parity backend

On Windows:

build_ovstage.bat --release
build_openusd.bat --release

Each command prints ovclash build completed successfully., then ovclash install tree assembled at <install-dir>, where <install-dir> is the backend’s install tree in the table that follows, and exits with code 0. Deleting _build/ removes every dependency, build, install and distribution tree. The next build bootstraps from scratch.

On Linux, _build/ itself may be a symbolic link to another location, such as a larger drive. On Windows, the packaged CMake cannot resolve a junction, so clean, install and packaging refuse a junctioned _build/. Links further down, inside _build/, are refused wherever a generated directory would be replaced or removed. To move only the dependencies, use the dependency overrides, such as PM_PACKAGES_ROOT.

Install trees are per backend, not per configuration. The install step deletes the previous tree before it assembles a new one. A Debug install therefore replaces the Release install of the same backend, and an install from the Ninja tree replaces one from the Visual Studio tree. On Windows, close any process that holds files from an install tree before you rebuild it.

Builds assemble the install tree by default. Pass --no-install for a faster build-only iteration.

--clean, and the clean step of --rebuild, removes:

  • the selected compile tree;

  • the backend’s install tree and its distribution directory (both generators share them);

  • that compile tree’s validation evidence for every configuration (_build/validation/<backend>/<generator>/);

  • the sample build root.

It keeps _build/deps, the other generator’s compile tree, the other backend’s trees and the viewer state, _build/viewer/<backend>.

An explicit BUILD_DIR (a Linux -DBUILD_DIR=... option or a direct cmake -P call) under _build must be one of the four compile trees of the backend table. Any other build tree must be outside _build. Its validation evidence goes to _build/validation/<backend>/external-<id>/.

Install step#

The install step, scripts/install.cmake, turns the build outputs into the relocatable install layout. The install_sdk CMake target brings the library and the native tests up to date and then runs it. The step does this:

  1. It deletes the previous install tree and runs cmake --install for the selected configuration.

  2. It runs scripts/package_deps.py, which writes dependency_audit.txt. For OpenUSD the script copies the namespaced OpenUSD dependency closure, and scripts/verify_pyless_closure.py then checks that the closure is Python-free. For ovstage, CMake install rules select the closure.

  3. It assembles the license payload, the documentation and the agent skills.

  4. On Linux it strips the ovclash-built ELF binaries of a Release install and enforces the GLIBC 2.35 / GLIBCXX 3.4.30 baseline.

  5. On Windows, when code signing is enabled, it signs the binaries last. A --validate run whose plan has the sign_sdk step signs in that step instead.

It compiles nothing, builds no wheel or archive and uploads nothing. The configuration selects only the ovclash-owned binaries: a Debug ovstage install holds Debug ovclash binaries and symbols over the published Release ovstage, OpenUSD and Carbonite closure.

  • Run setup_ovrtx_viewer.sh instead of --setup-ovrtx-viewer. It accepts --build-local-ovui.

  • Ninja is the only generator.

Local-ovstage mode builds against an ovstage source checkout instead of the staged wheel. Packaging and publishing reject such builds. Local ovstage source builds describes the mode.

Rules for combining flags:

  • --prepare-sentinel and --stage-inputs can follow --validate in the same invocation. After a passing validation, the wrapper only stages, and only with --stage-inputs: the validated build has already produced the Sentinel helpers.

  • Neither --prepare-sentinel nor --stage-inputs can be combined with --test, --generate, --clean, --rebuild, --target, --install or --no-install. On Windows, they also cannot be combined with --generate-vs. On Windows they cannot be combined with --setup-ovrtx-viewer either.

  • --validate cannot be combined with --generate or --clean.

On Linux, the install step enforces an ELF release contract with the manylinux_2_35 baseline (GLIBC <= 2.35, GLIBCXX <= 3.4.30). A host build on a newer distribution cannot meet it. A public source export always builds on the host, so build on Ubuntu 22.04 or a compatible environment. For a host build whose output you never publish, SKIP_GLIBC_CHECK=1 waives only the ABI baseline check.

Test and validate#

Before you begin: the host meets the Prerequisites. Each command builds and installs what it needs. The test_ovrtx_sample step of a validation also installs the viewer’s Python packages from the package indexes; Validation steps shows how to drop it offline.

On Linux:

./build_ovstage.sh --release --test        # packaged native tests only
./build_ovstage.sh --release --validate    # full validation, one backend
./test_all.sh --release                    # full validation, both backends
./test_all.sh --backend ovstage --release  # full validation, one backend
./build_openusd.sh --release --target test_python_runtime   # Python runtime suite only

On Windows:

build_ovstage.bat --release --test
build_ovstage.bat --release --validate
test_all.bat --release
test_all.bat --backend ovstage --release
build_openusd.bat --release --target test_python_runtime

Each command exits with code 0 when everything it ran passed. Every --validate run, including each backend run of test_all, ends with All validation checks passed! No bugs, only features...; Validation output shows a passing and a failing run, and Troubleshooting lists the common failures.

test_all validates both backends by default (--backend both, or --both):

  1. It prints its plan.

  2. It runs each selected backend wrapper, OpenUSD first, with your other options followed by --validate.

  3. After both backends pass, it checks the two installs’ ovclash-build-provenance.json files. Both must be source-verified and record the same source revision, source tree, build type and ovclash version.

test_all rejects --rebuild, --target, --static-carb and --dynamic-carb. test_all.sh also rejects the Windows-only generator flags.

An install built from a Git checkout records the working tree it was built from: HEAD and, with local changes, the tree of every staged, unstaged and untracked, not ignored file. Both installs of a two-backend run must be built from the same working tree, so do not edit sources between the two builds.

To run one native test or one Python test module instead of a whole step, see Run focused tests. Contributing lists the validation each kind of change requires.

Validation steps#

Each --validate run first builds and installs (build, install_sdk). A public source build has no signing step unless OVCLASH_CODESIGN is on, which needs a staged signing tool; then a sign_sdk step signs the install right after install_sdk. Code signing describes when signing runs. The run then executes these steps in order:

What it does

test_c_compat

Compiles, links and runs a C consumer against the install tree.

test_cpp

Runs the packaged native tests.

test_python_runtime

Runs the sharded Python runtime tests.

test_python_wheel

Builds the wheel (build_wheel), then checks it in a clean virtual environment: smoke queries plus the shipped-docs link check.

test_ovrtx_sample

Runs the ovRTX sample viewer’s one-shot smoke against the install tree. It renders only when OVCLASH_TEST_OVRTX is set.

Checks that nothing references the Kit clash extension sources.

test_ovx_package_coherence

The steps named in OVCLASH_VALIDATE_EXTRA_TARGETS

Run in the order given; the table of opt-in steps in this section lists them.

test_c_compat_sdk_archive

Packages the SDK archive (package_sdk), then runs a pure-C consumer against the extracted archive.

A signing failure stops the run before the tests and packaging.

A full run writes both a wheel and an SDK archive to _build/dist/<backend>. Debug and Release, and the Visual Studio and Ninja trees, share that directory, so the latest run replaces the earlier artifacts. Runtime evidence stays apart per tree and configuration. For the ovstage archive, test_c_compat_sdk_archive first installs the archive’s requirements.txt offline, from the ovstage wheel the build staged, into a separate environment. It then checks the installed native files against the archive’s ovclash-runtime-closure.json inventory.

--validate builds the Sentinel executables but runs neither Sentinel nor its checker tests, and it runs no KPI workloads.

OVCLASH_VALIDATE_EXTRA_TARGETS appends opt-in steps:

Step

What it runs

build_docs

The documentation render. A public source build renders the public site as a gate only; otherwise the render is staged into the install tree’s docs/html.

test_sentinel_checkers

The Sentinel controller and checker tests.

package_sdk

The packaging of the SDK archive as an explicit step. Every run packages anyway, so this does not package twice.

test_python_sample_app

The ovRTX sample-app Python suite under tests/sample_app_tests/.

An unknown extra name is fatal. OVCLASH_VALIDATE_EXCLUDE_TARGETS drops steps. An unknown exclude name only warns. Both take a ;- or space-separated list. Set them as environment variables, or, on Linux and in direct validate_all.cmake calls, as -D options. For example, on Linux:

OVCLASH_VALIDATE_EXTRA_TARGETS=build_docs ./build_ovstage.sh --release --validate

On Windows, in PowerShell:

$env:OVCLASH_VALIDATE_EXTRA_TARGETS = "build_docs"
.\build_ovstage.bat --release --validate
Remove-Item Env:OVCLASH_VALIDATE_EXTRA_TARGETS

Without OVCLASH_TEST_OVRTX the test_ovrtx_sample step only detects and needs no GPU, but it installs the viewer’s Python packages from the package indexes. Drop it where that is not possible. On Linux:

OVCLASH_VALIDATE_EXCLUDE_TARGETS=test_ovrtx_sample ./build_ovstage.sh --release --validate

On Windows, in PowerShell:

$env:OVCLASH_VALIDATE_EXCLUDE_TARGETS = "test_ovrtx_sample"
.\build_ovstage.bat --release --validate
Remove-Item Env:OVCLASH_VALIDATE_EXCLUDE_TARGETS

Parallel tests and shard planning#

--validate runs native test groups, Python shards and sample checks concurrently. It uses at most min(task count, CPU count, 16) workers. The validation steps themselves run one after another.

Setting

Effect

OVCLASH_PARALLEL_JOBS=N

Caps the workers at N.

OVCLASH_PARALLEL_TESTS=OFF

Forces one worker.

validate_all.cmake reads both from -D or the environment; -D takes precedence. Called directly, test_cpp.cmake, test_python_runtime.cmake and test_samples.cmake run one task at a time unless OVCLASH_PARALLEL_TESTS=ON. test_samples.cmake reads it only from -D.

Before you reproduce a failure with one worker: the host meets the Prerequisites. The rerun is a full --validate run, which builds and installs what it needs, as Test and validate describes.

On Windows, in PowerShell, use the environment, because the Windows wrapper rejects -D options:

$env:OVCLASH_PARALLEL_JOBS = "1"
.\build_ovstage.bat --release --validate
Remove-Item Env:OVCLASH_PARALLEL_JOBS

On Linux, pass the option to the wrapper:

./build_ovstage.sh --release --validate -DOVCLASH_PARALLEL_JOBS=1

The validation header then reads Parallel tests:    ON (max workers = 1). The rerun passes as any --validate run does: it ends with All validation checks passed! No bugs, only features... and exits with code 0. When a task fails again, the console prints its output, which also stays in <validation-dir>/run_parallel_logs/<suite>/<task>.log; Validation output shows how a failed step reads, and Troubleshooting lists the common failures.

When you call scripts/validate_all.cmake directly, add -DOVCLASH_PARALLEL_JOBS=1 to the same backend and build options. One worker runs the same shards one after another. It does not limit the native libraries’ own threads.

Python shards come from the current unittest discovery, so adding, renaming or removing tests needs no maintained test-name list:

  • Every run recalculates the shard count from the test inventory, the worker count and the per-test durations cached under <validation-dir>/python_test_durations/<suite>/.

  • PYTHON_TEST_SHARD_SIZE and PYTHON_TEST_SHARD_SECONDS override the derived shard size and time target.

  • A module’s literal PYTHON_TEST_MIN_SHARDS = N raises its minimum shard count.

  • The derived time target is a planning goal, not a timeout. More shards cannot shorten a single slow test, so measure by test ID rather than by shard number.

Ordinary python_tests shards have no default timeout, including coverage runs. A positive PYTHON_TEST_TIMEOUT_SECONDS=N, given as -DPYTHON_TEST_TIMEOUT_SECONDS=N or as an environment variable, sets a per-shard timeout; the -D value wins for a direct test_python_runtime.cmake call and for --validate, which forwards it to test_python_runtime and prints it in its header as Python timeout:    <N>s per shard, or Python timeout:    none. An explicit value also replaces the 1860-second default of the KPI reference-fixture suite. The test_python_runtime and test_python_coverage CMake targets inherit the environment form; they do not forward a PYTHON_TEST_TIMEOUT_SECONDS cache value.

The ovRTX sample_app_tests shards have no default timeout either, and --validate also forwards the value to test_python_sample_app.

Each task’s full output is saved to <validation-dir>/run_parallel_logs/<suite>/<task>.log. A failed task also prints it on the console. Each Python test result line ends with its duration in seconds, such as ... ok [0.123].

The opt-in test_sentinel_checkers step uses the same planner. Checker tests in the Sentinel guide describes its workers and evidence.

Test environment and fixtures#

The native, Python runtime and smoke test drivers put temporary files under _build/test_tmp:

  • Outside Windows, the native driver instead uses a per-checkout /dev/shm/ovclash-test-<hash> directory. It does so when /dev/shm is a tmpfs with at least 48 MiB free and the directory is private to the current user. The storage tests of the Suite API sync every record and SQLite commit, so a memory-backed directory is faster.

  • Set OVCLASH_TEST_TEMP_ROOT to choose another writable parent. Direct calls to scripts/test_cpp.cmake, scripts/test_python_runtime.cmake and the other test drivers also accept -DOVCLASH_TEST_TEMP_ROOT=PATH, which takes precedence. Relative values are anchored to the ovclash checkout.

  • The drivers set TMP, TEMP and TMPDIR only for their own process tree. Each fixture owns a private child directory, and no driver deletes the shared parent.

The drivers also keep many concurrent test processes from oversubscribing the host, unless you export your own value:

  • The native driver sets PXR_WORK_THREAD_LIMIT=2. Set 0 to restore OpenUSD’s one worker per hardware thread.

  • The Python runtime driver sets OPENBLAS_NUM_THREADS=1. Otherwise numpy’s OpenBLAS starts a worker per logical CPU in every test process, and on Windows each worker commits a large buffer up front.

Rules for test fixtures:

  • Keep regression fixtures just large enough to exercise their boundary.

  • Fixtures that fake optional modules must import native dependencies such as NumPy before patching sys.modules. Restoring that dictionary must not unload a newly imported extension.

  • Give synthetic GUI gestures explicit modifier state, so the host keyboard cannot affect unrelated tests.

  • Redaction fixtures use only synthetic secret values.

The Suite API migration test (test_suite_legacy_migration.py) needs no OpenUSD Python bindings. It runs in every validation on both backends.

Before you begin: the render needs an install tree of the backend it renders against, the ovstage one by default, so build and install that backend first; the link check needs no build.

  • The render, repo docs --project <project> --warn-as-error=1, renders docs/ to HTML with Sphinx, the documentation generator, and Doxygen, the C/C++ documentation generator. It fails on a broken cross-reference, a page that no {toctree} (the page list of a root page’s table of contents) lists, or a Doxygen parse error. In a public source export the project is ovclash-public: the public site rooted at docs/index_public.md, with the public pages only.

  • The link check, scripts/check_docs_links.cmake, checks the Markdown that ships. It builds one stage for the wheel and one for the SDK archive:

    • docs/consumer/ in the SDK archive stage only, and the package’s README, staged the way that package stages them;

    • skills/ and samples/, copied from the checkout. They include the ovRTX sample’s README, which neither package ships.

Building against a local install tree#

The consumer pages describe building against a released SDK archive: Linking in the C/C++ Quickstart, with every consumer CMake variable. This section covers what differs for a local install tree.

Local install trees and the OpenUSD SDK archive#

A local install tree, _build/install/<backend> in a source checkout, and the unpublished OpenUSD SDK archive keep the complete runtime closure beside libovclash.so. They need neither the separate ovstage install nor Python at configure time. They still need the ovx headers, which they do not ship: their include/ovx holds only dlpack. Add -DOVCLASH_OVX_INCLUDE_DIR=<ovstage>/include to the configure command, where <ovstage> is the ovstage package directory. In a source checkout that is _build/deps/pip-deps/ovstage/ovstage under ovclash/. With an installed ovstage wheel it is <site-packages>/ovstage. Without it, the configure stops with ovx/string_types.h (or ovx/types.h) was not found; see The ovx include tree.

For example, from your project directory, against a checkout’s ovstage install tree:

cmake -S . -B _build \
    -Dovclash_DIR=<ovclash>/_build/install/ovstage/lib/cmake/ovclash \
    -DOVCLASH_OVX_INCLUDE_DIR=<ovclash>/_build/deps/pip-deps/ovstage/ovstage/include
cmake --build _build --config Release

<ovclash> is the ovclash/ directory of the checkout. Both commands exit with code 0 when the configure and the build succeed, and the build directory _build of your project then holds your program.

To run such a program, put the runtime directories of the install tree <install>, such as <ovclash>/_build/install/ovstage, on the loader path of its process. Windows has no run path: put <install>\bin and <install>\plugins on PATH. On Linux, a CMake program started from its build tree has a run path to <install>/lib; a program linked through pkg-config, or moved out of its build tree, needs <install>/lib and <install>/plugins on LD_LIBRARY_PATH. Otherwise it exits with 0xc0000135 (Windows) or 127 (Linux) before main. The run_*_cpp sample launchers set these paths themselves.

The ovx include tree#

<ovclash/ovclash.h> includes <ovx/string_types.h>, or the older <ovx/types.h> when that header is absent. ovclash does not ship either header. ovstage produces them, in the include/ directory of the installed ovstage wheel or of the ovstage SDK. Every ovclash install tree ships exactly one ovx header, ovx/dlpack/dlpack.h, in its own include tree.

The CMake config of the product SDK archive finds the headers in the installed ovstage package. A local install tree has no such package, so name the ovx include directory yourself:

Setup

OVCLASH_OVX_INCLUDE_DIR

Source checkout

_build/deps/pip-deps/ovstage/ovstage/include under ovclash/, where the build stages the pinned ovstage wheel

pip-installed ovstage wheel

<site-packages>/ovstage/include

The exported config validates the directory: one without ovx/string_types.h or ovx/types.h is a fatal configure error. Linking gives the full lookup order and OVCLASH_ALLOW_MISSING_OVX.

pkg-config consumers set the directory through the ovx_includedir variable of ovclash.pc. In a local install tree and the OpenUSD SDK archive, ovx_includedir defaults to the ovclash include directory, whose only ovx header is ovx/dlpack/dlpack.h. A local tree’s ovclash.pc has no ovstage_root variable, so point ovx_includedir at the ovstage include directory.

Before you begin: the install tree <install> exists, built as Backends and trees describes, and <ovstage> is the ovstage package directory of Local install trees and the OpenUSD SDK archive. On Linux, from the directory that holds your C program app.c:

gcc app.c -o app $(PKG_CONFIG_PATH=<install>/lib/pkgconfig \
    pkg-config --define-variable=ovx_includedir=<ovstage>/include \
               --cflags --libs ovclash)

The command exits with code 0 and writes the executable app. When ovx_includedir names no ovx headers, the compile stops at #error "ovclash requires ovx/string_types.h or ovx/types.h". The link may also need -Wl,-rpath-link,<install>/lib, where the install tree keeps the ovstage libraries. The CMake config adds that option for you; ovclash.pc does not. Run app with the loader path that Local install trees and the OpenUSD SDK archive gives for a program linked through pkg-config.

On Windows, use the CMake config instead, with -DOVCLASH_OVX_INCLUDE_DIR as the example in Local install trees and the OpenUSD SDK archive shows.

Samples in a source checkout#

Samples describes the shipped samples and their launchers in the wheel and the SDK archive, and Building the C++ samples the build_samples options. A source checkout behaves differently, as Building the shipped samples and Sample launchers in a source checkout describe.

Building the shipped samples#

samples/build_samples.sh (samples\build_samples.bat on Windows) builds every sample against a local install tree as well as against an SDK archive:

  • Without --install-root or OVCLASH_INSTALL_ROOT, the script uses the first directory that holds lib/cmake/ovclash/ovclashConfig.cmake: the root that contains samples/, then _build/install/openusd, then _build/install/ovstage under it. With both backends installed, pass --install-root to choose one.

  • The default build root is _build/samples under the ovclash root, with one child directory per sample.

  • When OVCLASH_OVX_INCLUDE_DIR is unset, the script takes the first of these directories that holds ovx/string_types.h or ovx/types.h: _build/deps/pip-deps/ovstage/ovstage/include under the root that contains samples/, then the same path under the directory above that root, then ovstage/include beside the root, then ovstage/include one level higher, and last the staged tree of the checkout that built the selected _build/install/<backend>. Set the variable when an ovstage directory beside the root, such as a sibling checkout, must not be used.

  • Local install trees configure without Python.

  • The script copies the install’s ovclash-build-provenance.json into each sample tree and configures a tree from scratch when its copy differs. A sample tree therefore starts fresh after an install with new provenance, such as a build of a new commit.

Sample launchers in a source checkout#

Before you begin: the host meets the Prerequisites. A launcher builds a missing install tree itself, so the first run of each backend takes as long as its build.

The clash_api and clash_suite_api launchers in a source checkout default to --backend both: they run the OpenUSD backend against _build/install/openusd, then the ovstage backend against _build/install/ovstage, and build a missing install tree first; a failed build stops the launcher, and Troubleshooting lists the common causes. An explicit --backend (or --openusd / --ovstage) or OVCLASH_BACKEND selects one backend, and OVCLASH_INSTALL_ROOT is ignored when they run both. With --backend both, --output-dir DIR writes the OpenUSD outputs under DIR/openusd and the ovstage outputs under DIR/ovstage.

With the default --backend both, a launcher prints === Running OpenUSD backend === and === Running ovstage backend === as it starts each backend, and exits with code 0 when both runs pass. Without --output-dir, each run writes its results to _build/<sample>_<language> for OpenUSD and _build/<sample>_<language>_ovstage for ovstage, such as _build/clash_suite_api_cpp and _build/clash_suite_api_cpp_ovstage for run_clash_suite_api_cpp.

Source-checkout launchers use the checkout’s staged Python and skip the sample runtime helper samples/sample_python.py.

To pass your own processor arguments through a launcher, select one backend and put the arguments after --:

On Linux:

./samples/clash_suite_api/run_clash_suite_api_cpp.sh --backend ovstage -- --stage tests/data/time_sampled.usda --num-tasks 8

On Windows:

samples\clash_suite_api\run_clash_suite_api_cpp.bat --backend ovstage -- --stage tests/data/time_sampled.usda --num-tasks 8

The launcher exits with code 0 when the processor does, and writes only the outputs that your arguments name.

samples/legacy_clash_detection/ has its own run_legacy_clash_detection_cpp and run_legacy_clash_detection_python launchers, without a backend selector. From a source checkout they use _build/install/openusd unless --install-root selects another tree.

samples/clash_suite_api/run_custom_clash.{sh,bat} runs the Clash Processor, the sample program that runs one query on a USD stage from command-line arguments and saves the results; samples/clash_suite_api/clash_processor.md is its guide. In a source checkout it uses a built _build/install/<backend> of the checkout before it falls back to the published wheel, so after ./build_ovstage.sh --release a plain run_custom_clash runs your build. --backend openusd builds a missing _build/install/openusd. The wheel fallback installs into _build/deps/venv/custom_clash, and runs the checkout’s processor against the published wheel, which can lack newer API.

Troubleshooting#

Troubleshooting lists loader, version-mismatch and package configuration failures by their exact messages. These cases are specific to a source checkout:

  • Unknown option: <flag> from a build wrapper. The backend wrappers accept a fixed flag set and stop before building on anything else. The Windows wrappers also reject -D options. Wrapper flags lists the flags each platform accepts.

  • ELF strip/GLIBC baseline contract failed during a Linux install. The build ran on a host whose glibc or libstdc++ is newer than the manylinux_2_35 baseline. Delete the build tree (_build/compile/<backend>/ninja), whose cached compiler and objects are the host toolchain’s, and rebuild on Ubuntu 22.04 or another manylinux_2_35 compatible environment. For local work that will never be published, set SKIP_GLIBC_CHECK=1 instead; it waives only this check. See Wrapper flags.

  • error: ovstage install source_verified must be true for a dual gate (or openusd) at the end of a two-backend test_all. A Git command failed, or the index file that git rev-parse --git-path index names was missing, when that install was built, so its source is unknown. Check that Git works in the checkout (git reset rebuilds a missing index from HEAD) and run again. See Test and validate.

  • The source identity changed since the last successful native build during --validate, an install or packaging. The source identity covers every file of the Git repository that no ignore rule excludes, not only ovclash/. Something edited a file, created a new untracked file, ran git add, or committed or checked out after the build. While a validation runs, do none of these anywhere in the checkout, and keep editors and other tools from writing files there that are not ignored. The message lists the changed fields and the paths that differ. When it reports source_verified: true -> false instead, a Git command failed and the sources may be unchanged: run again once git status shows a settled checkout. A missing index file, the one git rev-parse --git-path index names, also reports it; git reset rebuilds the index from HEAD and leaves the working tree as it is. Build provenance explains each field.

  • The selected OVX include directory has no ovx/dlpack/dlpack.h, which the public <ovclash/ovclash.h> requires: <dir> when you configure ovclash itself. <ovclash/ovclash.h> includes <ovx/dlpack/dlpack.h>, and the install rule copies that header from OVCLASH_OVX_INCLUDE_DIR into the ovclash include/ tree. Point OVCLASH_OVX_INCLUDE_DIR at a complete ovx include directory. A consumer that fails to compile that include has a different problem; see Troubleshooting.

  • Could not find the ovclash suite shared library: neither OVCLASH_LIB nor OVCLASH_SUITE_LIB is set, ... with PYTHONPATH pointing at python/. The checkout’s python/ directory holds no build output beside the packages. Set OVCLASH_LIB to the absolute path of the install tree’s library, as Running the module from a source checkout shows.

  • A consumer program exits with 0xc0000135 (Windows) or 127 (Linux) before main while OpenUSD Python tests run. Those test runs temporarily replace the install tree’s OpenUSD library with a Python-enabled one. That library needs python312.dll (libpython3.12.so.1.0 on Linux), so a native consumer started during the swap cannot load it. A *.ovclash_pyless_backup file beside the OpenUSD library means that an interrupted run left the swap in place. Rerun those tests, which restore the backup first, or rename the backup over the swapped file.

  • A Packman download fails with HTTP 403, and the cloudfront.net URL it names answers with a page that reads 403 ERROR, The request could not be satisfied and Request blocked (Generated by cloudfront (CloudFront)). The content delivery network that serves the packages refused the request, for example while its firewall limits anonymous downloads. The package is not missing and the checkout is not misconfigured. Wait and run the build again: it continues from the packages already in the Packman cache (PM_PACKAGES_ROOT, by default _build/deps/packman-cache; see Dependency sources), which are not downloaded again. If the block lasts for hours, report it with the URL that the error names.

  • A Packman or pip download fails with a connection error, a proxy error or a timeout. The build then stops with Failed to download <dependencies> (exit code: <n>) after Packman’s own error, or, for the ovstage wheel, with Failed to materialize ovstage from <source kind>: <source> (pip exit code <n>) after pip’s. The network blocks a host that the build needs. Allow HTTPS to these hosts: d4i3qtqj3r0z5.cloudfront.net and d2cerybs4newgl.cloudfront.net for the Packman packages (the first redirects the PhysX SDK, the OpenUSD packages and the documentation tools to the second, so allowing only the first is not enough); bootstrap.packman.nvidia.com for Packman and the Python it runs on, on the first run; and pypi.org and files.pythonhosted.org for the pinned ovstage wheel and the Python packages that the build and its tests install.
