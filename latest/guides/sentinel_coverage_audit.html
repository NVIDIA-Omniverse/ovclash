Sentinel settings coverage audit#

This page maps ovclash settings and their interactions to the layer that tests them:

  • the engine corpus of Sentinel, ovclash’s correctness campaign;

  • the native controls that the combined Sentinel gate runs: one Sentinel run, whose verdict needs every native control, serialization comparison and engine cell to pass;

  • ordinary validation outside Sentinel.

It does not claim that every combination of settings is covered. Paths on this page are relative to the ovclash/ project directory. The Sentinel glossary defines the terms used here, such as case, variant, witness, obligation, cell, golden and build tuple.

Five named engine cases assert interactions and boundaries that individually correct settings do not establish; see implemented interaction and boundary checks. They also compare their typed results with reviewed goldens for each build tuple. An independent expected answer never replaces a golden, and a golden never replaces an independent expected answer. Propose and accept results describes the golden workflow.

What counts as coverage#

Three layers test settings:

  1. Sentinel engine corpus. Named cases with frozen settings and actions, independent semantic checks and backend-specific repository goldens. tests/sentinel/engine_cases.json declares the cases, and tests/sentinel/engine_contract.json declares the obligations they satisfy; see case fields and obligation fields.

  2. Native controls in the combined Sentinel gate. tests/sentinel/native_targets.py requires the installed ovclash.native.test without a selector, which runs every test registered in tests/native/TestNativeClash.cpp. It also requires a fixed list of other native test programs; see native controls. These assertions count toward the combined gate even without a matching engine case. OVCLASH_OVSTAGE_ONLY guards in TestNativeClash.cpp decide which tests each backend registers.

  3. Ordinary validation outside Sentinel. The Python runtime test group that scripts/test_python_runtime.cmake runs, and the native test programs that scripts/test_cpp.cmake runs. A native test program is a Sentinel native control only when native_targets.py lists it.

Most test_sentinel_* Python modules are checker tests. They test the checkers’ rejection logic, and their existence does not prove that a product scenario ran. scripts/python_test_inventory.py names the three serialization modules that run against the installed SDK instead.

engine_contract.json gives every canonical setting, a member of ovclash_settings_t or a settings flag with a canonical mapping, an explicit coverage decision:

  • a behavior disposition with the obligations that exercise it, or

  • a transport-only disposition with a reason.

Each setting with a canonical mapping carries its decision in settings.<name>.canonical_coverage. The two Suite API-only settings, depth_epsilon and discard_touching, have none. canonical_input_coverage holds the decisions for OVCLASH_SETTINGS_FLAG_LOG, startTime, endTime and timeCodesPerSecond, all four of them and no other name. ovclash.h defines the canonical behavior. source/suite/SuiteSettings.cpp translates the Suite settings declared in ovclash_suite_types.h. tests/sentinel/source_inventory.json labels ovclash_settings_t mapped-settings: its member names and types must match the launch defaults and the typed native capture. It labels ovclash_suite_run_settings_t and both Python RunSettings classes structural-only. Neither disposition is runtime interaction coverage.

Four kinds of evidence answer different questions:

  • Requested and effective settings readback shows that a value reached the API.

  • A private event shows that an implementation path ran.

  • An independent expected answer establishes the named geometric or policy behavior.

  • A golden comparison detects a change to the retained typed outputs of an approved case.

For example, equal overlap reports cannot prove that a bounds offset was applied when both offset values produce the same candidate pairs. A golden detects an unexpected payload change, but it does not prove the depth algorithm. Sentinel expands only the variants and axes that each case declares. The extended profile adds seeds, repeats and task budgets, not interactions; see declared combinations and coverage limits.

Implemented interaction and boundary checks#

Each case in this section asserts an interaction or boundary that individually correct settings do not establish. Its oracle derives the expected answers from exact rational geometry and the public contract, never from native output. The docstrings of the oracle modules option_hit_depth.py, option_point_interactions.py, option_bounds_limits.py and option_kernel_boundaries.py in tests/sentinel/oracles/ describe their fixtures and proofs. The neighboring native checks are named so that new coverage does not duplicate them.

Any-hit or a triangle limit with depth and depth culling#

ovclash_set_any_hit keeps one representative triangle pair per mesh pair and computes maxLocalDepth from that pair only. A truncated hit set can therefore change the depth and the contact-epsilon culling decision. engine-options-hit-depth (tests/sentinel/oracles/option_hit_depth.py) uses two triangle pairs with MINIMAL depths 1/8 and 1/2, in both orders. It runs unlimited, limit-one and any-hit settings, steps the contact epsilon around both depths, and then restores disabled culling. The header does not say which pair is retained, so either face is accepted. Each execution tuple needs all six variants and a shallow culling witness for both limiting modes. Witnesses cannot be pooled across backends, configurations, seeds or repeats.

testTriangleLimitAndAnyHitSetters, testMaxLocalDepthDirectSetter and testContactEpsilonDirectSetter in tests/native/TestNativeMeshQueries.cpp check these settings one at a time. On ovstage, testNarrowPhaseReuse in tests/native/TestNarrowPhaseReuse.cpp checks narrow-phase reuse and invalidation when they change.

Point-cloud isolation from mesh clearance and depth culling#

The header says that the point-vs-mesh narrow phase ignores the tolerance, so it reports no point near misses. A point-vs-mesh overlap reports a maxLocalDepth of 0.0 in every depth mode. On ovstage, testMeshPair in source/OvstageClashCollision.cpp applies contact-epsilon culling to mesh pairs only, and runNarrowPhase collects point hits separately.

engine-options-point-options (tests/sentinel/oracles/option_point_interactions.py) places a point hit, a point near miss and a mesh clearance pair in one scoped scene. 36 of its 38 variants enable point clouds and combine these values (2 × 3 × 3 × 2):

  • tolerance 0 and 1/4;

  • disabled, MINIMAL and HIGH depth;

  • disabled, zero and 1/4 contact epsilon;

  • report masks 16 (OVCLASH_OVERLAP_REPORT_FLAG_POINTS0) and 30 (the OUTLINE, FACES0, FACES1 and POINTS0 bits of ovclash_overlap_report_flag_t).

The other two variants run with point clouds disabled. The native testPointCloudExperimentalMatchesStandalonePointClouds in tests/native/TestNativePointClouds.cpp checks that the experimental point path reports the same results.

Bounds epsilon and the positive finite broadphase limit#

engine-options-bounds-limits (tests/sentinel/oracles/option_bounds_limits.py) uses three disjoint triangles on distinct parallel planes, with tight bounds. The bounds computation turns each half-extent h = 1/2 into (h + epsilon) * (1 + epsilon). The scene therefore has two candidate pairs at epsilon 0, three at 1/4 and none at -1/4. The X spacing of the triangles detects an ignored epsilon, a missing offset or scale term, and an offset applied after the scaling.

BoundsConfig private events record the mesh flags, not the numeric epsilon. The case therefore infers the candidate count from the public limit contract of ovclash_set_broadphase_limit: a run whose candidate count exceeds the limit is cancelled, not truncated. Kernel choices at coplanar and floating-point boundaries#

engine-options-kernel-boundary (tests/sentinel/oracles/option_kernel_boundaries.py) runs intersection codes 0 to 3 at zero tolerance, with coplanar handling off and then on. Its one scene holds an exact positive segment hit, a separated pair whose axis-aligned bounding boxes (AABBs) overlap, and a strictly coplanar pair. It checks pair membership and the face buffers (report mask 12), not outline segments. The case excludes positive tolerance on purpose: PhysX selects its distance leaf function before it reads the kernel selector (getLeafFunc in the repository’s physx/source/geomutils/src/mesh/GuBV4_MeshMeshOverlap.cpp). A clearance case repeated across codes would test that the selector is ignored, not four kernels.

engine-reports-floating-point-kernel0 runs the fp-subnormal-kernel0 recipe: code 0 on the subnormal fixture, with the legacy manager, a dynamic query run and the architecture’s round-to-nearest mode that flushes denormals. It uses its own v4 request protocol. The other floating-point recipes in tests/sentinel/fp_scenario.py keep code 3 and the v3 protocol. The header allows the kernels to differ marginally in borderline hit classification, so both cases check selected proved domains. They do not claim equality across kernels, rounding modes or cooking profiles.

Coverage outside Sentinel#

Ordinary Python and Suite validation covers consumer routes beyond the native controls. All files are in tests/python_tests/:

  • test_runtime.py: test_run_settings_round_trip_through_the_native_context, test_report_buffers_implement_the_dlpack_protocol and test_report_buffers_can_be_viewed_as_warp_arrays. The NumPy and Warp checks skip when those optional packages are missing.

  • test_runtime_lifetimes.py: the async pipeline and overlap report owner-lifetime tests.

  • test_suite_api_run_settings_and_scope.py: test_suite_run_settings_translate_all_original_python_settings, test_suite_run_settings_derive_stage_times_like_original_python, test_suite_run_settings_prefer_the_native_stage_timeline and test_suite_set_settings_sampling_rate_override_keeps_stage_times. They check Suite naming, the depth gate and selector conversion, and timeline derivation. Canonical option cases do not replace these translation checks.

  • test_suite_original_behavior.py: test_depth_queries checks Suite contact classification and discard behavior on the contact_cases.usda fixture. SuiteSettings.cpp translates the Suite compute_max_local_depth gate and its three-valued max_local_depth_mode selector into the four-valued canonical depth mode, so the two settings domains differ.

  • test_attached_ovstage.py: Python owner operations, callback errors and borrowed-stage lifetime. The source inventory entry for ovclash_ovstage_binding_t makes no behavioral claim for attachment transport.

  • test_parallel_phase_results.py: threading and narrow-phase chunk regressions. Sentinel has its own optimization cases; they do not replace these regressions.

Backend differences and inert settings#

Backends, Limitations, the divergence ledger of the “Backend contract” section of AGENTS.md and the public header constrain new expected answers and goldens:

  • ovclash_set_use_usdrt is stored, read back and serialized with the query settings, but it changes no clash result on either backend. The engine contract marks it transport-only, and Sentinel launches with it off. The log flag is also transport-only; ordinary Python tests, such as test_cli_log_flag_reaches_the_backend_diagnostics_without_touching_stdout, check its diagnostics.

  • ovclash_set_point_clouds_experimental alone does not enable point clouds; the points-experimental-alone variant of engine-options-points checks this. With point clouds enabled, the flag is inert on ovstage and, when multi-threading is active, selects a multi-threaded point-vs-mesh path on OpenUSD. The native equality check covers experimental versus regular results.

  • ovclash_set_nb_tasks bounds the legacy manager, selected when ovclash_set_new_task_manager is off. The new manager ignores it, and ovclash_set_single_threaded overrides either manager. Overlap index order is not contractual; see overlap index order is not contractual.

  • ovclash_set_sort_mode changes behavior on ovstage only for UINT32_MAX, which zeroes the duplicate triangle count. That case is observable and covered. Neither backend validates the value, so other values are accepted, not invalid input.

  • Uniform per-point widths and instanced point clouds have declared backend-specific results and existing tests. Do not report them as missing point coverage or force them into a cross-backend equality check.

  • Matrix decomposition selection (ovclash_ovstage_set_matrix_decomposition) is ovstage-only. Subcomponent and point-size changes during a run, OpenUSD cancellation scope, async progress synchronization and step-status fidelity are declared limitations. New checks should pin those contracts, not redefine them.

  • Compare default tables within one API surface. Canonical, Suite and curated Python defaults differ on purpose, and the RunSettings structural inventory does not assert one universal default configuration.

Open items and adding coverage#

No named case isolates the contact-cutoff path for a retained pair. Such a case would keep the evidence in one place. It is less urgent because the combined gate already requires testContactEpsilonDirectSetter.

For each addition:

  • bind the requested and effective values;

  • assert the complete applicable payloads;

  • add negative checker tests for missing or wrong evidence;

  • require actual private path events when the public answer cannot tell the paths apart.

Reuse a deterministic stage when it fits, but fewer process launches do not add semantic coverage. A new setting also needs a coverage decision in engine_contract.json. Follow add or change a case and propose and accept results. Source presence and registration show intended coverage; only a completed run shows execution on a particular backend, platform and configuration.
