KPI evidence, reports and verdicts#

This page explains how to read the result of a KPI run:

  • the exit codes;

  • the live console progress and the final summary;

  • the public record measurements.json and the calibration evidence calibration.json;

  • the private execution tree.

Outputs lists where a run writes each file. The page uses the terms of the KPI glossary, such as attempt, run, campaign, series, noise, budget, package, bundle, CPU model, controller, driver, child and verified drain. The backend names ovstage and OpenUSD follow the consumer glossary.

All numbers in the examples are synthetic. The console and summary text comes from the code’s own format strings.

Reports and verdicts#

The controller, python -m benchmarks.kpi run, decides every verdict. It freezes the requested inventory, journals the start and the completion of every attempt, drains its child processes and then classifies the campaign. A child process that reports a pass cannot qualify a result by itself.

Every report keeps five verdicts apart: execution, work consistency, environment, workflow and performance. The work-consistency section, workload_consistency, records verification_kind=benchmark-work and correctness_qualified=false. KPI checks only that each workload did its frozen work. Sentinel owns correctness.

Exit

Status

Meaning

0

pass

Every required condition qualified and passed. Warnings stay visible

1

product-failure

A product or work-contract failure, a native crash, or a failed normal operation

2

regression

A confirmed performance regression: a candidate median above its failure limit

3

insufficient-evidence

Not enough qualified evidence, for example a missing or incompatible budget, an unqualified environment, exhausted CPU retries, unstable noise or an incomplete inventory

4

harness-failure

Invalid input, schema or identity, an output directory that already exists, failed input preparation, a harness or collector failure, or unverified process cleanup

75

(CI only)

The CPU-contention warning of CI check mode on Linux x86-64 and AArch64; Windows exits 0 instead. The benchmark verdict stays 3

76

(process only)

Too few physical cores, found before any native measurement. The benchmark verdict stays 3

130

interrupted

Cancellation, for example Ctrl+C

When several outcomes apply, the first one in this order wins: 1, 4, 130, 2, 3, 0 (runner.EXIT_PRIORITY). A product failure therefore outranks a regression in the same campaign, and a regression outranks missing evidence. The per-metric results stay visible in the summary and in the public record.

Deadlines and operation watchdogs are not budgets. An expired watchdog gives insufficient evidence (3), never a regression; deadlines gives their values. Baseline collection reports its own result with the same codes; see collection status and exit codes.

Exit 76: too few physical cores#

KPI measures each attempt on four physical cores. Exit 76 reports a proven shortage before anything was measured. benchmarks/kpi/exit_codes.py returns it only when all of these hold:

  • The benchmark verdict is 3, and the output is verified.

  • The workflow receipt passed and the inputs stayed unchanged, where they were checked.

  • At least one attempt was executed. Every executed attempt is a drained, non-retryable CPU selection record of kind insufficient_physical_cores.

  • The retained topology of each record fails the four-core proof again, with the same core count.

python -m benchmarks.kpi run and the launchers return 76, also in a CI job. The launchers also need verified private cleanup and a published public record; without them they exit 4. Check mode usually finds the shortage in its budget phase, from the observed topology, before fixture generation. It prints:

KPI insufficient physical cores (process exit 76; benchmark exit 3).

The public record keeps "benchmark_exit_code": 3 and "ci_exit_code": 76; read them where a CI system reports every nonzero Windows exit as 1. Baseline collection never returns 76: it reports the shortage with exit 3; see collection status and exit codes.

These cases never give 76:

Case

Result

A CPU quota below four, or a malformed or unsupported topology

Exit 3: there is no measurable CPU model, so there is no coverage

An explicitly selected budget path that is missing or is not a CPU-model package

Exit 3: measurement is skipped, whatever the core count

Busy cores, missing observations of a simultaneous multithreading (SMT) sibling, or an incompatible pool

The ordinary CPU-admission outcome

A shortage after a native measurement started

The campaign’s ordinary verdict

The CI CPU-contention warning#

scripts/kpi_ci.py turns exactly one kind of insufficient evidence into a warning: a campaign that ran out of CPU availability and has no other problem. It does so only in check mode in a CI context: a job that the built-in provider adapter detects (GitLab’s CI_JOB_ID), or one declared with OVCLASH_CI_PROVIDER or OVCLASH_CI_JOB_ID; see run KPI in another CI system. A local run and a baseline collection keep exit 3. The controller marks a campaign as eligible (ci_cpu_availability_warning in the private summary) only when all of these hold:

  • The benchmark verdict is 3 and no other reason is recorded. The producer workflow passed, the inputs stayed unchanged, and the build is of verified, clean source.

  • The campaign ran in the four-core four-physical-cores-retry-v2 CPU domain.

  • Every required metric has exactly one enforcing CPU-model limit, all for one CPU model.

  • Every executed attempt either qualified with every required metric, or is a CPU-busy rejection that the controller replayed. A cell that a busy wait left no time to start is marked as caused by that rejection.

  • Every comparison passed, warned, or lacks values only because its workload has missing cells.

  • Even with zero for every missing value, no median exceeds its failure limit.

Any actual operation failure, unsupported result, cohort mismatch, incomplete inventory or plain deadline stop prevents the warning. An eligible campaign then exits like this:

Platform

CI exit

Why

Linux x86-64 and AArch64

75

A nonzero code that differs from 3. A CI system that shows every nonzero exit as a failure needs the exit code or the KPI CI: non-blocking warning line to tell 75 from 3

Windows

0

A success code. A CI system can report every nonzero Windows exit as 1, so 0 is the only code that stays distinct from a failure

The console states the warning in one line:

KPI CI: non-blocking warning (exit 75); CPU availability exhausted; performance not verified; benchmark exit 3; public numerical diagnostics only; raw controls execution-only

Windows prints the same line with exit 0. What stays unchanged:

  • measurements.json keeps verdict.status insufficient-evidence and benchmark_exit_code 3. Only ci_exit_code is 75 or 0. The summary ends with Saved exits: benchmark=3, CI=75.

  • The private results/summary.json keeps exit 3. The driver also writes results/ci-disposition.json into the private execution tree. It binds the summary’s SHA-256 and records performance_verified: false. Like the rest of the private execution tree, it is deleted after a verified drain.

  • The warning never permits budget creation. The campaign is incomplete, so it exports no calibration evidence.

Workload tables#

Before the first Release workload, a Noise calculation block states the definition of MAD, the median absolute deviation, both noise limits and the budget formulas. It prints only once. Each executed workload then prints a heading, a two-line legend, its setup references and one table row per actual attempt. This Release workload goes from its first attempt to a stable result. Every number in it is synthetic, chosen to show the noise calculation, and is not a typical duration; the values that the calculation does not use show <s>:

Noise calculation
  MAD = median absolute deviation of all measured values. Warm-up is excluded.
  Stability noise = 3*MAD/median*100; Load limit 25%; other metrics 15%.
  Reported noise is the highest required non-Load metric; Load noise is shown separately.
  Largest deviations are retained. Budget allowance N=max(3*MAD, largest deviation);
  Suite serialization N is at least 30% of the median (runner-host spread);
  warning=1.05*median+N; failure=1.10*median+N.
  Values are rounded for display; saved gates use full precision.

Read it like this:

  • Run 1 is the warm-up. Runs 2 to 4 are the three measured runs.

  • CPU admission rejected the first attempt of run 3 because the CPU was busy. The rejected attempt used no run slot, and the second attempt, a retry, qualified.

  • After run 4, every required metric had three measured values and noise within its limit, so the workload became stable; see the noise gate.

  • The PASSED line shows the highest noise of the required non-Load metrics, then the Load noise. Here result_capture_seconds is the highest: 3 * 0.01 / 1.02 = 2.94%.

  • The heading Workload: 1.1 Body / Static query gives the campaign number and the workload number. A check run is campaign 1; a collection counts its campaigns. Workload numbers follow the execution order.

  • The Run and Try numbers start at 1. Attempt directory names count from 0; see attempt directories.

  • A workload that never started prints no table. Its counts and stop reason appear in the final summary.

  • An Invalid row prints the rejected counter operands, starting with CPU counter sample invalid:.

  • Another CPU rejection prints CPU check: Rejected: <reason>.

A rejected attempt does not stop the campaign by itself. The workload’s closing line says whether it stopped.

Sampling and stop lines#

Each Release workload ends with one closing line. PASSED marks a stable workload, as in the workload tables example; the final summary shows the same saved decision in its campaign summary. The other closing lines are described with their rules:

  • Campaign stopped: ... lines and every Recovery: CPU contention ... line, both the one that precedes a CPU-retry restart and the ones that end smoke CPU recovery: when a Release campaign stops.

  • The calculation block after a noise stop, for its deciding metric: how a stop is explained.

  • Restarting this workload only ... and Restart limit reached ... in collect-baseline: console and log lines.

Reading the evidence directory#

A launcher or CI check run exports only two things: the public record and, for an eligible Release campaign, the calibration evidence. A collection also writes its progress log, its status and the generated packages; see outputs. Private captures, runtime binaries and host paths are never exported. Start here:

Where to look

Did the run pass?

The Overall: line of the final summary, or verdict in public/measurements.json

The final summary#

The final KPI JOB SUMMARY (public diagnostic) is rendered from the public record alone. It never reads private files and never changes the verdict.

  • By default the driver prints the summary at the end of the run: --summary-mode inline is its default, and the launchers pass no --summary-mode.

  • A CI job can pass --summary-mode deferred and print the summary with --after-script from a later step, which also runs after a timeout or a cancellation. See print the summary in a later step.

The record states where it was made: {"kind": "local"}, or {"kind": "ci-job", "job_id": N} with the controller-validated numeric job ID. The reader compares it with the current context before it prints anything. A record from another job, or a record it cannot read, prints only:

KPI public snapshot unavailable; original verdict unchanged.

The result table states VALID or INCOMPLETE measurements. The Validity column and the Overall: line use VALID, PARTIAL, REJECTED, NOT RUN or UNKNOWN. Each metric comparison shows its saved result:

Result

Meaning

ACCEPTED (saved pass)

The median is at or below the warning limit W

ACCEPTED with WARNING

The median is above W and at or below the failure limit F

REJECTED (saved regression)

The median is above F

NOT EVALUATED

No budget, no median, insufficient evidence, or a product or harness failure

Budget limits defines W and F. Change, Warn > and Fail > give the median, W and F as percent changes from B, the baseline median of the budget row: a change above Warn > is a warning, and above Fail > a regression. When two different values print alike, for example a median just above F that rounds to the same percentage, the metric name gets [rounded] and the saved result decides.

The position bar draws the same numbers. All bars of one table share an axis of twelve cells from -20% to the largest failure limit in the table, and the column header labels both ends and B:

Mark

Meaning

:

The budget’s baseline median B

=

The change from B: left is faster or smaller, right is slower or larger

W, F

The row’s warning and failure limits

*, !, X

The median: at or below W, above W, above F

<, >

In place of a bracket: the median lies beyond that end of the axis

The median’s mark compares the unrounded values, so it stays correct when it covers a limit’s cell. Without a budget or a median, the cell reads unavailable. The bar is a picture; it recomputes no verdict. The comparison details of the driver’s KPI JOB SUMMARY use the same columns and bar, with one table per verdict group and workload.

How to read the counts and values:

  • Runs counts successful runs, the warm-up included. Attempts counts actual attempts, CPU rejections included. Valid/metric is the smallest count of qualified measured values across the required metrics.

  • An unstarted placeholder is not an attempt. An attempt record does not prove native execution. A rejected attempt is not a performance rejection.

  • For each cell, the latest retained record counts. A later failed or pending record replaces an earlier successful one.

  • Durations are in seconds and sizes in binary units (KiB, MiB, GiB). Displayed values have six significant digits; the JSON keeps the exact values. A missing value reads unavailable, never zero.

  • CPU precheck time, contention waiting, attempt durations and the total controller time overlap. Do not add them.

  • Passing CPU admission does not prove that the machine stayed idle during the operation.

A valid measurement does not mean accepted performance. Campaign performance stays NOT EVALUATED for a partial report, incomplete initial evidence, a workload without comparisons, omitted records, or any verdict other than pass or regression. The per-metric results stay visible even then, as in the measured Release campaign example of the final summary.

Baseline readiness applies the noise limits to the public values of every report, smoke included. It is arithmetic on the displayed values, not an eligibility decision. When the record holds more than one CPU model, it does not evaluate variability.

A check run ends with this sentence and a heart only when its saved record shows a benchmark pass, CI exit 0, a final record (incomplete is false) and verified private cleanup:

All KPI workloads passed and stay within their approved limits. Everything is awesome!

The heart is a Unicode character; a console whose encoding cannot show it prints <3 instead. An interactive terminal shows the line in green. Any warning, insufficient evidence, unverified cleanup or failure prints no sentence, and neither does the CI CPU-contention warning on Windows, whose CI exit 0 keeps benchmark verdict 3. With --summary-mode deferred, the sentence ends the after-script summary. A collection that exits 0 prints its own sentence; see collection progress log.

Public record#

Every launcher check run publishes public/measurements.json. A collection publishes one per campaign, in public/campaigns/<NNNN>/public/. The format:

  • Schema ovclash-kpi-public-measurements-v4 with the numeric-logical-references-v1 privacy contract.

  • One line of compact ASCII JSON with sorted keys and a trailing newline, at most 2 MiB. Row caps bound its inventory, attempts and comparisons rows.

  • Only fixed workload and metric names, numbers, UTC timestamps and logical references. A CPU label appears only when it comes from a complete, normalized hardware identity. Host and user names, unknown strings, paths, error text and raw console bytes are never copied.

The driver writes a context-only record, marked incomplete, as soon as the run starts. It replaces the file atomically after each controller inventory, attempt and summary event, and writes the final record at the end. A timeout or cancellation therefore leaves the latest partial record for the after-script.

The record has no calibration, runtime or approval authority. budget create cannot use it.

The schema is closed: a reader rejects any field that these tables do not list.

Calibration evidence#

Calibration evidence is the replayable record of one complete Release campaign. It is the only input that budget create accepts; see offline budget recording.

A --profile release check run writes calibration/calibration.json (--calibration-output selects another directory) only when all of these hold:

  • The campaign measured: compatible coverage let it pass the budget phase.

  • The campaign verdict is 0 or 3. CI exit 75 counts as 3. A regression, a product or harness failure and an interruption export nothing.

  • Every writer drained, and private cleanup is not held.

  • calibration.export accepts the campaign.

calibration.export requires:

  • the Release profile and the current nine-workload adaptive sampling policy, adaptive-release-warmup-robust-load25-noise15-retry10-runs10-restarts10-v10;

  • a clean, verified Release build of the selected backend and a passing validation receipt of the same build;

  • every workload of the frozen manifest stable: each passed the noise gate, so every required metric has at least three measured values. A campaign that stopped before every workload became stable exports nothing;

  • a verified child runtime, expected work and staged input closure;

  • the measurement code, the build closure and the stage inputs unchanged from the start of the campaign until the file is published.

Smoke, incomplete, failed and interrupted campaigns therefore export no calibration. Once the first three conditions hold, check mode prints one of two lines, depending on whether calibration.export accepts the campaign:

KPI complete calibration evidence exported; producer content receipts and offline numeric replay retained.
KPI campaign is ineligible for portable calibration; diagnostic verdict unchanged.

A collection exports every campaign that exits 0 with a verified drain to public/campaigns/<NNNN>/calibration/, before the independent replay checks the campaign. The file stays even when the replay rejects the campaign; see collection outputs. The collection’s progress log records the export instead of printing either KPI ... calibration line.

The output of a check run therefore holds the public record and, only for a complete qualifying Release campaign with compatible coverage, one calibration.json. The output of a collection holds one calibration.json per exported campaign. Pass those directories to budget create --artifacts, extracted first when they come from a CI artifact.

The format:

  • Format ovclash-kpi-calibration-evidence-v11 (schema_version 11), privacy contract numeric-logical-references-v1, validation boundary producer-validated-content-receipts-offline-numeric-work-replay-v1.

  • Canonical JSON, at most 64 MiB. Row caps bound its attempt rows and CPU placement receipts.

  • It holds only each workload’s final series; see what counts after a restart. It keeps every attempt and rejection of that series, the original child identities as hashes, the full frozen inventory, the numerical CPU histories and the expected-work proof.

  • It holds no runtime binary, host or user identity or local path.

Offline checks#

Offline readers (calibration.validate, which budget create runs) recheck everything they can without the original machine:

  • They require the complete closed schema, the v11 format and the current sampling policy. They recompute content_sha256 and accept only campaign_exit_code 0 or 3.

  • They verify the workload and metric inventory, child uniqueness, the runtime and backend receipts and the expected work.

  • They replay the numerical CPU admission and load checks and the adaptive sampling decisions. They never trust a stored qualification flag or projected budget.

  • They treat hash receipts as producer attestations: content hashes and sizes record what the producer validated, because binaries absent from the artifact cannot be hashed again.

  • They recheck the supported-workflow signing rules, with pass counts and permitted skips kept separate.

A portable calibration artifact holds exactly one calibration.json and at most one measurements.json, with no other file and no link. To check one before budget create, run this from ovclash/ with $PY, the KPI input Python of the quick start:

from pathlib import Path

from benchmarks.kpi import calibration, evidence

path = Path("_build/kpi-local-example/calibration/calibration.json")
document = evidence.load_json(path)
calibration.validate(document)  # raises ValueError("calibration ...") on any mismatch
print(document["format"], document["campaign_exit_code"], len(document["attempts"]))

For a campaign of the nine workloads with four runs each and verdict 3 (the synthetic campaign of tests/python_tests/kpi_calibration_fixture.py), it prints:

ovclash-kpi-calibration-evidence-v11 3 36

Private execution tree#

One controller owns one fresh private execution tree. Each attempt runs in its own child process with explicit bindings and native libraries. The shared process supervisor launches it, enforces its timeout and cleans up its descendants. Cleanup tries every remaining handle and keeps the original failure. If the supervisor cannot confirm that every owned child exited, the campaign stops: no later workload runs, and the report marks the output unverified.

The background observer, the in-process sampler of the child, reads OS counters only, and its memory and CPU cost are part of the measured process. A failure of the observer alone is a harness error. Its thread counts (Linux procfs tasks and Python thread counts) do not identify native ovclash workers, and the requested nb_tasks is not an observed thread count.

The launchers place the private execution tree of each campaign:

  • Linux: below the --output container.

  • Windows: in the system temporary directory, which keeps native paths short. Python takes it from TMPDIR, then TEMP, then TMP. Before the campaign starts, the driver checks the generation root and every frozen bundle member against the native MAX_PATH limit (260 UTF-16 units including the terminating NUL). Without long path support, Windows refuses such a path earlier, and a directory of 248 characters or more as well: when the driver creates the private execution tree, extracts the wheel into it or generates the bundles, or when a check writes the report of a failed phase. In each case the run stops with exit 4 and names the remedy Windows private KPI paths exceed MAX_PATH; set TMPDIR, TEMP and TMP to a shorter folder:

    • A check prints the remedy as the reason of the failed phase. When not even the private execution tree can be created, no phase has started, and the check prints KPI harness failure; <remedy>. instead.

    • A collection logs the remedy as the kind of its Failed phase: line and stops with collection_harness_failure; see collection status and exit codes.

Both locations get the same ownership, link, reparse-point, protected-input and cleanup checks. The driver removes the tree only after it verified the drain. Removal stops if the directory, its owner marker or its top-level entries changed, or if it holds more than 100,000 files. An unverified cleanup keeps the tree and exports nothing from it.

  • attempt.py: each attempt’s task.json, admission.json, stdout.log and stderr.log;

  • benchmark_execution.py and benchmark_depth.py: the capture files of a completed canonical capture, the report capture of a workload other than a Suite save; see attempt directories.

scripts/kpi_ci.py writes ci-disposition.json.

Private summary encoding#

results/summary.json grows with every retained attempt. calibration.export refuses a private results tree with any JSON file larger than 128 MiB (budget_package.MAX_JSON_BYTES). The controller therefore writes summary.json as one line of compact UTF-8 JSON, without NaN or infinity, with a trailing newline. When the cohort of an observation serializes exactly like the top-level cohort, the observation stores the string "summary.cohort" instead of a copy. This applies to observations and to the observations inside each comparison.

Read the file with benchmarks.kpi.runner.load_summary, or pass a parsed document to runner.restore_summary. Every KPI reader does, and the result equals the summary the controller held in memory. Only a direct run keeps summary.json; this example reads the _build/kpi-local/results directory of a direct campaign. Run it from ovclash/ with $PY:

from pathlib import Path

from benchmarks.kpi import runner

summary = runner.load_summary(Path("_build/kpi-local/results/summary.json"))
print(summary["status"], summary["exit_code"])

Any other string cohort, or a shared cohort without a top-level cohort object, is rejected with private KPI summary has an invalid shared observation cohort. The private summary is not signed: because shared observations are restored from the top-level cohort, a replay cannot detect an edit of only that cohort. Calibration, public records, packages and reports do not use this encoding.

Attempt directories#

Each attempt has its own directory below results/, named <workload_id>[-r<series>]-<sample>-<replacement>:

benchmark-body-representative-static-000-0       sample 0, first attempt
benchmark-body-representative-dynamic-002-3      sample 2, third CPU retry
benchmark-body-representative-dynamic-r1-000-0   restart series 1, sample 0, first attempt

  • sample is the zero-based inventory cell, in three digits.

  • replacement counts the CPU retries of one cell, from 0. Recovery gives how many each profile and CPU domain permits.

  • -r<k> appears only for a series that collect-baseline restarted; the original series has none.

  • An unexecuted cell may have no directory.

  • The numbers do not identify dynamic frames. One dynamic attempt runs all 65 samples of its workload, and one depth attempt all 10.

A four-core placement failure happens before a child launches and can leave only attempt.json; read the campaign’s cpu-selection.json then. A child that exhausts CPU admission can keep every file of its attempt directory without running a query.

A completed canonical capture adds these files. Their presence alone does not mean that the work or performance checks passed.
