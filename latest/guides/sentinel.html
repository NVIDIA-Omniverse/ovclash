Sentinel correctness validation#

Sentinel checks ovclash engine behavior and serialization against the current installed SDK: the content of an SDK archive that a build installs. Each run compares the installed SDK with independent expected answers and with the goldens stored in the repository. It needs no earlier SDK or reader. It supports twelve build tuples: both backends, Release and Debug, on Windows x86-64, Linux x86-64 and Linux AArch64. The glossary defines the Sentinel terms used on this page and the other Sentinel pages.

Related pages:

  • Sentinel reference: every command, option, environment variable, evidence file, verdict rule and error message.

  • Sentinel goldens: the golden catalog and its review workflow.

  • Sentinel coverage audit: which layer tests each setting.

  • ovclash/tests/sentinel/README.md: implementation contracts for maintainers, from its “Contract files” section to its “Maintainer entry points”.

How Sentinel fits into validation:

  • Normal builds compile and install the SDK, and compile the ordinary native regression executables and Sentinel’s native helpers.

  • --validate runs neither the Sentinel campaign nor Sentinel’s checker tests: Sentinel’s Python controller tests and the shared process-tree supervisor tests (test_process_tree.py and test_process_tree_owners.py). scripts/python_test_inventory.py lists their modules. Run them with check-tests or the test_sentinel_checkers target.

  • A CI job runs the checker tests first, then the campaign; see run Sentinel in CI.

  • The implementation lives in ovclash/tests/sentinel/.

Git metadata is optional. Sentinel can run from an exported source tree with materialized test data and goldens:

  • Fixture admission uses the data inventory (tests/sentinel/fixture_inventory.json) and the golden manifests.

  • Missing files, unsafe paths, links and unresolved Git LFS (Large File Storage) pointers are errors.

  • When the source root is a Git checkout and Git is available, Sentinel also checks every tracked file under tests/data and tests/sentinel/goldens. It uses Git only when .git is in the selected source root, never a parent directory’s repository.

What is checked#

tests/sentinel/engine_contract.json declares the required behaviors and capabilities. tests/sentinel/engine_cases.json defines fixtures, variants, settings, timelines, actions and supported axes; case fields lists its fields. The controller selects the complete inventory before execution. Runtime discovery cannot remove a required cell.

Area

Exact rational triangle intersections, face/end-point checks, and every eligible positive and negative pair within the oracle’s declared domain.

Literal memberships, component-boundary scopes, visibility, instance placements, public statistics, reselection and stale-result behavior.

Sampling

Independent repeated-binary64-add schedules, empty and nonempty samples, retained timestamps and actual ovstage sample events.

Literal matrices and independent OpenUSD evaluation of parents, resets, nested instances and numeric/default queries; private collision-pose observations where required.

Recovery

Deterministic cancellation/fault boundaries, allocation and publication failures, process deadlines, drained work and healthy restart equality.

Reports and floating point

All 16 report masks (each even report_mask from 0 to 30, a combination of the four report-buffer flags; see case fields), directed typed payloads, duplicates, Unicode, subnormal/signed-zero behavior and caller/worker floating-point controls.

Delivery and persistence

Ownership/release, sync/async operations, reset/reselection/fresh contexts, current Suite API/SQLite round trips and reading historical database fixtures.

ovstage private test executables expose bounded observations and deterministic failure controls. Required public/private comparisons use the selected installed SDK. OpenUSD runs only its declared public capabilities. Backend ordering is preserved: Unicode checks independently verify pair membership and directed product hashes, while golden comparisons keep the selected backend’s complete typed records.

Oracles#

An oracle is the rule that determines the expected answer:

  • Independent rational geometry and OpenUSD evaluation derive answers from authored inputs.

  • Literal checks implement a specific API contract.

  • Metamorphic checks assert a defined relation between executions, such as fresh versus cached results.

  • Goldens detect changes from reviewed outputs. A matching golden alone does not prove geometry.

  • A serialization round trip checks transport of the supplied records, not the mathematical correctness of detection.

Run locally#

Before you begin, you need a source checkout or source export with materialized test data and goldens, and the build prerequisites of building ovclash from a source checkout. The commands build and validate the installed SDK, run the checker tests, then run Sentinel.

From ovclash in Windows Command Prompt (cmd.exe):

build_ovstage.bat --release --validate
test_sentinel.bat check-tests --output _build/sentinel-local-checkers.json --allow-skips
test_sentinel.bat
rem Optional explicit run with a new evidence directory:
test_sentinel.bat run --output _build/sentinel-local-run

On Linux:

./build_ovstage.sh --release --validate
./test_sentinel.sh check-tests --output _build/sentinel-local-checkers.json --allow-skips
./test_sentinel.sh
# Optional explicit run with a new evidence directory:
./test_sentinel.sh run --output _build/sentinel-local-run

  • With no arguments, test_sentinel.bat or ./test_sentinel.sh runs run with backend ovstage and configuration Release.

  • OVCLASH_VALIDATION_BACKEND and OVCLASH_VALIDATION_CONFIG replace those defaults when set. Explicit --backend and --configuration still win.

  • For OpenUSD, use build_openusd and --backend openusd. For Debug, use --debug and --configuration Debug together.

  • --engine-profile extended selects the larger profile; see declared combinations.

  • --help lists the commands, and COMMAND --help describes one. The Sentinel reference lists every option and environment variables every variable.

A passing check-tests ends its Checker summary with the result PASS and exits 0. A passing run exits 0, and its last line is ALL PASSED. Sentinel Council approves. This is the way.; see summary and final line. A failed build or validation stops the sequence before Sentinel runs; its output names the failed step, and troubleshooting lists common causes. A failed check-tests or run exits 1; see read a failure.

Each run writes its evidence to a new results directory, _build/sentinel/<UTC time>-<backend>-<configuration>, for example 20261015T050144Z-ovstage-Release. A run started in the same second adds -2, -3, and so on, so the parameter-free command can be repeated. The Results: line names the run’s evidence/ directory. Earlier results directories accumulate under _build/sentinel; delete them when you no longer need them. An explicit --output must be new or empty, because existing evidence is never overwritten.

Automatic input preparation#

run prepares its inputs in two steps.

Launcher bootstrap. The launcher needs an orchestration Python. It looks for one in its own checkout, in the selected portable input bundle and in the --source-root tree; Python selection gives the exact order. If none exists, run first builds the source tree with build_<backend> --<configuration> --validate. That build prints to the console and writes no Sentinel evidence. An explicit --inputs bundle without its Python runtime fails instead; regenerate that bundle. Commands other than run never build.

Startup input preparation. Sentinel then checks the selected manifest, installed SDK, helpers, Python bindings and runtime, and OpenUSD dependencies. It prepares missing local inputs within --preparation-timeout:

  • A complete matching local build is used directly.

  • Missing local inputs trigger one matching build_<backend> --<configuration> --validate in the selected source tree.

  • When the installed SDK’s provenance names another backend or configuration, Sentinel first runs build_<backend> --<configuration> (build and install) in the same tree. This replaces the shared _build/install/<backend> tree, for example a Debug install with Release. The --validate build follows only if inputs stay incomplete.

  • A local input descriptor from the retired output layout, whose test interpreter sits in a virtual environment directly under _build, counts as missing. The matching --validate build regenerates it. --stage-inputs and --prepare-sentinel refuse such a descriptor and name the rebuild command.

  • An explicit --inputs bundle never triggers a build. Malformed provenance and errors in an explicit bundle stop startup before any build.

Fixture files are checked first, so missing files and unresolved Git LFS pointers fail before any build. Every --validate build that the launcher or Sentinel starts keeps the test_python_runtime step, which produces Sentinel’s Python environment and the Windows Debug runtime. If an inherited OVCLASH_VALIDATE_EXCLUDE_TARGETS names it, that entry is dropped for that build only, and the console says so.

Each automatic build prints its command and its log, then relays the build’s output in either verbosity mode. On this page, <evidence> is the run’s evidence/ directory:

Running Sentinel input build/validation: ovclash/build_ovstage.bat --release --validate; log: <evidence>/logs/prepare-local-inputs.log
DETAIL prepare-local-inputs | <build output line>

The install-only build uses prepare-local-install instead. <evidence>/commands.json records both commands. If a build fails or times out, startup fails with a message that names the build and its log. If inputs are still incomplete or mismatched after a build, the message names the build and _build/sentinel-local/<backend>/<configuration>/manifest.json. Sentinel does not build again.

An automatic build passes only --release or --debug, plus --validate for the validation build. It therefore uses the wrapper defaults: the Visual Studio generator on Windows and, on Linux, the wrapper’s default build environment (see Wrapper flags). Inherited settings such as GENERATOR still apply. For a Ninja tree, run the matching build with your generator flags before Sentinel, for example build_ovstage.bat --release --ninja --validate.

Portable input bundles#

A portable input bundle (format ovclash-portable-inputs-v1) holds everything a run needs without a build tree. --stage-inputs stages one in _build/portable-inputs/<backend>/<configuration>. From ovclash, for the ovstage Release and Debug bundles:

Windows (cmd.exe):

build_ovstage.bat --release --validate --stage-inputs
build_ovstage.bat --debug --stage-inputs

Linux:

./build_ovstage.sh --release --validate --stage-inputs
./build_ovstage.sh --debug --stage-inputs

For OpenUSD, use build_openusd instead. Each command exits 0 when the bundle is staged and nonzero when the build, the validation or the staging fails; the bundle path never holds a partial bundle.

  • Staging copies the validated installed SDK, its Python runtime and the Sentinel helpers from the build that _build/sentinel-local/<backend>/<configuration> describes. It compiles nothing.

  • With --validate in the same invocation, staging follows only a passing validation.

  • A tree without the helper outputs, for example one built only with --target, cannot be staged.

Normal builds already produce sentinel_native_inputs, so --prepare-sentinel is only an explicit helper rebuild in the configured build tree:

  • It runs scripts/prepare_sentinel.cmake through the same wrapper as the build.

  • It refuses a GCC or Clang tree whose recorded compiler is missing or reports a different version, instead of recompiling the validated tree with another toolchain.

  • It installs no SDK and does not rebuild the installed ovclash.native.test, whose Windows post-build install/signing hook would reassemble the validated SDK.

  • With --stage-inputs, it also stages the bundle. After --validate in the same invocation, it rebuilds nothing.

Staging replaces any earlier bundle for the same backend and configuration. It swaps whole directories by renames, so the path never holds a partial bundle. On Windows, a file that another process holds open makes restaging fail and leaves the bundle unchanged. A library that a running KPI or Sentinel process still loads stays behind in a <configuration>-* directory beside the bundle until you delete it.

When configurations share an install directory, run the matching build or validation last, before staging. Staging refuses an install that holds another backend or configuration and keeps the earlier bundle.

--inputs DIRECTORY selects an existing bundle instead of local outputs. A bundle staged without the Sentinel helpers, or with missing files, fails before execution. The message names the restaging command build_<backend>.bat|.sh --<configuration> --validate --stage-inputs. A CI system can therefore validate and stage in one job and run Sentinel from the staged bundle in another; see run Sentinel in CI.

Build outputs and the native test runtime#

Generator-specific build roots are kept. For example, Windows Visual Studio outputs are:

_build/compile/ovstage/vs/windows-x86_64/release/
  ovclash.dll
  tests/             ordinary native regression executables
  tests-sentinel/    ovclash_sentinel[.exe] and ovclash.sentinel_engine.test[.exe]

Both backends and Debug use the corresponding root and configuration directory; Ninja uses _build/compile/<backend>/ninja.

Test executables have no copied SDK DLLs beside them. Windows searches that location before PATH, which could silently select a stale or different SDK. The native validation launcher and Sentinel supply the selected installation’s runtime directories, and the Debug runtime where needed. Sentinel’s public consumers also verify where the loaded SDK came from.

The build writes path metadata to _build/sentinel-local/<backend>/<configuration>/manifest.json (format ovclash-sentinel-local-inputs-v1). Selection checks backend, configuration, platform, architecture and required paths, including the installed SDK’s backend and build configuration. Native admission checks loaded-library origins. The installed SDK’s verified source revision is descriptive provenance, not a reference pin. An SDK without one, or built with uncommitted changes, is recorded by content identity.

Native controls read fixture scenes from the Sentinel checkout’s ovclash/tests/data. Sentinel sets OVCLASH_NATIVE_TEST_DATA (a directory path) for those controls, so prebuilt executables do not depend on the checkout path of the machine that built them. A direct native-test invocation uses its compiled fixture directory unless this variable is set. A set variable is used as given and never falls back, so a wrong directory makes the tests fail. Environment variables lists every variable that Sentinel reads or sets.

Checker tests#

check-tests --output FILE runs the checker tests outside normal build validation:

  • The test_sentinel_checkers target runs them too, and OVCLASH_VALIDATE_EXTRA_TARGETS=test_sentinel_checkers appends it to a --validate run.

  • test_python_runtime still runs the three SDK-dependent Sentinel serialization modules, and run does not repeat the checker tests.

  • Standalone check-tests rejects any skip. --allow-skips, which the CMake target passes, accepts ordinary unittest skips, including platform-specific ones, and reports their counts. Failures, errors, unexpected successes, incomplete execution and empty modules fail either way.

  • --check-workers N sets the number of concurrent checker shards. Without it, the count is 1 when OVCLASH_PARALLEL_TESTS is 0, OFF, NO or FALSE, otherwise OVCLASH_PARALLEL_JOBS when set, otherwise the available CPU count. The available CPUs and the shard count bound every worker count.

  • The CMake target passes 1 when OVCLASH_PARALLEL_TESTS is OFF, otherwise OVCLASH_PARALLEL_JOBS when set, or 16.

Each run keeps per-shard logs, method durations and complete method accounting beside the output file, in a directory with the same name and a .modules suffix: checkers.modules for checkers.json. Neither may exist yet; otherwise check-tests fails with Checker evidence must be fresh. Delete both, or choose a new name, before you repeat a command. The CMake target writes a new timestamped file for every run: _build/validation/<backend>/<generator>/<configuration>/sentinel_checkers/<UTC time>-<8 hex>.json. check-tests options lists every option, the accounting JSON and the evidence layout.

The console prints one line per completed shard, in completion order, then a table of checker groups and a summary. A Windows run with eight workers prints lines like these, where <elapsed> and <UTC time> stand for the measured durations and clock times:

Scheduling.

  • --engine-workers (1 to 4, default 2, capped by the available CPUs) bounds concurrent producers.

  • Only ordinary serial cells run concurrently (parallel_eligible() in tests/sentinel/engine_campaign.py). Such a cell has:

    • serial, single-threaded detection in the normal floating-point mode;

    • a generated geometry, selection, options, reports or schedule fixture;

    • public capture as its only capability;

    • only run, snapshot and query actions.

  • Private, floating-point, recovery, fault and other cells run alone. Each of them waits for the concurrent cells before it to finish.

  • Compatible cells share one loaded stage, in groups of at most 64. Grouping changes their launch order once; see console output.

  • Admission, caches, progress and publication stay on the controller.

Admission. For each cell, the controller first runs the cell’s semantic checks and requires the declared capabilities and artifacts. Only then does it compare the snapshots with goldens:

  • Live-fixture cells collect no golden snapshots.

  • Native floating-point cells check all eight runtime snapshots and compare four representatives; see the floating-point matrix.

  • A malformed candidate typed bundle fails the cell.

  • Any other golden comparison result, such as MISSING or DIFFERENT, leaves the cell’s check passing. The golden status is recorded and decides the verdict at completion.

Each cell keeps its files in differential/engine/cells/<nnnnn>/, where <nnnnn> is the cell’s zero-based index in differential/engine/plan.json. A failed cell adds failure.txt with the traceback.

Completion. Engine completion requires every planned cell to be independently validated. The engine status is PASS only when every golden comparison is PASS.

Final accounting#

Validate differential summary reads differential/summary.json and requires:

  • PASS with complete serialization accounting: every required comparison exactly once, with zero differences;

  • a complete engine campaign with consistent required, completed and feature counts;

  • the launched dataset: the profile’s seed count and all live cases.

It uses the validated records. It does not rehash sources, reopen every bundle, repeat every oracle or authenticate saved results directories. Verdict rules lists every verdict rule, and differential/summary.json its fields.

The controller owns validated results in memory. A producer’s saved PASS label cannot complete a cell. Recovery after an interrupted run is diagnostic and cannot resume a qualified run.

Fixtures and profiles#

All supported scenes are checked-in synthetic data or deterministic generated inputs. No cockpit, factory or other private production asset is required. Fixture generation happens during preparation, before the consumer opens the resulting full stage path.

The serialization corpus compares every live case declared in engine_contract.json and synthetic records from 6 generated seeds (mr) or 100 (extended), and reads every historical database fixture. Independently authored values cover every serialized field, Unicode, audit data, exact IDs, repeated times, empty/singleton/multiple arrays and floating-point bit patterns. One outline is just large enough to cross the 65,536-byte external payload boundary.

The optimization cases (engine-optimization-* in engine_cases.json) use the smallest scenes that cross each production boundary: reuse and invalidation, prefetch and serial matrix windows, the matrix-cache budget and static chunk sizes. Each requires the actual reuse, prefetch, window or worker observation it targets as well as complete report equality. The budget case, engine-optimization-budgets, checks the matrix-cache budget, not total process memory.

Floating-point matrix#

Three base recipes exercise dynamic ordinary meshes, dynamic subnormal meshes and static meshes, each on a stage with four separated mesh-pair groups, under both managers. On x86-64, four rounding directions combine with four tiny-number settings: gradual underflow, flush-to-zero (FTZ), denormals-are-zero (DAZ) and FTZ+DAZ. That gives 3 × 16 × 2 = 96 cells. Linux AArch64 supports eight mode combinations, gradual underflow or flush-to-zero (FZ) in each rounding direction: 48 cells.

The fp-subnormal-kernel0 recipe adds one cell per tuple:

  • It explicitly requests intersection code 0, the value 0 of the overlap_code setting that selects the triangle intersection kernel (see Settings), on the subnormal stage, with the legacy manager, nearest-flush detection (nearest-ftz-daz on x86-64, nearest-fz on AArch64) and toward-zero-gradual extraction.

  • It uses zero tolerance. With a positive tolerance, PhysX selects its distance test for the triangle pairs of a bounding-volume leaf before it reads overlap_code, so the code would have no effect.

  • Recipes that omit overlap_code keep its default, code 3.

  • The recipe does not require equality across kernels or floating-point modes.

Each cell checks the prescribed action protocol and snapshots for synchronous, cached, alternate/repeated, independent recomputation, matched extraction, restart and asynchronous executions. It also requires the caller’s floating-point state to be restored. Dedicated native parallel controls separately test worker floating-point state and actual worker participation. Comparisons use the intended same-mode relation; different rounding directions need not produce bit-identical geometry. First, all eight runtime snapshots and their equality edges must pass. Then each backend compares four representatives (sync, alternate, oracle and matched) with its goldens. Both backends recompute outlines under the report caller’s controls.

Repository goldens and historical databases#

The approved catalog root is tests/sentinel/goldens/manifest.json. Run Sentinel in CI#

A CI job runs the same two commands as a local check, from ovclash/, against the portable input bundle that its build job staged. For the Linux x86-64 ovstage Release tuple:

./test_sentinel.sh check-tests --allow-skips --output <checker-directory>/checkers.json
./test_sentinel.sh run --backend ovstage --configuration Release --inputs <bundle-directory> --output <results-directory>

<bundle-directory> is the portable input bundle that the build job staged, <checker-directory> a new directory for the checker output and <results-directory> a new or empty results directory. On Windows, run the same commands with test_sentinel.bat. Each tuple needs its own job, its own bundle and its own results directories.

  • --allow-skips accepts platform-specific unittest skips; without it, any skip fails check-tests.

  • --inputs selects the staged bundle, which never triggers a build.

  • --engine-profile, else OVCLASH_VALIDATION_ENGINE_PROFILE, else OVCLASH_EQ_ENGINE_PROFILE selects the profile, mr (the default) or extended; see environment variables.

  • Each job’s own verdict is authoritative: run exits 0 only when the run passed; see exit codes.

  • Keep the results directory’s evidence/ and golden-proposal/ and the checker output (checkers.json and checkers.modules) as job artifacts. evidence/junit.xml feeds the CI system’s test report; see JUnit report. A golden-only failure’s golden-proposal/ can be accepted on another machine as it is; see propose from a run on another machine.

Read a failure#

Before you begin, you need the failed run’s console output and its results directory with the evidence/ directory; a CI job keeps both as job artifacts (see run Sentinel in CI).

  1. Read the Sentinel summary block; summary and final line lists its lines. It lists failed checks with their first reasons and the failure.txt or command log path.

  2. Read the final Clash validation CI gate failed: line. It names the failing command or condition.

  3. Open evidence/gate-summary.json. error holds the failure. Once the campaign has written its summary, checks_status reports the independent checks and golden_status reports the golden comparisons; gate-summary.json lists every field.

  4. Follow the evidence: evidence/differential/summary.json, evidence/differential/engine/results.json, the cell’s evidence/differential/engine/cells/<nnnnn>/failure.txt and the logs in evidence/logs/.

You are done when you can name the failed check and its cause: a failure.txt traceback, a failing command log, or the golden snapshots whose status is not PASS. evidence/junit.xml carries the same verdicts for CI test reports. Evidence layout describes every evidence file and status value. The examples of a native control failure, an engine cell failure, a golden-only failure and a startup failure show <elapsed> in place of each duration.

Shared stages and concurrency#

Eligible cells share deterministic USD assets from an invocation-owned pool. Compatible cells run grouped on one loaded native stage, keeping separate settings, selections, detections, snapshots and verdicts. Complete structured scene/recipe/dependency inputs determine reuse; filename equality alone does not. Changes to the selected scene state or unsupported composition require separate execution.

The independent OpenUSD scene session can reuse an answer for identical authored queries and literal expected values. It does not replace native detections. Immutable metadata text and successful nested semantic checks may be reused within one controller-owned admission operation. These caches are not global, not persisted across runs and not substitutes for required observations.

Ordinary eligible serial-engine cells may produce results concurrently in separate processes. Private, floating-point, recovery/fault and other incompatible cells stay exclusive. Shared loaded-stage groups execute as groups. Each producer owns its input, process tree and output directory; admission, caches and publication stay on the controller. --engine-workers 1 disables producer concurrency but keeps compatible stage reuse.

Child processes run under shared process supervision: a Windows Job Object, a Linux subreaper or an owned POSIX process group. Timeout and interruption drain owned work before results are consumed, and a successful exit alone cannot satisfy semantic checks.

Performance measurements#

Sentinel measures the existing correctness workload. It adds no benchmark loops or KPI thresholds. Each check line carries one global [current/total] index over the selected controls, serialization comparisons and engine cells, and the settled share of checks; see console output. The index counts work units, not elapsed time. The run’s UTC start time appears in its first line and in the Sentinel summary; phase lines show the monotonic run time.

The timing summary tables, SUMMARY engine and serialization campaign and SUMMARY CI driver (excluding CI checkout/uploads), report passed, failed and unfinished timed stages. Each row is <status> <elapsed>  <label>, indented by nesting depth, and each table ends with TOTAL   <label>  <elapsed>. For more than ten stages a table lists every failed stage plus the ten slowest. The summary JSON keeps every stage with its original identifier.

performance.json and performance.csv appear in evidence/ and in the differential campaign directory, evidence/differential/. Metrics use monotonic elapsed time; the displayed UTC times are for people and are never measurements. The console reports Performance: <n> metrics, <m> collection errors: <path>. Add or change a case#

Before you begin, you need a source checkout in which run locally passes on each tuple you can run, and the engine obligation that the case must satisfy.

  1. Identify the obligation and its supported axes in engine_contract.json; obligation fields lists its fields.

  2. Author deterministic inputs and an independent expected answer or explicit comparison relation.

  3. Add the case, with its fixture, settings, timeline, actions and deadline, to engine_cases.json; case fields lists every field.

  4. Connect the producer and the immediate semantic checker.

  5. Require the applicable process, loaded-library, settings, observation and public/private checks.

  6. Add focused negative checker tests for wrong or missing evidence.

  7. Update the source-derived field mappings of every API or storage schema that the change alters, and never silently default a new field.

  8. Map the case to an input family in FAMILY_CASES (tests/sentinel/golden_catalog.py).

  9. Run check-tests.

  10. Run normal validation, build_<backend> --<configuration> --validate, on every applicable tuple you can run.

  11. Run Sentinel on every applicable tuple you can run.

  12. Propose the new goldens from each run whose independent checks passed; see repository goldens and historical databases.

  13. Accept each reviewed proposal.

When check-tests, normal validation or the Sentinel run fails, read the failure, fix the case or the product and repeat from check-tests. Never propose goldens from a run whose independent checks failed. The change is complete when goldens verify prints a verification-only: PASS line and a new run of each tuple you ran ends with ALL PASSED. Sentinel Council approves. This is the way.. For the tuples you cannot run, follow changes that affect tuples you cannot run. The “Typed comparison contract” and “Updating fields and settings” sections of ovclash/tests/sentinel/README.md describe the typed comparison contract and the source-inventory workflow.

Glossary#

The Sentinel pages use one name for each of these concepts. Consumer terms such as backend, ovstage, OpenUSD and Suite API keep their meaning from the consumer glossary.

Term

Meaning

Build tuple

One platform, architecture, backend and configuration, such as Linux x86-64 ovstage Release. Sentinel supports twelve, and each has its own goldens

Installed SDK

The SDK install tree that a build installs, _build/install/<backend>, or the install/ directory of a portable input bundle: the content of an SDK archive. Sentinel checks it as the candidate

Candidate

The installed SDK under test and the results it produces (source_role candidate)

Portable input bundle

A staged copy of the installed SDK, its Python runtime, its OpenUSD dependency and the Sentinel helpers in _build/portable-inputs/<backend>/<configuration>; see portable input bundles

Driver

scripts/sentinel_ci.py, which the launchers run. It prepares the inputs, runs the native controls, starts the campaign child, judges the run and writes gate-summary.json

Campaign child

scripts/run_sentinel.py, which the driver starts under the label small-differential to run the campaign

Campaign

The serialization and engine checks that the campaign child runs: the Engine and serialization campaign phase

Controller

The process that plans, admits, journals and publishes results: the driver and, inside the campaign, the campaign child. A producer’s own PASS never completes a check

Producer

A child process that runs one cell or one serialization command and writes outputs for the controller to admit

Native controls

Existing native executables that run against the installed SDK before the campaign: the capture controls, the native target controls and, on ovstage, the observer controls; see native controls

Observer controls

The ovstage native controls of ovclash.sentinel_engine.test observer, which check private path, threading and cache observations and their equality with the public installed SDK

Checker tests

Sentinel’s Python controller and checker tests and the shared process-tree tests, which check-tests runs; see checker tests

Case

An engine case, one entry of tests/sentinel/engine_cases.json (see case fields), or a live serialization case of tests/sentinel/cases.json

Variant

One declared variant of a case, with its witness kind and optional overrides

Witness

The kind of evidence that a variant gives for an obligation: positive, negative or boundary

Obligation

A required behavior that tests/sentinel/engine_contract.json declares and one case satisfies; see obligation fields

Cell

One planned unit of checking. An engine cell is one case variant expanded over seed, scheduler, state sequence, floating-point mode, oracle, repeat and task budget; see engine campaign. A Suite cell is an engine cell of a case whose api_surface is suite. A serialization comparison cell is one required comparison of the serialization campaign

Oracle

The rule that determines a cell’s expected answer; see oracles

Snapshot

One typed result that a cell captures at a point of its action protocol, such as snapshot_bundles.oracle. Goldens are compared per snapshot

Typed bundle

A directory or ZIP archive of typed results: manifest.json, records.jsonl and optional payloads/

Golden

The reviewed typed result of one case, variant and snapshot for one build tuple and one set of frozen inputs, stored in the golden catalog. The Sentinel pages use no other name for it

Golden catalog

tests/sentinel/goldens/: the root manifest.json, its shards, the stored typed bundles and the historical database fixtures; see catalog files

Tuple file

The catalog shard expectations/<platform>-<architecture>-<backend>-<configuration>.json, which holds the golden rows of one build tuple

Shard

A catalog shard is one catalog metadata file with its own revision: an input family file, a tuple file or provenance.json. A checker shard is one slice of a checker module that check-tests runs in its own process

Golden-only failure

A run whose independent checks passed and whose golden status is MISSING or DIFFERENT. Such a run can supply a golden proposal; see golden-only failure

Profile

The engine profile, mr (the default) or extended; see declared combinations

Results directory

The directory that one run writes, _build/sentinel/<UTC time>-<backend>-<configuration> or the --output directory. Its evidence/ directory holds the run’s evidence

Drained

Said of an owned process tree whose processes have all exited. A command whose tree could not be drained leaves its output unverified and fails the run

Intersection code

The value of the overlap_code setting, which selects the triangle intersection kernel; code 3 is the default. See Settings

Report mask

The report_mask of a case: the report-buffer flags that its cells request, an even value from 0 to 30; see case fields

Release gate

The full release qualification. Sentinel never completes it, so every summary records release_gate_complete: false; see limits

Limits#

Passing Sentinel proves its declared scenarios and checks, not universal bug freedom, race freedom or full release readiness. The summary keeps release_gate_complete: false. Production-asset coverage, sanitizers, installed-product qualification and Kit integrations need their own evidence. The private observer wrapper runs one active context per process; Sentinel does not qualify several simultaneously active contexts that share it.
