Run KPI#

This page explains how to start KPI and what it prints when it starts: the launchers, input preparation, every option and environment variable, the settings block, the CI contract, the controller commands and the observer study. For a first run, follow the quick start. Pages in this guide lists the other KPI pages.

Run every command from the ovclash/ directory of a source checkout or source export. In the Python commands, $PY (%PY% in cmd.exe) is the KPI input Python that the quick start defines: the packaged CPython 3.12 of the staged inputs. The KPI glossary defines the KPI terms used here, such as portable input bundle, validation receipt, driver, controller, campaign, catalog, cohort, budget, package and verified drain. The consumer glossary defines backend, ovstage, OpenUSD and SDK archive.

The launchers set OVCLASH_KPI_LAUNCHER_DEFAULTS to the number of default arguments, for the startup check and the driver only. The settings block uses it to tell launcher defaults from your arguments. Do not set it yourself.

The launchers answer two requests themselves. These work without an SDK archive or a Python runtime:

  • --help or -h, anywhere on the command line, prints the launcher help.

  • --version as the only argument prints ovclash <version>.

Automatic preparation#

Without an explicit --inputs or --dist, the launcher makes sure that the default inputs belong to the checked-out source:

  1. It runs the startup check scripts/kpi_startup.py with the bundle’s Python. When that Python is missing, it goes straight to step 2.

  2. When preparation is required, it runs build_<backend> --release --validate --stage-inputs once. It adds package_sdk to OVCLASH_VALIDATE_EXTRA_TARGETS for this build.

  3. It runs the startup check again. Any result other than 0 now stops the launcher with exit 4.

  4. It starts the driver.

Startup check result

Launcher action

0: the SDK archive, wheel, portable inputs and producer receipt (the validation receipt of the build that produced the inputs) match each other and the checkout

Reuses the inputs and starts the driver

10: inputs are missing, invalid or built from other source

Builds once, as in step 2

11: as 10, for a local ovstage check of uncommitted source

Builds once with the diagnostic validation plan

4: invalid arguments, a source identity it cannot verify, or uncommitted changes in a baseline collection or CI run

Stops with exit 4. A build cannot fix this; see source identity

More rules:

  • The extra package_sdk target keeps the SDK archive when an inherited OVCLASH_VALIDATE_EXCLUDE_TARGETS drops test_c_compat_sdk_archive.

  • The Windows launcher sets OVCLASH_CI_REF_PROTECTED=false for the build when none of CI_JOB_ID, CI_COMMIT_REF_PROTECTED, OVCLASH_CI_PROVIDER, OVCLASH_CI_JOB_ID and OVCLASH_CI_REF_PROTECTED is set. The receipt then records an unprotected development ref, which KPI requires before it accepts an ovstage signing skip. An OpenUSD skip does not depend on the ref. See supported workflows.

  • The Windows launcher clears OVCLASH_KPI_LAUNCHER_DEFAULTS for the build.

  • A failed build stops the launcher with the build’s exit code.

  • Preparation runs at most once, before any KPI timer starts.

The settings block appears twice: the startup check prints it before the build, and the driver prints it again when the run starts. The Release preparation is required. line names the reason:

  • After a commit or an edit, it reads KPI startup: the checkout changed since the validated Release build. Release preparation is required.

  • When an SDK archive, wheel or receipt is missing or invalid, it reads KPI startup: the SDK, wheel, portable inputs or producer receipt is missing or invalid. Release preparation is required.

With uncommitted source, the startup check adds the notice described in source identity, and for a diagnostic build the line described in diagnostic validation plan. On Windows, the START: line names build_<backend>.bat.

Diagnostic validation plan#

A local ovstage check of uncommitted source only needs its build to be measurable. The startup check then returns 11 and prints:

KPI startup: uncommitted local check; preparing with the diagnostic validation plan (build, wheel and SDK packaging, staged inputs).

The launcher then validates less. It appends these targets to OVCLASH_VALIDATE_EXCLUDE_TARGETS: test_c_compat, test_cpp, test_python_runtime, the ovRTX viewer smoke test_ovrtx_sample, test_samples, test_no_clash_dependency, test_ovx_package_coherence and test_c_compat_sdk_archive. Build, install, the wheel (test_python_wheel), SDK packaging and staging still run, and so does signing when OVCLASH_CODESIGN is on. The receipt lists only the steps that ran. The START: line ends with (including package_sdk; diagnostic validation plan).

The startup check asks for the full plan instead when:

  • the source is committed;

  • the backend is OpenUSD;

  • the checkout has no Python test venv (_build/deps/venv/python_tests). Staging runs with that venv, and only test_python_runtime creates it;

  • the bundle’s Python is missing, so the startup check cannot run (the first run after a clean).

A baseline collection or a CI run never gets this plan: with local changes it stops before preparation. A diagnostic-plan build is always dirty, so it serves only a local check; see source identity. Committing changes the source identity, and the next run prepares with the full plan.

Source identity#

The startup check computes the same source identity that the build records in its provenance. Ignored files, such as everything under _build/, never count.

  • In a Git checkout, it uses the Git executable that the build tree recorded, or git on PATH when the tree is not configured. The build tree is the Ninja tree; on Windows it is the Visual Studio tree unless GENERATOR selects Ninja.

  • A source export without Git uses the content snapshot of scripts/source_snapshot.cmake. The startup check also uses the snapshot when the build tree recorded an empty or NOTFOUND Git, when an unconfigured tree finds no git on PATH, when Git finds no repository, or when the repository root is not the parent of ovclash/. The snapshot runs the CMake that CMAKE names, else the bundled CMake, else cmake on PATH.

Source state

Startup check

Measurement

Committed, no local changes

Reuses inputs built from this commit; otherwise builds

Runs

Source export without Git

Reuses inputs built from the same content; otherwise builds

Runs

Staged, unstaged or untracked changes

Reuses inputs built from the same working tree; otherwise builds

Only a local check, as a diagnostic check. A staged change that the working tree reverted counts as committed source, because the working tree then equals HEAD

With local changes, the identity is HEAD and the tree of the whole working tree: every staged, unstaged and untracked file that is not ignored. Git hashes unstaged and untracked changes into a scratch copy of the index, so your own index never changes. Staging a change keeps the identity; any edit changes it and makes the next run build again.

Baseline collection and CI measure only committed source. With local changes they stop at startup, before any preparation, with KPI startup: baseline collection measures only committed source; ... or KPI startup: CI measures only committed source; ... (exit 4). Commit or stash the changes first. With caller-managed inputs, the driver applies the same rule after preparation and stops with exit 4. Budget creation and calibration export also require committed source.

A local check of uncommitted changes measures and compares with the budgets as usual. Its verdict is for development only: a release-profile run exports no calibration evidence, and no budget package can be created from it. The run prints this notice:

KPI diagnostic run: the checkout has uncommitted changes. Limits are checked as usual, but the result is not release evidence; commit the changes for a recorded verdict or a baseline.

The notice appears each time the startup check runs (before an automatic build and again after it), after the driver’s Release preparation, and again after the verdict.

Caller-managed inputs#

An explicit --inputs or --dist turns automatic preparation off, even when it names the default directory. --inputs=PATH and --dist=PATH count too. The launcher then never builds, and the driver never builds either. Use this to measure inputs that were staged elsewhere.

Before you begin, make sure that the inputs meet these requirements. Troubleshooting gives the line that each failure prints.

  • <inputs>/python-runtime/bin/python3 (python-runtime\python.exe on Windows) must exist. Otherwise the launcher stops with exit 4 before the driver starts.

  • --dist must hold exactly one SDK archive (*.zip, *.tar.gz, *.tar.xz or *.tgz) and exactly one wheel. A --dist without an SDK archive, for example after a validation that excluded test_c_compat_sdk_archive, stops preparation with exit 4.

  • This checkout must hold exactly one passing validation receipt of that build; see prepare inputs explicitly.

  • In CI and in a baseline collection, the inputs must be built from committed source; see source identity.

Replace <bundle-directory> with the staged portable input bundle and <dist-directory> with the directory that holds its SDK archive and wheel.

Linux:

bash ./run_kpi.sh --inputs <bundle-directory> --dist <dist-directory> --output _build/kpi-staged-01

Windows:

run_kpi.bat --inputs <bundle-directory> --dist <dist-directory> --output _build/kpi-staged-01

The run then continues as with the default inputs: a passing check ends with All KPI workloads passed and stay within their approved limits. Everything is awesome! and exit 0; reports and verdicts lists the other exit codes.

Prepare inputs explicitly#

You can prepare the inputs yourself before you run KPI. The commands, including the Windows signing setting, are in the quick start. Preparation works like this:

  • Release validation packages the SDK archive and the wheel into _build/dist/<backend>.

  • Validation writes validation_receipt.json into the tree it validated, _build/compile/<backend>/<generator>/, where <generator> is vs or ninja. The local validation workflow describes it.

  • --stage-inputs copies the validated installed SDK (the install tree), its Python runtime and the Sentinel helpers into _build/portable-inputs/<backend>/Release. It compiles nothing. Portable input bundles describes the bundle and how restaging replaces it.

When configurations share an install, run the matching Release build and validation last. Staging refuses an install that holds another backend or configuration, and keeps the earlier bundle. For OpenUSD, use build_openusd and --backend openusd; OpenUSD has its own budgets.

KPI selects the receipt by the artifacts it describes, not by the tree it sits in. The driver and the startup check read validation_receipt.json from every _build/compile/<backend>/<generator>/ tree. Visual Studio and Ninja validations of one backend share _build/dist/<backend>, but each keeps its own receipt. KPI uses the one passing receipt that matches the packaged artifacts and ignores receipts of other artifacts.

With caller-managed inputs, preparation stops with exit 4 when no receipt matches, when the matching receipt did not pass, or when two passing receipts match. With the default inputs, the startup check treats the same cases as inputs that need preparation. A direct run --validation-receipt instead turns a receipt that did not pass into a campaign result; supported workflows states what a receipt must contain and how its state maps to a result.

Rules for the values:

  • Relative paths resolve against the current directory. --budgets is the exception: it resolves against ovclash/. In --budgets and PARENT_OVCLASH_KPI_BUDGETS, the literal texts {backend} and {platform} are replaced by the selected backend and platform.

  • A --budgets path that names a removed .kpi-budget.zip package is an input failure (exit 4). A missing path, or a file that is not a .kpi-budget.json package, supplies no budgets: such a file is never read, and the check stops with exit 3 before fixture generation. Check against a local package gives the outcome of each --budgets value.

  • The driver accepts abbreviated option names, for example --collection-sec 3600. The launchers recognize --inputs, --dist, --output and --backend only when spelled in full, so abbreviate none of these four.

  • strict admission with the four-core domain is rejected with exit 4. A collection also rejects strict admission and the inherited domain. Admission policy and CPU domain gives the defaults of each entry point.

  • A collection accepts only labels of the closed calibration vocabulary. Check mode accepts any label, but calibration export then fails. See runner and storage labels.

  • The public and calibration directories must not exist yet. Choose a new --output for every run; see outputs.

Options that the launcher does not interpret go to the driver unchanged. The launcher never chooses or approves budgets.

OVCLASH_KPI_LAUNCHER_DEFAULTS is set by the launchers; do not set it yourself. An explicit option always wins over a variable, and an empty variable means “use the default”. The OVCLASH_CI_* variables are the exception: each takes effect once it is set, even to an empty value. Console colors#

An interactive terminal shows the build’s palette: violet headings, bright green passes and bright red failures. The Linux launcher colors its own help headings, banner and PASS and failure lines too; the Windows launcher’s own lines stay plain. Redirected output, CI logs, progress.log, reports and JSON stay plain. A nonempty NO_COLOR, TERM=dumb, or a Windows console without escape-sequence support turns color off.

A passing check and a complete collection end with a fixed success sentence. The final summary and the collection progress log give the sentences and when they print.

Run KPI in another CI system#

A CI job runs KPI with the same launchers, options and driver as a local run. Only the CI context changes what the driver does. KPI reads that context only through tooling/ci_context.py, and no KPI module holds a server, project, job or revision constant. The producer build reads its part of the same context, the source revision, the ref name and the ref protection, through tooling/ci_context.cmake. The context itself is never written to a file; only validated IDs reach exported evidence. CI context describes how both sides build it.

Declare the job#

tooling/ci_providers/ holds one built-in provider adapter, which reads GitLab’s predefined CI_* variables. Any other CI system declares its job with provider-neutral variables. A declared job never reads provider variables, so set every field that you need.

Before you begin, the job must have staged its own portable input bundle and its dist directory, as in prepare inputs explicitly, from committed source. Replace <bundle-directory> and <dist-directory> as for caller-managed inputs. Run from ovclash/.

Linux:

export OVCLASH_CI_PROVIDER=example-ci
export OVCLASH_CI_JOB_ID=1234
bash ./run_kpi.sh --inputs <bundle-directory> --dist <dist-directory> --profile release \
  --summary-mode deferred --output _build/kpi-ci-1234
<bundle-directory>/python-runtime/bin/python3 -I -B scripts/kpi_ci.py --after-script \
  --public-output "$PWD/_build/kpi-ci-1234/public"

Windows (cmd.exe):

set "OVCLASH_CI_PROVIDER=example-ci"
set "OVCLASH_CI_JOB_ID=1234"
run_kpi.bat --inputs <bundle-directory> --dist <dist-directory> --profile release ^
  --summary-mode deferred --output _build/kpi-ci-1234
<bundle-directory>\python-runtime\python.exe -I -B scripts/kpi_ci.py --after-script ^
  --public-output "%CD%\_build\kpi-ci-1234\public"

The explicit --inputs and --dist keep the inputs caller-managed, so the job measures the inputs that its build staged. The first command exits with the run’s verdict: 0 for a pass, exit 75 or 0 for the CI CPU-contention warning, and the codes of reports and verdicts otherwise. The second command prints the final summary and always exits 0; for a passing run it ends with the check success sentence; see print the summary in a later step.

Print the summary in a later step#

With --summary-mode deferred, the driver finalizes the public record measurements.json and verifies cleanup, but prints no final summary. Print it from a later step of the job, one that also runs after a failure, a timeout or a cancellation of the measuring step. Run scripts/kpi_ci.py --after-script --public-output <public-output> with the input bundle’s Python (python-runtime\python.exe on Windows) and -I -B, as the second command in declare the job does.

The after-script follows these rules:

  • It reads only the public record. The public directory must hold exactly measurements.json.

  • It prints the final summary only for a record of the current context: the current job ID in a CI job, {"kind": "local"} otherwise. A verified pass ends with the check success sentence.

  • When the record is missing, invalid or from another job, or the CI job ID is invalid, it prints only KPI public snapshot unavailable; original verdict unchanged.

  • It always exits 0 and never changes the job result.

  • A collection ignores --summary-mode. Its progress.log and status.json are the record, so it needs no after-script.

Deadlines and frozen inputs#

  • Check mode has no campaign deadline, so only the job timeout of the CI system bounds a check run; see deadlines. A timeout fails the run like any other failure; only the supported CPU-contention case becomes the CI warning.

  • CI never writes the frozen contract files benchmarks/kpi/representative_*.json or the budget catalog. A job reads them from its checkout, and they grant it no calibration or approval authority. See frozen workloads and profiles and catalog rules.

  • Ref protection reaches KPI only through the producer’s validation receipt, never through the Python context. Set OVCLASH_CI_REF_PROTECTED for the producer build; see supported workflows.

Troubleshooting#

The launchers forward the driver’s standard error. Interpreter startup, import and loader failures can therefore appear before the driver establishes its filtered console. Those messages can include paths and are not sanitized by the campaign’s output filter.

During a campaign, the driver still suppresses raw Python and native console output and prints fixed progress, failure categories and verdicts. Use the exit code, the final summary and the public files. To retain the full execution record when investigating a failed step, run it directly with the controller, which prints the reason on standard error.
