KPI workloads and metrics#

KPI measures nine frozen workloads on three generated fixture bundles. This page defines what each workload does, its frozen settings, the work it must produce, and what each recorded time and memory value covers. The KPI glossary defines workload, bundle, attempt, campaign, controller, budget and the other KPI terms used here. Consumer terms such as backend, ovstage, OpenUSD, query, stage, duplicate and Suite API keep their consumer meaning. The KPI maintainer guide gives the quick start and explains how a run works, and Run KPI explains how to run KPI. Representative fixture stages explains how the bundles are generated, and KPI frozen contracts and maintenance the contract files behind these tables.

The three bundles are body-representative, cockpit-representative and body-representative-depth, a full-motion Body bundle that only the Dynamic depth workload uses. The workloads cover static and dynamic canonical reports (the overlap reports that the canonical API returns), fresh saves through the Suite API, Body maximum local depth in MEDIUM mode (OVCLASH_MAX_LOCAL_DEPTH_MODE_MEDIUM, the refined estimate of medium accuracy), Cockpit 7.5 mm clearance and Body duplicates-only detection. Both backends, ovstage and OpenUSD, run the same stages, settings, scopes and sample grids on Windows x86-64, Linux x86-64 and Linux AArch64. Every launcher run measures the same nine workloads, and no renderer or GPU is needed.

Depth, clearance and duplicates-only workloads#

These three workloads each change one setting of a base workload. Static clearance and duplicates-only run on the bundle of their base static workload. Static clearance has its own reviewed expected work. Duplicates-only keeps the 353 Body static duplicates and expects no overlap pairs, records, elements or report bytes.

Dynamic depth runs on the dedicated body-representative-depth bundle, which compresses the same Body motion into 1.125 seconds; see geometry and motion. Its expected work binds every record’s maximum local depth to its pair, sample and element count. MEDIUM depth is computed inside the timed pipeline.

The nine-workload contract describes the extension and depth references, how the depth rows are captured and replayed, and what the references do not prove.

Timing boundaries#

operation_seconds runs from runtime creation through usable results: complete canonical report consumption, or a successful explicit Suite save. A Suite operation also includes fresh database creation and query insertion. Process launch, module import, stage generation, CPU admission and teardown are outside this interval. The attempt’s Total in the console workload tables is the attempt’s wall time: it adds CPU placement and admission, process launch, module import, verification, retention and cleanup to the operation. Each attempt starts a fresh process and runtime after the input preflight, the content hash of the bundles at the start of the session, has warmed the filesystem cache, so it is not a cold-disk measurement. Suite workloads record this as the local-disk-warm-cache-after-preflight filesystem policy.

Each attempt records these clocks in its metrics object. Every value is a number of seconds. “Canonical” marks the seven canonical-report workloads (operation canonical-cold), and “Suite” the two Suite saves (operation suite-fresh-save).

Metrics and measurement boundaries#

The noise gate and the budgets cover only the required metrics of each workload:

Operation

Required metrics

Canonical report (canonical-cold): every workload except the Suite saves

operation_seconds, load_seconds, pipeline_step_seconds, result_capture_seconds, resident_high_water_bytes; on Windows also private_high_water_bytes

Suite save (suite-fresh-save)

operation_seconds, load_seconds, pipeline_step_seconds, extraction_serialization_seconds, database_bytes, resident_high_water_bytes; on Windows also private_high_water_bytes

Seven canonical and two Suite workloads give 47 required cells per CPU model on Linux and 56 on Windows. Every other recorded value is descriptive and has no budget:

  • pipeline_samples_per_second is the canonical dynamic sample count divided by pipeline_step_seconds.

  • logical_payload_bytes is the sum of stored BLOB lengths from the controller’s metadata scan.

  • serialization_seconds records the same interval as extraction_serialization_seconds.

  • The sampled and starting memory values are described in memory scope.

database_bytes is the physical length of the closed SQLite file. It is a required metric with a budget in each platform’s packages, not an expected value, because it differs between platforms; see expected-work identity.

The budget noise of extraction_serialization_seconds is at least 30% of its pooled median, because its time varies between runner hosts more than one collection job shows; see budget limits.

Canonical cold operations#

The operation starts immediately before context creation. It includes stage opening, complete settings application and readback, scope, pipeline creation and execution, and every requested report buffer. Report mask 30 copies the matrices, the point-size scalar, faces, outlines and points in bounded chunks, and releases each borrowed report. The same traversal collects pair, sample and element metadata. The six base workloads have no payload hash oracle, raw binary replay capture or second report traversal. The Body dynamic-depth workload adds the post-result-ready metadata replay described in the nine-workload contract. report_bytes counts the two matrices, the point-size scalar and the buffers at their native field sizes, excluding pointers and Python object overhead. Extraction neither keeps nor hashes the buffer contents.

Canonical attempts also keep diagnostic buffer counts in benchmark-report-cardinalities.bin and a canonical pair-name mapping in benchmark-report-cardinality-pairs.json. Each packed 33-byte row identifies its pair and sample, the face-buffer counts for both canonical object names, the outline-segment count, the point-index count, the element count and the point-owner side. These are counts from the same report lease; no geometry or buffer content is copied again. Collecting them belongs to metadata time inside the operation. Writing and hashing the files happens after result-ready and belongs to retention_seconds. The controller checks their bounded file lengths, hashes and binding to the compact summary without replaying single rows.

The files help locate a report-volume difference; the expected-work and exact volume checks still decide the verdict. They are bounded diagnostic evidence (32 MiB for the pair mapping, 160 MiB in total), not a geometry oracle or a source of new expectations.

The timer stops at result-ready, before statistics, the expected-work comparison, receipt writing and teardown. Context creation is included; process launch, module import and input preparation are outside. A fresh child gives a cold library state, while input preflight has already warmed the filesystem caches.

Dynamic and Suite operations#

Pipeline throughput excludes loading and report consumption. Step-name lookup and schedule validation are outside the step-call sum. A schedule cannot be inferred from report records alone, because some required samples have no clashes.

The Suite operation starts before runtime, serializer and data-handle creation. It includes fresh database creation, query insertion, stage opening, settings and scope, the pipeline, a full fetch_and_save_overlaps iteration, iterator closure, native commit and a successful explicit data.save(). This is API-level save completion, not a power-loss durability guarantee. Serialization is already inside the operation.

After result-ready, the child collects live metadata, closes the database and drains native owners. The controller then scans the closed database once. It compares every stored header and frame’s metadata with the live results and the frozen expectations, including the exact saved query settings and logical BLOB length. No geometry predicate or payload decoding runs. DELETE journal mode and the absence of the WAL (write-ahead log), SHM (shared-memory index) and journal sidecar files are required. The controller hashes the database and keeps benchmark-stored-summary.json for calibration export, which does not repeat that scan.

Memory scope#

Linux VmHWM and Windows PeakWorkingSetSize cover the operation child from process startup through result-ready, as resident_high_water_bytes. Windows also records PeakPagefileUsage as private_high_water_bytes. These counters include Python, runtime bootstrap, normal result capture and the in-process observer, even though operation latency starts later. They exclude the controller and post-result verification and are not process-tree aggregates. The public-API operation must not spawn descendants.

Each memory value is an integer number of bytes in the attempt’s metrics object. A value that the observer could not take is left out of metrics, so only the required metrics must be present:

All of them describe absolute memory sizes, not growth; do not add or subtract them as separate allocations. Resident memory is RAM held by the process, including shared pages. This observer provides no private-memory counter on Linux.

Memory freezes at the explicit result-ready boundary, before the remaining audit, receipt serialization and teardown. Canonical metadata collected inside the operation is included. A final process-exit peak cannot repair an absent boundary or a missing counter. Resident and private-commit values are distinct series; neither establishes minimum machine RAM or the capacity for an arbitrary scene.
