Testing and validation strategy#

Validation tests the product as it ships:

  • test_cpp, test_c_compat and test_python_runtime load the native library from the install tree (_build/install/<backend>), not from the compile tree. Each run therefore also checks that the runtime loads from the install layout, that its dependency closure is complete and that the OpenUSD plugin registry is set up.

  • test_c_compat_sdk_archive repeats the C consumer check against the extracted SDK archive. test_python_wheel checks the wheel in a clean virtual environment.

  • Source-contract tests read the sources and public headers directly. They pin the C ABI layouts and prototypes, the argument forwarding of every export and the backend parity of the canonical API.

Rules:

  • During development, run the focused tests of the surface you changed; see Run focused tests.

  • Before handoff, run the full gate that Required validation names for the change. --validate and test_all.* run it. A passing ovclash.native.test --test run alone does not complete the gate.

  • Sentinel runs separately. It checks the engine and serialization results of one build against independent oracles and reviewed goldens. It never compares the two backends with each other, and it does not qualify a release.

Native test programs#

tests/native/CMakeLists.txt builds the native test programs. scripts/test_cpp.cmake is their only run inventory: it lists each group, its selectors and its timeout. The ovclash project does not register native tests with CTest.

  • Build-tree programs land in <compile-tree>/<platform>/<configuration>/tests/, for example _build/compile/ovstage/vs/windows-x86_64/release/tests/.

  • ovclash.native.test also installs into _build/install/<backend>/bin. test_cpp runs that copy. No SDK archive or wheel ships it.

Every program accepts --help and --version. --help names the program’s purpose and selectors:

ovclash.suite_guard_failure.test (ovclash <version>)
Check allocation failure containment at Suite guard boundaries.

Usage: ovclash.suite_guard_failure.test entry|exception-format|restore
One selector is required; injected failures must be contained.
Example: ovclash.suite_guard_failure.test entry

Controls:
  -h, --help  Show this help and exit.
  --version   Show the ovclash build version and exit.

Add a native test#

Before you begin, build and install the backend that the test covers, so that _build/install/<backend>/bin holds ovclash.native.test (Test and validate). A test that needs a stage uses a fixture under tests/data/.

The backends that a test covers decide where it registers in the tests list of runRegisteredTests() in TestNativeClash.cpp:

The test covers

Its registration block

Both backends

Outside the backend blocks

ovstage only

The existing #if defined(OVCLASH_OVSTAGE_ONLY) block

OpenUSD only

The existing #if !defined(OVCLASH_OVSTAGE_ONLY) block

  1. Write the test in the source file of its behavior area.

  2. Declare it in TestNativeClash.h.

  3. Register it with OVCLASH_NATIVE_TEST(name) in the registration block of its backends.

Two scheduling lists take only some tests. Add the test to each list that applies to it before you rebuild:

  • kSlowTestCosts in TestNativeClash.cpp: a test much slower than its neighbors gets an entry with its approximate duration from a serial Release ovstage run. A test of ordinary duration gets none. The estimate only balances the shards; every test still runs exactly once.

  • _OVCLASH_NATIVE_FRESH_PROCESS_TESTS in scripts/test_cpp.cmake: a test that needs a process in which no other test has run gets an entry, and test_cpp then runs it alone with --test <name>. Any other test gets none.

For example, a test that expects one overlap between two meshes of an existing fixture:

// TestNativeMeshQueries.cpp
void testMeshPairHasOneOverlap()
{
    ovclash_context_t* context = nullptr;
    checkApi(ovclash_create_context(&context), "failed to create clash context");
    const std::string fixturePath = toApiPath(getFixturePath("mesh_mesh_overlapping.usda"));
    checkApi(ovclash_open_stage(context, makeString(fixturePath)), "failed to open mesh fixture", context);

    ovclash_settings_t settings;
    ovclash_reset_settings(&settings);
    settings.flags &= ~static_cast<uint32_t>(OVCLASH_SETTINGS_FLAG_ENABLE_POINT_CLOUDS);
    checkApi(ovclash_set_settings(context, &settings), "failed to apply query settings", context);

    const ovclash_string_t scopeA[] = { makeString("/World/Objects/meshA") };
    const ovclash_string_t scopeB[] = { makeString("/World/Objects/meshB") };
    checkApi(ovclash_set_scope_paths(context, scopeA, 1u, scopeB, 1u), "failed to set mesh scope", context);
    runSyncPipeline(context);

    uint32_t overlapCount = 0u;
    checkApi(ovclash_get_overlap_count(context, &overlapCount), "failed to read the overlap count", context);
    check(overlapCount == 1u, "expected exactly one mesh overlap");
    ovclash_release_context(context);
}

// TestNativeClash.h
void testMeshPairHasOneOverlap();

// TestNativeClash.cpp, in the tests list of runRegisteredTests()
OVCLASH_NATIVE_TEST(testMeshPairHasOneOverlap),

makeString takes a std::string or a string literal and does not copy it, so the string must outlive the call.

Notes:

  • borrowed programs compile SuiteFetch.cpp with OVCLASH_OVSTAGE_ONLY=1, the ovstage report mode. owned programs compile it with 0, the OpenUSD mode. Both backend builds produce both.

Validation scheduling#

scripts/test_cpp.cmake turns the programs into independent groups:

  1. It writes one small CMake driver per group to <validation-dir>/native_test_tasks/ and the task list to <validation-dir>/test_cpp_tasks.json. <validation-dir> is _build/validation/<backend>/<generator>/<configuration>.

  2. scripts/run_parallel.py runs the groups as separate processes. It captures each group’s output and reports every group, even when another one fails.

  3. The first group of each program also runs --help and --version. The help must contain Usage: and the version output (ovclash <version>).

Why some groups differ:

  • testParallelContextLifecycleOnBothBackends races the first context creation of a process. It also runs inside its shard, but only a fresh process reaches that first creation.

  • The fetch and batching programs link no backend code. They compile only their test sources, SuiteFetch.cpp and the Suite storage objects, with the report mode fixed per program. Both backend builds therefore produce the same program, and the ovstage validation for the same platform and configuration qualifies it. Sentinel’s native controls still run them on both backends. Return a group to the OpenUSD inventory if it ever compiles or links backend code.

Ordering and limits:

  • Groups start in list order, so the long ones start before short groups fill the workers. The order is: the native shards and the fresh-process test, then instancing_graph and dynamic_failure, the other programs, the suite_* groups longest first, and the selectors last.

  • The suite_* program groups time out after 180 seconds. owned_async_launch and the three ovstage controls time out after 30 seconds. The other groups have no timeout, so a hang shows as a START line without a verdict.

  • By default, validate_all runs the groups in parallel and a direct test_cpp run runs them one at a time. Parallel tests and shard planning describes OVCLASH_PARALLEL_TESTS and OVCLASH_PARALLEL_JOBS.

Each group’s full output goes to <validation-dir>/run_parallel_logs/test_cpp/<group>.log, with / in the group name replaced by _. The console shows the start and verdict of each group, explicit skips and the full output of failed groups. For example, on ovstage (times are illustrative):

Python coverage#

The test_python_coverage target reruns the product Python suite (tests/python_tests) under coverage.py. It runs scripts/test_python_runtime.cmake with PYTHON_TEST_COVERAGE=ON (a -D value or the environment; off by default). --validate never runs it, because instrumenting every frame makes the suite measurably slower.

The coverage run differs from normal validation:

  • It keeps the full module inventory, including the Sentinel controller tests, so the shipped code that they exercise is measured. The ovRTX clash sample app suite is not included.

  • The coverage sources are the shipped package directories under python/ and the top-level ovclash_suite module. A shipped module that no test imports reports 0% instead of disappearing.

  • It writes coverage.json, coverage.xml and html/ to _build/coverage/python_tests/ before the pass/fail check, so a failing suite still leaves a report.

  • Its ordinary test shards have no timeout, as in normal validation.

The target depends on install_sdk, so it rebuilds and reinstalls first. To measure an existing install without that step, run scripts/test_python_runtime.cmake directly with BUILD_TYPE, BUILD_DIR, INSTALL_DIR, OVCLASH_OVSTAGE_ONLY and -DPYTHON_TEST_COVERAGE=ON.

The target only measures. scripts/parse_coverage.py is the gate. From ovclash/, after an ovstage build:

The gate rules:

  • It exits 1 when any single package is below the floor, so a weak package cannot hide behind a large one. A dashed line separates the packages below the floor.

  • It exits 1 on every unusable report, including a shipped package missing from the report. A run without a coverage signal never passes.

  • The floor is 60%, set in DEFAULT_MIN_COVERAGE. --min-coverage or OVCLASH_MIN_COVERAGE overrides it with a finite percentage from 0 to 100.

  • The floor is a ratchet toward the 85% of the clash-detection gate of Kit, not a target. Raise it as coverage grows. Never lower the default to turn a failing gate green.

Native Suite test build and sample gate#

Shared Suite storage objects#

The Suite storage test programs share the storage sources through the ovclash.suite_storage OBJECT library in tests/native/CMakeLists.txt. Storage therefore compiles once, not once per program.

  • MSVC builds a second variant, ovclash.suite_storage_allocation, with _ITERATOR_DEBUG_LEVEL=0 in Debug. The allocation-failure programs (suite_writer, suite_directory, suite_fetch_* and suite_report_failure_*) link it in Debug and the normal variant otherwise.

  • The objects link into each program, so each program’s replacement allocators and stubs still apply to the storage code.

  • The object libraries set VS_GLOBAL_OvClashPreserveIntermediateDirectory and VS_GLOBAL_OvClashPreserveOutputDirectory. cmake/Directory.Build.targets.in then leaves their intermediate and output directories where CMake put them. CMake embeds those object paths in the consumers’ link commands, so relocated objects would break the link.

Persistence cases of the sample gate#

test_samples runs scripts/test_samples_default_clashdb.cmake once per language, python and cpp, after the clash_suite_api launcher check of How the samples are tested. The script runs the persistence-output cases of the clash_suite_api sample one after another, on a copy of tests/data/time_sampled.usda:

  • The first case runs through the sample launcher. That covers argument forwarding and builds the C++ sample against the install tree under test, in the requested configuration. The other cases call the built executable or clash_suite_api_python.py directly.

  • The passing cases cover:

    • SQLite with JSON and HTML exports, and an exact --clashdb path;

    • the directory store alone and with HTML;

    • the directory store with SQLite: first run, append and overwrite, including nested paths;

KPI harness code map#

benchmarks/kpi/ measures the nine frozen KPI workloads. The KPI maintainer guide lists the page that owns each KPI topic, and the source map gives the role of every module. Sentinel owns product correctness: the KPI workload-consistency check verifies only the frozen work, never geometry or payload correctness.

These modules hold the boundaries that a code change must keep:

Module

Boundary

representative_workloads.py

Never runs the product to learn expectations. Preparation generates the fixtures before any timing and checks each bundle against its pin

benchmark_execution.py

Runs no geometry predicate or payload digest. Each requested report buffer is copied once, and the report cardinalities come from the same pass

benchmark_session.py

A session ticket is no proof of the fixture bytes. A failed content check at the explicit session close invalidates the session

Derives every verdict itself, never from a label that the child supplies

Runs with an explicit interpreter in isolated mode (-I) and explicit bindings, so it ignores PYTHONPATH. It records the runtime it actually loaded

Never supervises processes. The memory observation covers the operation process only; descendants are not measured

Imports no ovclash runtime

Decides sampling; a stable decision never approves a baseline

Proposes limits from admitted calibration observations; never approves them

Every edit to a Python file under benchmarks/kpi/ or tooling/ starts a new measurement identity, even an edit to a comment. The benchmark helpers that KPI shares with benchmarks.backend_timings live in benchmarks/kpi/, so an edit to a standalone benchmark package leaves the identity unchanged.

KPI baseline collection files and selection#

These rules implement the collection that Collect a baseline describes.

Output ownership#

baseline_files.output_lock(output) makes one thread of one process the owner of an output directory. generate_series() holds it on the generated series while it writes and publishes it.

  • The lock is a nonblocking OS lock on a sibling file, .<name>.controller.lock: msvcrt.locking on Windows, flock elsewhere. A second owner fails at once with baseline_output_busy.

  • The lock key is the resolved, case-normalized path, so two spellings of one directory take the same lock. The lexical path is checked first: a symbolic link or Windows reparse point in it fails with baseline_output_invalid_path. The checkout’s own _build link is the only exception.

  • Ownership is reentrant within one thread and ends when the process exits.

  • Lock files stay in place, so two processes can never lock different files for one output. The collector removes only the released lock of its one-shot staging directory.

  • Only the acquiring process unlocks. A forked POSIX child that unlocked its inherited file description would release the parent’s lock (flock semantics).

<parent>/<name>/                     the output directory
<parent>/.<name>.controller.lock     its lock file, kept after release

Outputs lists the staging directories and lock files that a stopped collection can leave.

Status and renames#

  • baseline_files.atomic_write() publishes status.json (collection status and exit codes gives its fields). It writes a temporary sibling and replaces the file with os.replace, so readers see the old or the new file, never a partial one. This protects against interrupted writes, not against power loss.

  • Windows refuses to replace a file, or to rename a directory, while another process holds a handle in it, such as a polling reader or a scanner. The replace retries for at most 0.75 seconds. The rename of the generated tree retries for at most 7.85 seconds, inside the 30-second publication reserve, and never starts a retry after the deadline. POSIX never retries.

Bounded receipt reads#

Reader

Accepts

Byte bound

baseline_files.read_receipt()

Regular files with no link in their path

  • Both readers size each request to the bytes still expected, at most 64 KiB, and then read one more byte to detect growth.

  • read_receipt() also compares the device, inode, size and modification time of the path and the open file before and after the read.

  • Requesting the whole bound on every read would make even a tiny receipt allocate tens of MiB.

Selection cost#

scan_campaigns() in baseline_selection.py selects exactly. It ranks every sorted group of N whole campaigns, C(candidate_count, N) groups, as Campaign selection defines.

  • It validates each campaign’s observations and computes its metric medians once, before the enumeration.

  • It first checks that each metric’s widest possible score is a valid number, so pruning cannot hide an invalid score.

  • A group is abandoned as soon as one metric’s score exceeds the worst score of the best eligible group so far.

  • The pooled noise gate tries the most recently rejecting metric first.

  • An eligible group with a zero score ends the search. Sorted campaign IDs already break ties.

  • When any observation is 1e300 or more, the gate evaluates every metric in key order instead, so overflow errors surface unchanged.

  • The worst case stays O(C(candidate_count, N) × metrics), notably when no group qualifies. No candidate cap, approximation or weakened noise gate is used, so a larger N can need more collection and selection time.

  • The collection deadline is checked between every step.
