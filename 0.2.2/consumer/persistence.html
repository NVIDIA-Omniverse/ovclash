Persistence: Stores, Records and Clash States#

The Suite API saves clash results in a store that the caller opens explicitly. Every store holds the same four record types: queries, clashes, frames and point-cloud settings. Two built-in stores keep them, a SQLite database file and a folder of JSON files, and both work through one data API: the Python ClashData facade over a serializer, the class that reads and writes one kind of store, and the C ovclash_suite_data_t handle.

This page covers what all stores share:

  • Choosing a store compares the two built-in stores.

  • The walkthrough reads the store that Suite Workflows wrote, reviews its clashes and reads it again from C.

  • The object model, Opening and committing and CRUD are the reference for the records and the handle.

  • Saving detection results and Clash states cover fetch-and-save, its transaction rules and the clash states it maintains.

  • Custom stores, Numeric fidelity, Schema compatibility and Failures that do not raise complete the reference.

SQLite serializer and Directory serializer document each store’s format. Legacy Containers covers the .clashDetection file of Kit’s clash detection extension, a legacy container, and Export turns records into JSON or HTML reports.

Choose the SQLite serializer for large stores, compact storage and write throughput. It is the default. Choose the directory serializer when people or tools must read, diff or version the records as text. It costs more than SQLite in parsing, memory and file count, and it keeps every clash header in memory while the store is open.

Neither store converts the other’s format. To move records from one store to the other, read them through one handle and insert them through another. A NaN that the directory store holds cannot be written to a SQLite store. A custom store keeps records in storage that you implement, under the same transaction contract.

Walkthrough#

Before you begin, Step 1 to Step 3 need:

  • dynamic.ovclashdb in the current directory. Run the script from Step 3 of Suite Workflows to create it. It holds one query with 8 clashes.

  • The ovclash_suite Python package for the Python steps. Run each script from the directory that holds dynamic.ovclashdb.

  • For the C step, <ovclash_suite/ovclash_suite.h> and the ovclash library from the SDK archive.

The steps use the default SQLite serializer. Apart from creating and destroying the serializer (Directory serializer shows how), the Python code is the same for a directory store.

Step 1: Read the store#

This script lists the queries, the clashes of each query and the first frames of one clash:

from ovclash_suite import ClashData

data = ClashData()
try:
    data.open("dynamic.ovclashdb")
    if not data.is_open():
        raise RuntimeError(data.last_error() or "could not open dynamic.ovclashdb")

    for query_id, query in data.fetch_all_queries().items():
        print(f"Query {query_id}: {query.query_name}")
        overlaps = data.find_all_overlaps_by_query_id(query_id, False)  # without frames
        for info in overlaps.values():
            mesh = info.object_a_path.rsplit("/", 1)[-1]
            kind = "hard" if info.is_hard_clash else "soft"
            print(
                f"  {mesh}: {kind}, {info.state.name}, {info.num_records} frames,"
                f" min distance {info.min_distance:.3f}"
            )

        first = next(iter(overlaps.values()))
        frames = data.fetch_clash_frame_info_by_clash_info_id(first.identifier, num_frames_to_load=3)
        print(f"First frames of {first.object_a_path.rsplit('/', 1)[-1]}:")
        for frame in frames:
            print(f"  t={frame.timecode:.3f} s, {frame.overlap_tris} triangles")
finally:
    data.destroy()

  • find_all_overlaps_by_query_id() returns a dict keyed by overlap_id, the clash hash as text. The clashes come in overlap_id order.

  • is_hard_clash is true for a hard clash: a mesh clash with min_distance 0 that is not a contact. is_contact is true when such a pair’s max_local_depth stays within depth_epsilon, or is exactly 0 when depth_epsilon is not positive.

  • is_soft_clash is true for a soft clash, a mesh clash with a positive min_distance. The meshes do not touch, but they are closer than the query’s tolerance of 5 units.

  • Every clash starts as NEW. Fetch-and-save maintains the state; see Clash states.

Step 2: Review clashes in one transaction#

This script approves the soft clashes and writes all changes in one transaction:

from ovclash_suite import ClashData, ClashState

data = ClashData()
try:
    data.open("dynamic.ovclashdb")
    query_id = next(iter(data.fetch_all_queries()))
    for info in data.find_all_overlaps_by_query_id(query_id, False).values():
        if info.is_soft_clash:  # closer than the tolerance, but not touching
            info.state = ClashState.APPROVED  # also refreshes last_modified_*
            info.comment = "Clearance accepted in review."
            data.update_overlap(info, update_also_frame_info=False, commit=False)
    data.commit()  # one transaction for the whole batch

    counts = data.get_overlaps_count_by_query_id_grouped_by_state(query_id)
    for state, count in counts.items():
        print(f"{state.name}: {count}")
finally:
    data.destroy()

Expected output:

NEW: 6
APPROVED: 2

  • commit=False batches the writes. The single commit() writes them together. See CRUD for the batching and rollback rules.

  • update_also_frame_info=False keeps the stored frames. The default True replaces the stored frames with the frames attached to info. A ClashInfo read with fetch_also_frame_info=False has none attached, so the default would delete its frames.

  • Assigning a review field refreshes the modification metadata. See The object model for the fields you can assign.

Step 3: Read the store from C#

This program opens the same store, reads the first query and walks its clashes with a cursor. Save it as a C source file, and build and link it against the SDK archive as C/C++ Quickstart shows. When the build cannot find the headers or the program does not start, see Configuring with CMake and Starting a C or C++ program. Run it from the directory that holds dynamic.ovclashdb:

#include <ovclash_suite/ovclash_suite.h>

#include <stdio.h>

static int ok(ovclash_suite_result_t result)
{
    return result.status == OVCLASH_SUITE_STATUS_SUCCESS;
}

int main(void)
{
    static const char path[] = "dynamic.ovclashdb";
    const ovclash_suite_string_t store = { path, sizeof(path) - 1u };
    ovclash_suite_data_t* data = NULL;
    ovclash_suite_overlap_cursor_t* cursor = NULL;
    ovclash_suite_query_view_t query;
    ovclash_suite_clash_info_record_view_t overlap;
    uint32_t has_value = 0u;
    int64_t query_id = -1;
    int status = 1;

    if (!ok(ovclash_suite_data_create(&data)) || !ok(ovclash_suite_data_open(data, store)) ||
        !ok(ovclash_suite_data_get_query_at(data, 0u, &query)))
        goto cleanup;
    query_id = query.identifier; /* the view is reused by the next query read */
    printf("Query %lld: %.*s\n", (long long)query_id, (int)query.query_name.length, query.query_name.ptr);

    /* offset 0, limit 0: every overlap of the query, without frame payloads */
    if (!ok(ovclash_suite_data_get_overlaps_by_query(data, query_id, 0, 0, &cursor))) goto cleanup;
    for (;;)
    {
        /* has_value is 0 both at the end and on error, so check the status first */
        if (!ok(ovclash_suite_overlap_cursor_next(cursor, &overlap, &has_value))) goto cleanup;
        if (!has_value) break; /* running out of rows is not an error */
        /* overlap borrows cursor memory until the next advance: copy what you keep */
        printf("  %.*s: state %u, %u frames\n", (int)overlap.overlap_id.length, overlap.overlap_id.ptr,
               overlap.state, overlap.frame_count);
    }
    status = 0;

cleanup:
    if (status != 0)
    {
        ovclash_suite_string_t error = ovclash_suite_get_thread_last_error();
        fprintf(stderr, "error: %.*s\n", (int)error.length, error.ptr ? error.ptr : "");
    }
    ovclash_suite_overlap_cursor_destroy(cursor); /* destroy cursors before their data handle */
    ovclash_suite_data_destroy(data);
    return status;
}

The detection fields run from overlap_type to overlap_elements, plus the six penetration_depth_* axes. The review fields are state, priority, person_in_charge and comment, and the two timestamps and last_modified_by record changes. is_contact, is_hard_clash, is_soft_clash, is_duplicate and is_point_cloud_clash classify a record from its own fields, without a native call.

Two ClashInfo rules:

  • Most fields are read-only after construction. Assigning identifier, query_id, overlap_id, overlap_type, present, min_distance, depth_epsilon, tolerance, an object_a_* or object_b_* field, start_time, end_time, num_records, overlap_elements, creation_timestamp or last_modified_by raises AttributeError.

  • Editable fields refresh the modification metadata. Assigning state, priority, person_in_charge, comment, max_local_depth or a penetration_depth_* field goes through the native model. It sets last_modified_timestamp to the current time and last_modified_by to the current user.

The underscore-prefixed legacy aliases, such as _state, bypass both rules. Fetch-and-save maintains present and state; see Clash states.

Opening and committing#

ClashDataSerializerSqlite and ClashDataSerializerDirectory each own a native ovclash_suite_data_t, created by ovclash_suite_data_create() and ovclash_suite_data_create_directory(). ClashData is a facade over any AbstractClashDataSerializer:

  • ClashData() creates and owns a closed SQLite serializer.

  • ClashData(serializer) uses a serializer you own. destroy() then only closes it, and you destroy the serializer yourself.

This script opens or creates results.ovclashdb in the current directory, adds one query and commits it:

from ovclash_suite import ClashData, ClashQuery

data = ClashData()
try:
    data.open("results.ovclashdb")
    if not data.is_open():
        raise RuntimeError(data.last_error() or "could not open results.ovclashdb")
    query = ClashQuery(query_name="Example query")
    data.insert_query(query, commit=False)  # pending until commit()
    data.commit()
    print(f"Saved query {query.identifier}")
finally:
    data.destroy()

It prints Saved query <identifier>, where <identifier> is the identifier that the store assigned.

Call

Behavior

open(path)

Closes any open store, then opens path. Does nothing for an empty path, or when the store was opened through an absolute path that path resolves to.

is_open()

Reports whether a store is open, including an unnamed one.

commit()

Commits pending writes.

save(path=None)

Without a path, commits pending writes. On a SQLite store opened or migrated from a .clashDetection container, it also exports to that container until a save() or save_as() succeeds; after that it only commits to the temporary copy, so pass the container path to save_as() to export again. See Legacy Containers. With a path, calls save_as(path).

save_as(path)

SQLite copies the store to path and makes the copy current. A .clashDetection target instead exports a snapshot and keeps the current store. A directory store copies itself to an absent or empty directory outside itself and makes the copy current. Saving to the store’s own path only commits.

close()

Attempts to commit pending writes, including partial fetch results, then closes. A failed commit requests rollback, raises, and keeps the store for inspection and retry.

destroy()

Closes like close(). Then destroys the serializer that ClashData() created, with its native handle. A serializer you passed in is only closed.

These rows describe ClashData over a built-in serializer. A custom store defines its own behavior. SQLite serializer and Directory serializer give each store’s details.

The C calls follow the same sequence. This function belongs in a C source file of your program; it opens the same store, prints its query count and commits:

#include <stdio.h>

#include <ovclash_suite/ovclash_suite.h>

/* Returns 0 on success. */
static int count_queries(void)
{
    ovclash_suite_data_t* data = NULL;
    const char path[] = "results.ovclashdb";
    const ovclash_suite_string_t store = { path, sizeof(path) - 1 };
    uint32_t count = 0u;
    int status = 1;
    if (ovclash_suite_data_create(&data).status == OVCLASH_SUITE_STATUS_SUCCESS &&
        ovclash_suite_data_open(data, store).status == OVCLASH_SUITE_STATUS_SUCCESS &&
        ovclash_suite_data_get_query_count(data, &count).status == OVCLASH_SUITE_STATUS_SUCCESS &&
        ovclash_suite_data_commit(data).status == OVCLASH_SUITE_STATUS_SUCCESS)
    {
        printf("%u queries\n", count);
        status = 0;
    }
    ovclash_suite_data_destroy(data); /* accepts NULL */
    return status;
}

ovclash_suite_data_get_file_path() and ovclash_suite_data_get_file_size() report the store’s path and size. ovclash_suite_data_get_last_error() returns the handle’s last failure text.

Handle and cursor lifetime:

  • Python read methods materialize their results and release their native cursors before returning.

  • A live fetch operation blocks writes, commit and store lifecycle changes (open, save, save-as, migrate, close and destroy) until it is destroyed. An async fetch also blocks reads from other threads.

  • A live overlap or frame cursor blocks lifecycle changes, even when it is exhausted.

  • In Python, exhaust or close the fetch generator and any fetch_iter_saved_frames() iterator before you close or reopen the store.

Suite fetch and cursor lifetime has the full table.

Deferred creation and unnamed stores#

  • Creating a missing store waits for the first write by default. Opening a missing path creates no file or folder; the first write creates it. Change this with ovclash_suite_data_set_deferred_file_creation_until_first_write_op() or the ClashData.deferred_file_creation_until_first_write_op property.

  • open("") on a built-in serializer opens an unnamed store: a private temporary database for SQLite, a private temporary folder for a directory store. Its path is empty, and ovclash_suite_data_get_file_size() fails for it. It supports reads, writes and fetch-and-save.

  • Closing or destroying an unnamed store deletes its records. To keep them, call save_as(path) before closing. The named copy becomes the current store.

  • ClashData.open("") does nothing. Open the unnamed store through the serializer, then pass that serializer to ClashData(serializer).

Each store has its own path rules: see SQLite store path and Directory store path.

Use the class constants instead of literal extensions:

  • ClashDataSerializerSqlite.SERIALIZED_FILE_EXT is .ovclashdb.

  • ClashData.CLASH_DATA_LAYER_FILE_EXT is .clashDetection.

  • ClashDataSerializerDirectory.SERIALIZED_FILE_EXT is empty.

CRUD#

CRUD stands for create, read, update and delete, the record operations of the data API. Every C insert, update and remove function has two forms: a plain one and a _with_commit one.

  • The plain form is not “no commit”: it calls the _with_commit form with commit = 1.

  • To batch a run’s writes into one transaction, pass commit = 0 to the _with_commit form and call ovclash_suite_data_commit() once at the end.

  • The bulk ovclash_suite_data_replace_frames_by_overlap_with_commit() has only the _with_commit form.

  • In Python, the commit keyword argument makes the same choice and defaults to True.

  • Pending writes are committed by commit(), save(), save_as(), close(), destroy() or a later write with commit=True.

Note

A write that fails after its storage write began rolls back the handle’s whole pending transaction, on both built-in stores. Every earlier write made with commit = 0 is discarded, including writes that returned success. Committed data is kept. Such failures include:

  • constraint, SQLite and filesystem errors, and a failed commit;

  • a NaN REAL value on a SQLite store;

  • a non-finite frame matrix;

  • a record string containing NUL on a directory store.

Argument, open-state, fetch-reservation and not-found failures are reported before the write begins and leave pending writes untouched. Validate inputs before a batch, or commit before a write that may fail.

Return values with the built-in serializers:

  • Python inserts return the stored identifier. insert_clash_frame_info_from_clash_info() instead returns the number of frames it wrote.

  • Update methods and single-record remove methods return 1, or 0 when the identifier is not stored.

  • remove_all_overlaps_by_query_id() and remove_clash_frame_info_by_clash_info_id() return the number of records removed.

  • find_query() and the find_point_cloud_settings*() methods return None when no record matches. A C find function then fails with an empty last-error text, which separates absence from an error.

In C, fill a record view from the object model table and call the insert and update functions:

  • The insert and update functions copy input strings and buffers.

  • Views returned by a read are borrowed. A getter that is not a cursor reuses a per-kind scratch record on the data handle. Copy its view before the next read of the same kind, any write, close or destroy.

  • A cursor view belongs to its cursor.

The bounded C loop, as a function for a C source file of your program. Call it after a completed run of runtime, with data open and query_id stored in it:

#include <ovclash_suite/ovclash_suite.h>

/* Saves the completed run as the clashes of the stored query query_id. Pass the query's own
 * SETTING_TOLERANCE, SETTING_DEPTH_EPSILON and SETTING_DUP_MESHES values. Returns 0 on success. */
static int fetch_and_save(ovclash_suite_runtime_t* runtime,
                          ovclash_suite_data_t* data,
                          int64_t query_id,
                          double tolerance,
                          double depth_epsilon,
                          uint32_t include_duplicates)
{
    ovclash_suite_fetch_and_save_t* fetch = NULL;
    uint32_t complete = 0u;
    ovclash_suite_result_t r = ovclash_suite_runtime_fetch_and_save_begin(
        runtime, data, NULL, query_id, tolerance, depth_epsilon, include_duplicates,
        1u /* resolve_stale */, &fetch);
    while (r.status == OVCLASH_SUITE_STATUS_SUCCESS && !complete)
    {
        double progress = 0.0;
        r = ovclash_suite_runtime_fetch_and_save_next(fetch, &progress, &complete);
    }
    ovclash_suite_runtime_fetch_and_save_destroy(fetch); /* accepts NULL; consumes it, even on error */
    return r.status == OVCLASH_SUITE_STATUS_SUCCESS ? 0 : 1;
}

Step 4 of Suite Workflows runs this loop in a complete program. The SDK archive’s samples/clash_suite_api/ClashSuiteApi.cpp runs it with progress reporting, and also runs the background ovclash_suite_runtime_fetch_and_save_async() variant.

Rules for the fetch operation:

  • Pass the values the query stores: SETTING_TOLERANCE as tolerance, SETTING_DEPTH_EPSILON as depth_epsilon and SETTING_DUP_MESHES as include_duplicates. The Python wrapper does the same, with 0.0, -1.0 and false for a missing setting. include_duplicates does not follow the runtime’s current only_find_duplicates setting.

  • Each step bounds its work, not its time. Each ovclash_suite_runtime_fetch_and_save_next() call handles at most 1,024 frame reports and 1,024 overlaps, and stops once about 8 MiB of report payload is acquired; one indivisible report can exceed that. Reconciling absent clashes scans at most 1,024 stored identifiers per call, so it can take several calls. begin enumerates every stored identifier of the query and is not bounded. The call that reports completion has committed.

  • Threading follows the runtime’s settings. Fetch preparation uses single_threaded, new_task_manager and nb_tasks, which may differ from the ones detection used. Set them before begin and keep them until destroy. Frame preparation for a directory store, or for a custom store with a prepare_frame callback, can use worker threads. SQLite frame encoding and every storage write stay on the driving thread: the calling thread for the bounded C calls and the Python generator, the background worker for the asynchronous calls. Python progress, modification and timing callbacks stay on the iterating thread.

  • Destroy the operation before you close its runtime or data handle. A live operation leases both; Suite fetch and cursor lifetime lists what it blocks.

ovclash_suite_runtime_save_overlap_to_data() persists one runtime overlap and its frames in one call. It keeps the review fields of a stored clash with the same query_id and overlap_id. A record the engine cannot report is dropped instead of failing the call; compare out_frame_count with nb_records from ovclash_suite_get_overlap_data() to detect the loss.

Fetch-and-save failures and transaction boundaries#

Fetch-and-save is not all-or-nothing for every failure. The rules in this section hold for every fetch call of Saving detection results, on both built-in stores and custom stores, and in serial and parallel modes. The storage transaction belongs to the data handle, so a rollback or the final commit also affects unrelated writes pending on that handle.

Outcome

Transaction behavior

Successful completion

Reconciles absent clashes and commits before it reports completion, even for an empty result. The commit publishes every pending write on the handle. Intermediate batches do not commit.

A storage callback, a transaction, a frame release or a saved-data read fails after initialization

Requests rollback of the whole pending transaction, including earlier batches of the same fetch and other uncommitted writes on the same destination.

Extraction, frame preparation (including a failed prepare_frame), scheduling or other native processing fails

Restores the incomplete streamed clash record, if any, and keeps earlier completed pending writes. If that restore fails, it requests a full rollback.

Initialization fails

Leaves writes that were pending before begin alone.

Cancellation is observed before the commit

Stops further reconciliation and the commit. Completed writes and absent-state updates already applied stay pending, unless restoring the incomplete clash record fails and forces a full rollback.

The operation is destroyed before completion

Restores the incomplete clash record, falls back to a full rollback if that fails, and never commits. Completed writes stay pending.

A clash record is streamed when fetch-and-save writes it before all the reports of its overlap are captured, as for a long dynamic clash.

  • Committed data is always kept.

  • A failed operation cannot resume. Destroy it and start a new one. Destruction consumes the operation even when its cleanup reports an error. In Python, close an abandoned generator before closing the store.

  • Closing or destroying a built-in data handle attempts to commit. Error cleanup can therefore save partial results. If that commit fails, the handle requests a rollback and stays available for inspection or retry, so the pending writes may be gone.

  • Callbacks after the final commit cannot undo it. In Python, the last modification notification, the final progress_callback call and timing_callback run after the final commit. An exception they raise leaves the results committed.

  • A record without an available report is skipped. The engine can report OVCLASH_SUITE_STATUS_UNAVAILABLE for a record while the overlap’s data stays readable. The fetch then drops that frame, prints a persisted X of Y records notice to stderr, and continues. The stored num_records then counts only the persisted frames. Compare it with nb_records from ovclash_suite_get_overlap_data() when the loss matters. An overlap whose records all fail fails the fetch.

The public data API has no rollback function, and destruction is not one. To publish results only after complete success, fetch into a separate staging store and publish it once completion is confirmed.

The approval comparison#

An APPROVED clash keeps its approval only when the new run detects exactly what the store holds:

  • Identity. The query and the clash hash, the hash of the ordered pair of prim paths, establish result identity. A matching clash hash alone does not preserve an approval.

  • Compared contents. Type, tolerance, depth epsilon, object paths and mesh checksums, the aggregate results, and every frame’s times, matrices, metrics and geometry, in persisted order.

  • Ignored. Record identifiers, review fields, timestamps and user penetration-depth annotations.

  • Precision. Values compare at the precision of the Suite C ABI: binary64 for scalars, times and matrices, and binary32 for outlines and point sizes. The comparison uses no epsilon. Signed zeros are equal, a NaN never counts as unchanged, and subnormals stay distinct from zero, whatever the caller’s floating-point controls.

The comparison needs a reader for the stored results:

  • Built-in stores and Python custom stores supply it automatically. A Python custom store serves the saved frames through fetch_iter_saved_frames(); see Custom stores.

  • A custom C or C++ store passes an ovclash_suite_fetch_saved_data_reader_t to ovclash_suite_runtime_fetch_and_save_begin_with_reader() or ovclash_suite_runtime_fetch_and_save_async_with_reader(). Pass a null reader with a built-in destination.

  • With state updates on and no reader, a re-detected APPROVED clash becomes ACTIVE, because unchanged contents cannot be proven.

Custom stores#

A custom store keeps records in storage that you implement, and receives fetch-and-save results under the same transaction contract as the built-in stores. The built-in lifetime guards protect only the built-in stores: a custom store keeps its destination stable for the whole fetch and enforces its own lifetime and connection rules.

In Python, derive from AbstractClashDataSerializer, implement its record methods, and pass an instance to ClashData(serializer) or directly to the fetch call.

  • Override fetch_transaction(operation). Without that override, fetching raises NotImplementedError before any work starts, because rollback cannot be emulated through the record methods.

  • The other fetch_* hooks have defaults built on the record methods: fetch_visit_existing(), fetch_find_overlap(), fetch_write_overlap(), fetch_clear_frames(), fetch_append_frame(), fetch_mark_absent() and fetch_iter_saved_frames(). The defaults need record methods that raise on persistence errors. Override a hook when its default is slow for your store. Override fetch_visit_existing() when the store allows several records with the same clash hash.

  • Identifiers that the hooks return fit a signed 64-bit integer and are never -1, which ClashInfo reserves for an unsaved record.

  • For long APPROVED histories, override fetch_iter_saved_frames(identifier, first_frame_offset=0) with a forward cursor. The cursor yields owned frames in persisted order and has a close() method. The fetch may close it and reopen it at a nonzero offset around writes. The default issues one ranged read per frame.

  • Threads. The hooks run on the calling thread, or on the background worker of an asynchronous fetch. Progress, modification and timing notifications stay on the iterating thread.

The docstrings of AbstractClashDataSerializer and its fetch_* hooks give the full contract.

In C or C++, fill an ovclash_suite_fetch_serializer_t callback table, the serializer interface of a custom store, and pass it to the fetch call with a NULL data handle; exactly one of the two is non-null. Each callback acknowledges success by writing exactly 1 to its out_success argument, and no exception may cross the C ABI.

Schema compatibility#

Each store records the version of its format, and open refuses a store newer than the build:

  • A SQLite store records a schema version per table. An older file with a registered migration path must be migrated before it opens. An older file without one, and a file newer than the build, never open, and no migration recovers them. See Schema versions and forward compatibility.

  • A directory store records one format version in manifest.json, and has no migration path. See Manifest and internal files.

Failures that do not raise#

A native failure normally becomes a Python exception that carries the native error text. The data and serializer classes keep the legacy return contract in these places:

  • ClashData without an open store, or without a serializer, returns False, 0, None, {} or [] from its record methods, save() and save_as(), according to the result type, and logs nothing. Its close() and commit() then do nothing. A destroyed built-in serializer returns the same values from its record methods and does nothing on close() and commit(). Its open(), save() and save_as() raise.

  • SQLite open() leaves an incompatible database closed without raising. It logs the reason as a warning through the ovclash_suite logger, as ovclash_suite: store left closed after open(<path>): <reason>, where <path> is the path you passed and <reason> is SQLite database tables are incompatible; migration to the latest version is possible or SQLite database tables are incompatible and cannot be migrated to the latest version. Inspect is_open(), data_structures_compatible and data_structures_migration_to_latest_version_possible.

  • migrate_data_structures_to_latest_version() returns False instead of raising, and logs the reason as a warning: ovclash_suite: migrate_data_structures_to_latest_version(<path>) failed: <reason>, where <reason> is the native error text.

  • ClashQuery.load_settings_from_str() returns False for empty or invalid JSON, and logs nothing.

For the SQLite open and the migration, last_error() returns the reason the call recorded. Without it, a store left closed looks exactly like an empty one.

Everything else raises: other open failures, directory format errors included, and native close, commit and destroy failures. fetch_all_queries() and fetch_all_point_cloud_settings() raise RuntimeError instead of returning a partial dictionary.
