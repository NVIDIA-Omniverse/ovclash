System Requirements and Compatibility#

This page lists what ovclash, the clash detection library for USD scenes, needs on the machine that runs it, and how a release stays compatible with other releases, with stored clash data and with Kit code. It ships as docs/consumer/compatibility.md in the SDK archive.

  • No package exists for any other operating system or CPU.

  • Each package carries the launchers of its own platform only: .bat launchers on Windows and .sh launchers on Linux.

  • The py3-none tag means that the wheel holds no compiled Python extension. The Python packages load the native library through ctypes, so the wheel is not tied to one Python version.

Linux glibc baseline#

The Linux binaries require at most the GLIBC_2.35 and GLIBCXX_3.4.30 symbol versions, and the build checks every Linux binary against that baseline. A system with glibc 2.35 or newer and the libstdc++ of GCC 12 or newer meets it, for example Ubuntu 22.04 or later.

  • pip installs the wheel only where the glibc version meets the manylinux_2_35 tag. pip does not check libstdc++.

  • The SDK archive has no tag. ldd --version prints the glibc version of a machine.

  • On an older system, the dynamic loader refuses the library with a message that names the missing GLIBC_ or GLIBCXX_ version.

Windows Visual C++ runtime#

ovclash does not bundle the MSVC runtime (MSVCP140.dll, VCRUNTIME140.dll and VCRUNTIME140_1.dll), although its Windows binaries import it. Install the Microsoft Visual C++ Redistributable (x64) on every machine that runs ovclash. Without it the native library does not load, and import ovclash raises an OSError that names the runtime libraries the machine cannot load; see Troubleshooting.

Python versions#

The wheel declares Requires-Python: >=3.10. The SDK archive carries the same Python packages under python/, with the same requirement. find_package(ovclash) also runs a Python 3.10 or newer interpreter at configure time, to check that interpreter’s installed ovstage.

The optional extras pin these version ranges:

The core API needs no extra. Optional extras says what each one is for.

The ovstage runtime#

ovclash reads USD through ovstage. Each ovclash release pins exactly one ovstage version, and neither package bundles it. ovstage supplies the USD runtime, so ovclash needs no usd-core of its own. The pinned version is published on public PyPI.

  • Wheel. The wheel’s metadata declares ovstage==<pin>, and pip installs that version with ovclash. At import the wheel checks only that a complete ovstage runtime is installed, not its version, so it relies on pip to keep the pin. Do not upgrade, downgrade or uninstall ovstage on its own, and do not install ovclash with --no-deps.

  • SDK archive. requirements.txt holds exactly ovstage==<pin>, where <pin> is the pinned ovstage version. Install it into every interpreter that builds or runs your code. From the extracted SDK archive root:

    python -m pip install -r requirements.txt

    find_package(ovclash) and the SDK archive’s Python packages accept only the pinned version. Another version, or none, is an error that names the interpreter and the install command. OVCLASH_OVSTAGE_PACKAGE_DIR selects another installation of the same version. The sample launchers prepare the pin themselves; see How the launchers select a runtime. Installing the ovstage runtime covers the CMake side.

The pinned ovstage runtime carries a namespaced OpenUSD, so the Python packages publish its plugin registry only through OV_PXR_PLUGINPATH_2511, not through PXR_PLUGINPATH_NAME. USD coexistence covers a process that also loads another OpenUSD.

System SQLite#

SQLite stores, and legacy .clashDetection containers, use the operating system’s SQLite library. ovclash neither links nor bundles SQLite. It loads the library at run time, once per process:

  • On Windows, it loads only winsqlite3.dll from the System32 directory.

  • On Linux, it loads libsqlite3.so.0, else libsqlite3.so. Install the distribution’s SQLite library package where neither exists, for example libsqlite3-0 on Debian and Ubuntu.

The JSON directory store and the canonical API do not use SQLite. System SQLite library gives the error messages.

Maturity and versioning#

ovclash is pre-1.0 software. The wheel’s metadata classifies it as Development Status :: 3 - Alpha.

  • One MAJOR.MINOR.PATCH version covers the native library, both C ABIs and the Python packages.

  • A wheel version can carry a local version label after a +, as PEP 440, the Python standard for version numbers, allows. When you compare versions yourself, compare value.split("+", 1)[0].

  • Before 1.0, a minor or patch release can carry a breaking change, and the changelog calls out each one. A release lists them under a Changed — breaking heading, or among the entries under Changed.

The changelog also states the deprecation policy for entry points that shipped in a release:

  • An entry point that is going away is deprecated in a 0.x.N release. It keeps working, and its declaration carries a message that names its replacement and the release that removes it.

  • It is removed no earlier than 0.(x+1).0, one minor release later.

  • The replacement is added beside it, with a _v2 (or higher) suffix, instead of a changed signature.

  • A release that deprecates or removes an entry point lists each one in a Deprecated section of the changelog.

No entry point is deprecated at present, and neither API layer is.

These checks run without your help:

  • Importing either Python package compares the native library’s major.minor.patch with the package version, and raises RuntimeError on a mismatch. A partial upgrade therefore fails at import; see Troubleshooting.

  • The SDK archive’s find_package(ovclash) and Python packages check the installed ovstage against the pin; see Troubleshooting.

C and C++ code checks itself. The headers describe the version you compiled against, and the loaded library can be another one. Compare ovclash_get_version() with the <ovclash/version.h> constants at startup. Before 1.0 a patch release can break the ABI, so compare all three numbers. Checking the loaded library shows the check.

The SDK archive’s CMake package accepts any newer version: find_package(ovclash 0.2) also finds a 0.3 release. Add EXACT to require one version.

Stored data#

Store formats carry their own version numbers, which are not ovclash release numbers. Compatibility is forward-only: a release opens stores in its own format, and migrates an older SQLite store when a migration path to the current schema exists. No release opens a store in a newer format, and nothing converts a store back.

Store

Compatibility

SQLite .ovclashdb

Each table records its schema version. Releases with the same table versions read and write the same files. A store with older tables opens only after a migration, which works in place and exists only for the versions that page lists. A store with newer tables is refused. See Schema versions and forward compatibility.

JSON directory store

manifest.json records the format version. Version 1 is the only format, and a store with an unsupported version does not open. See directory_serializer.md.

Legacy .clashDetection container

ovclash writes container format version 1 and rejects a newer version. The SQLite payload follows the SQLite rules, and migration works on a temporary copy, never on the container. See legacy_container.md.

Because migration is in place and an older release refuses a migrated store, copy a store before you migrate it if an older release must still read it.

Kit compatibility#

ovclash runs outside Kit and needs no Kit SDK or runtime. It uses no Kit services, such as the timeline, the current USD context (the Kit object that holds the application’s open stage) or the product UI. Three parts keep Kit-era code and data working:

  • omni.physxclashdetectioncore exposes the Suite API under the module names of the Kit extension, for code that you port from Kit. A few names are missing, and a few behaviors differ; see Kit Compatibility and its behavioral differences.

  • The Suite API reads and writes Kit-era .clashDetection containers; see Legacy Containers.

  • The canonical C ABI keeps some entry points only for compatibility with Kit’s clash interface. Limitations lists them and what they do here.

The engine’s default settings mirror the Kit extension’s defaults. use_usdrt is stored and read back, but it has no effect; see Settings without effect.

Upgrading#

Before you begin, know which package you installed, the wheel or the SDK archive, and where. python -m ovclash --version prints the version of the loaded native library as ovclash <version>. Upgrade the whole package, never a part of it.

  1. Read the changelog entries of every release between yours and the new one, for breaking changes under Changed — breaking and Changed, and for Deprecated sections.

  2. Wheel: upgrade it as Upgrading the wheel describes.

  3. SDK archive: upgrade it as Upgrading the SDK archive describes.

  4. Open each of your stores with the new release.

  5. Copy each SQLite store that reports incompatible tables and that an older release must still read.

  6. Migrate each SQLite store that reports incompatible tables that can be migrated, as Schema versions and forward compatibility describes.

  7. Refresh the sample environments as Refreshing the sample environments describes.

Do only the one of steps 2 and 3 that matches your package. A store that has no migration path to the new schema does not open in the new release; keep reading it with the release that wrote it.

The upgrade is complete when the new release reports its version: python -m ovclash --version prints ovclash <version> with the new version, and a C or C++ program’s ovclash_get_version_string() returns it.

Upgrading the wheel#

  1. Run python -m pip install --upgrade ovclash. pip also installs the new release’s ovstage pin.

When pip finds no wheel for your platform or Python, check Platforms and package names and Python versions. An import that raises RuntimeError after the upgrade means that the native library and the Python package differ in version; see Troubleshooting.

Upgrading the SDK archive#

  1. Extract the new archive.

  2. Install its requirements.txt into every interpreter that you build or run with.

  3. Point OVCLASH_LIB or OVCLASH_SUITE_LIB at the library of the new SDK archive.

  4. Windows only: replace the old SDK archive’s bin\ on your PATH with the new one’s.

  5. Configure your CMake build again with the new ovclash_DIR. When find_package(ovclash) fails, its message names the cause; Configuring with CMake lists the messages and their fixes.

  6. Rebuild every native consumer against the new headers: a pre-1.0 release can change a signature or a struct layout. When the compile fails on a changed declaration, the Changed — breaking and Changed entries of the changelog describe the change.

Linux programs need no PATH change: they find the library through the run paths that the rebuild of step 6 records.

A pip install --target <dir> --upgrade across a pin change can leave a stale ovstage-*.dist-info beside the new one. The SDK archive’s ovstage check then reports two versions; Troubleshooting gives the fix.

Refreshing the sample environments#

  • Outside an SDK archive, or with --wheel, the run_custom_clash launchers reuse the virtual environment that their first run created, .venv-ovclash beside the script. OVCLASH_VERSION does not repin it, so delete it to pick up the new release; see The Clash Processor. Inside an SDK archive without --wheel, they run against that SDK archive and create no .venv-ovclash.

  • The other sample launchers cache one environment per package location, ovstage pin and interpreter. A release extracted to a new location, or one with a new ovstage pin, gets a new environment; one that reuses both reuses the environment. Delete the ones that you no longer need from the cache directory that How the launchers select a runtime names.
