Troubleshooting#

This page lists the failures you are likely to hit first. Each entry has three parts:

  • Symptom: the literal text that ovclash, the OS or CMake prints, or what you observe when nothing is printed. Search this page for the first words of your message.

  • Cause: why it happens.

  • Fix: what to change.

Environment variables describes the runtime variables that this page names. Limitations lists behavior that is limited by design rather than broken. When nothing here matches, collect the facts in Collecting diagnostics for a bug report.

First checks#

Run these before you look further. They show which library Python loaded and what the last native call reported.

Before you begin: run the Python command with the interpreter that runs your ovclash code. Add the C helper to a C source file of a program that builds against the SDK archive, as Linking shows.

Python: print the loaded version and backend.

python -c "import ovclash; print(ovclash.version_string()); print(ovclash.backend_info())"

A working installation prints two lines and exits with status 0. X.Y.Z is the installed version. Identifying the loaded library gives the type and released value of each BackendInfo field.

X.Y.Z
BackendInfo(backend_name='ovstage', native_openusd_linked=False, ovpopulation_runtime_loaded=True, ovstage_cuda_enabled=False, native_library_path='<path of the loaded library>')

If the import fails, find the message under Loading the Python packages. native_library_path shows which library file was loaded.

C: test every result by its status, and print the context’s last error on failure.

#include <stdio.h>

#include <ovclash/ovclash.h>

/* Returns 1 on success. On failure prints what failed and the context's last error. */
int check(ovclash_context_t* ctx, ovclash_result_t result, const char* what)
{
    if (result.status == OVCLASH_STATUS_SUCCESS)
        return 1;
    ovclash_string_t error = ovclash_get_last_error(ctx);
    fprintf(stderr, "%s failed: %.*s\n", what, (int)error.length, error.ptr ? error.ptr : "");
    return 0;
}

Call it right after each call, for example check(ctx, ovclash_open_stage(ctx, path), "ovclash_open_stage"). The last error is sticky, so read it only after a call failed.

Collecting diagnostics for a bug report#

When a failure is not listed on this page, or a result looks wrong, collect these facts. They identify the exact build and show what the run did and where it spent its time.

Fact

How to get it

ovclash version

python -m ovclash --version prints ovclash <version>. In Python, ovclash.version_string() is the version of the loaded native library and ovclash.__version__ that of the Python package. In C, ovclash_get_version_string(), or ovclash_get_version() and ovclash_suite_get_version() for the numbers.

ovstage version

python -m pip show ovstage in the environment that runs ovclash. An SDK archive’s requirements.txt names the version it pins.

Backend

ovclash.backend_info() or ovclash_suite.backend_info(); in C, ovclash_get_backend_info() or ovclash_suite_get_backend_info(). Report backend_name, ovstage_cuda_enabled and, from Python, native_library_path.

Platform

The operating system and its version, the CPU architecture and python --version.

Error text

The full Python exception. In C, ovclash_get_last_error() right after the failing call; on the Suite API, ovclash_suite_get_last_error(), ovclash_suite_data_get_last_error() or ovclash_suite_get_thread_last_error().

Query

The stage, or the smallest stage that reproduces the problem, the scope and the settings: ClashRuntime.get_run_settings(), ovclash_get_settings() or ovclash_suite_get_run_settings(). The clash_suite_api processor prints its Clash Processor Arguments: and Clash Engine Settings: at the start of every run.

Problem size

get_query_stats() in Python, ovclash_get_query_stats() or ovclash_suite_get_query_stats() in C, read after the run.

Engine log

See The engine log.

Stage-read and fetch timing

See Source and fetch timing.

The engine log#

The engine log prints per-phase progress and timing lines to stdout. Turn it on with any of these:

  • C: ovclash_set_log(context, true); Suite C: the enable_log field of ovclash_suite_run_settings_t.

  • Python: RunSettings(enable_log=True); Suite Python: SettingId.SETTING_LOGGING.

  • Command line: python -m ovclash --log, which moves the lines to stderr and keeps the JSON summary on stdout, or --logging for the clash_suite_api processor.

There is no log callback, so capture the process’s output. The text is diagnostic output, not a stable format.

Source and fetch timing#

OVCLASH_SOURCE_PERF=1 turns on timing lines for the stage reads and for every Suite fetch-and-save operation. Only the exact value 1 turns them on. The library reads the variable once per process, so set it before the process starts.

  • [source-perf] lines go to stdout. Each phase of reading the stage prints one line when it begins and one when it ends:

    [source-perf] begin phase="<name>" input=<count>
[source-perf] end phase="<name>" elapsed_s=<seconds> input=<count> output=<count>

    [source-perf] field

    Type

    Lines

    Meaning

    phase

    Quoted string

    begin, end

    The name of the stage-reading phase

    input

    Integer

    begin, end

    The input count of the phase

    elapsed_s

    Seconds, six decimals

    end

    The duration of the phase

    output

    Integer

    end

    The output count of the phase

    The phase pipeline.finding_meshes prints only its end line; its elapsed_s covers all of step 1, Finding meshes....

  • One [fetch-perf] line goes to stderr for each fetch-and-save operation, when it is destroyed:

    [fetch-perf] query_id=<id> complete=<0|1> wall_s=<s> capture_s=<s> lookup_s=<s> prepare_s=<s> apply_s=<s> release_s=<s> commit_s=<s> capture_calls=<n> acquired_reports=<n> appended_frames=<n> batches=<n> commit_calls=<n>

python -m ovclash sends everything except its JSON summary to stderr, so one command collects the summary and every diagnostic line. Run it from the directory that holds your stage, here scene.usda. On Linux:

OVCLASH_SOURCE_PERF=1 python -m ovclash scene.usda --log > summary.json 2> diagnostics.txt

On Windows, in cmd:

set OVCLASH_SOURCE_PERF=1
python -m ovclash scene.usda --log > summary.json 2> diagnostics.txt

summary.json and diagnostics.txt then hold the summary and the diagnostic lines.

Loading the Python packages#

Visual C++ runtime missing (Windows)#

Symptom: import ovclash raises:

Could not load the ovclash native library at <path>. The file is present, so what is missing is a dependency: this machine cannot load VCRUNTIME140.dll, MSVCP140.dll. Install the Microsoft Visual C++ Redistributable (x64) from https://aka.ms/vs/17/release/vc_redist.x64.exe ...

Cause: ovclash does not bundle the MSVC runtime; see Runtime and platform requirements. The loader probes VCRUNTIME140.dll, VCRUNTIME140_1.dll and MSVCP140.dll, and names only the ones this machine cannot load.

Fix: Install the Microsoft Visual C++ Redistributable (x64), then import again.

A variant of the message says “the Microsoft Visual C++ runtime loads, so some other dependency is missing”. Then the redistributable is not the cause. Inspect the named library with dumpbin /dependents or the open-source Dependencies tool (Dependencies.exe). On Linux, the loader’s own error names the missing library.

Library override is not an absolute path#

Symptom:

OVCLASH_SUITE_LIB/OVCLASH_LIB must be an absolute trusted native library path

Cause: OVCLASH_SUITE_LIB or OVCLASH_LIB holds a relative path. The loader reads OVCLASH_SUITE_LIB first.

Fix: Set the variable to the absolute path of the library file, not of its directory:

  • Windows: <sdk>/bin/ovclash.dll

  • Linux: <sdk>/lib/libovclash.so

The loader treats the parent of that bin/ or lib/ directory as the runtime root. From that root it adds the Windows DLL search directories. For an SDK archive that pins ovstage, it then makes the pinned ovstage installation loadable: it registers that package’s DLL directories on Windows or preloads its libraries on Linux, adds its OpenUSD plugin registry to OV_PXR_PLUGINPATH_2511, and sets OVSTAGE_LIBRARY_PATH_HINT.

No native library found#

Symptom:

Could not find the ovclash suite shared library: neither OVCLASH_LIB nor OVCLASH_SUITE_LIB is set, and the ovclash package bundles no bin/ovclash.dll (only the wheel does).

On Linux the message names lib/libovclash.so.

Cause: No override is set, and the imported ovclash package holds no native library. Only the wheel bundles one inside the package. The usual setup that causes this: the SDK archive’s python/ directory is on PYTHONPATH, but OVCLASH_LIB is not set.

Fix: Set OVCLASH_LIB to the library of the SDK archive, or install the wheel. For the SDK archive, where <sdk> is the absolute path of the extracted SDK archive, on Linux:

python -m pip install -r <sdk>/requirements.txt
export PYTHONPATH=<sdk>/python
export OVCLASH_LIB=<sdk>/lib/libovclash.so

On Windows, in PowerShell:

python -m pip install -r <sdk>\requirements.txt
$env:PYTHONPATH = "<sdk>\python"
$env:OVCLASH_LIB = "<sdk>\bin\ovclash.dll"

When pip cannot reach its package index, install the pin from a local wheel file as Sample Python setup failed describes, and set OVCLASH_OVSTAGE_PACKAGE_DIR to it. Then import ovclash succeeds.

OVCLASH_ALLOW_BARE_LIBRARY_LOAD is a developer-only fallback, not a deployment option:

  • It loads the library by its bare name, so the platform’s default search picks the copy (on Linux, LD_LIBRARY_PATH), not a pinned path.

  • It skips the runtime environment setup: no plugin directories or DLL search paths are registered.

  • The version check still runs.

  • Any value other than empty, 0, false, off or no (case-insensitive) enables it.

  • When the bare-name load fails as well, the error starts with Could not load ovclash suite shared library.

Library and package versions differ#

Symptom:

Loaded ovclash suite library version X.Y.Z does not match Python package version A.B.C

Cause: The Python packages and the native library are version-locked. The import checks them before any API is usable. Only major.minor.patch is compared; a local version label (+<label>) is ignored. Usually an OVCLASH_SUITE_LIB or OVCLASH_LIB override still points at the library of another SDK archive, or a bare-name load found a stale library.

Fix: Point the override at the library of the same SDK archive as the Python packages, or unset it and use the wheel’s own library.

An older or unrelated library can also fail before the version check, with the same cause and fix:

  • ctypes raises AttributeError for a function that the library does not export.

  • The import raises Loaded ovclash suite library does not expose constant <NAME>.

ovstage dependency missing from the environment#

Symptom:

The ovstage-backed ovclash package requires its exact ovstage dependency, but a complete ovstage runtime could not be found. Reinstall ovclash with dependencies enabled.

Cause: The wheel does not carry the ovstage runtime. It depends on the separate ovstage distribution. pip install --no-deps, or a partly uninstalled environment, leaves that distribution missing.

Fix: Reinstall ovclash with its dependencies, from the package index you installed it from, and without --no-deps:

python -m pip install --force-reinstall ovclash

Installation describes the install. On Linux, Failed to preload ovstage wheel dependency '<path>': <error> means that the ovstage package is present but one of its libraries does not load. <error> gives the loader’s reason.

Incompatible ovstage runtime#

Symptom: Opening a stage or running a query fails with:

incompatible ovstage runtime <major>.<minor>.<patch>: API version is not <major>.<minor>. ovclash requires the ovstage v2 population, query/read, and path dictionary APIs.

Other variants name another reason after the version, for example required vtable slots are missing.

Cause: The process loaded ovstage libraries of another version than the one ovclash was built against. ovclash requires the same ovstage API major and minor version, and the ovstage APIs it uses. It checks the runtime once per process.

Fix: Make the process load the pinned ovstage. For the wheel, reinstall it with its dependencies. For the SDK archive, install its requirements.txt into the interpreter in use, and give a C or C++ consumer the run-time directories of that installation; see Exit code 0xc0000135 or 127 before the program starts. Then start a new process, because the result of the check is kept for the process.

Starting a C or C++ program#

Exit code 0xc0000135 or 127 before the program starts#

Symptom: A C or C++ consumer exits with code 0xc0000135 (Windows) or 127 (Linux) before main runs.

Cause: The OS loader could not resolve a shared library in that launch environment. A working Python import does not prove that a plain consumer starts: the Python bindings set up their own loader environment.

Fix: Make the runtime directories visible to the child process:

  • Windows has no run path. Put the SDK archive’s bin directory on PATH, and the bin and bin\plugins directories of the separately installed ovstage package (<site-packages>\ovstage\bin and <site-packages>\ovstage\bin\plugins). Leave that package as pip laid it out: ovstage finds its plugins tree relative to the directory its DLL loads from.

  • Linux: a program built through find_package(ovclash) or pkg-config records the run paths it needs. When it still fails, see Linux SDK archive consumer cannot find the ovstage loader.

After find_package(ovclash), OVCLASH_RUNTIME_DIRS lists every directory the loader needs. The shipped run_*_cpp sample launchers set the same paths. Reproduce with the same executable, working directory and environment.

Linux SDK archive consumer cannot find the ovstage loader#

Symptom: One of these, from a Linux consumer of the SDK archive:

  • At startup: libovstage-dynamic.so: cannot open shared object file

  • When linking through pkg-config: cannot find -l:libovstage-dynamic.so

  • When compiling through pkg-config: #error "ovclash requires ovx/string_types.h or ovx/types.h"

  • Compiler flags that contain /OVCLASH_SET_ovstage_root

Cause: The SDK archive’s libovclash.so needs the ovstage loader from the separately installed ovstage package. Its own run path names only the SDK archive. In a pkg-config build, the flags contain /OVCLASH_SET_ovstage_root when the ovstage_root variable is undefined.

Fix: Define ovstage_root for pkg-config. <sdk> is the absolute path of the extracted SDK archive, and <site-packages> is the Location that python -m pip show ovstage prints for the interpreter with the pinned ovstage. From the directory that holds app.c:

export PKG_CONFIG_PATH=<sdk>/lib/pkgconfig
cc app.c -o app $(pkg-config --define-variable=ovstage_root=<site-packages>/ovstage --cflags --libs ovclash)

  • A program built through find_package(ovclash) records the loader and a build-tree run path to <site-packages>/ovstage/bin itself.

  • An installed copy of that program needs your own INSTALL_RPATH, or CMAKE_INSTALL_RPATH_USE_LINK_PATH=ON.

  • A hand-written link line needs the same loader, run-path and -rpath-link entries as the Libs line of the SDK archive’s ovclash.pc.

Compilation fails on the DLPack header#

Symptom: Compiling a consumer fails because the compiler cannot open ovx/dlpack/dlpack.h, which <ovclash/ovclash.h> includes on the line #include <ovx/dlpack/dlpack.h>. The wording of that error is the compiler’s own.

Cause: The DLPack header ships in the SDK archive’s own include/ tree, beside ovclash/ and ovclash_suite/. Either the SDK archive’s include directory is missing from the compile line, or the header tree was assembled by hand.

Fix: Use the exported CMake config (find_package(ovclash)) or, on Linux, the SDK archive’s ovclash.pc. They emit both include directories, the SDK archive’s and the ovx one, the include directory of the ovstage package’s C headers, and -DOVCLASH_STANDALONE together.

Configuring with CMake#

The installed ovstage does not match the SDK#

Symptom: find_package(ovclash) reports the package as not found with a message about the installed ovstage. Most variants start:

This SDK requires ovstage==<pin>, but ...

Other tools run the same check and print a message of the same form:

  • The SDK archive’s Python bindings, after The ovclash SDK at <sdk> cannot load its ovstage runtime:.

  • The C++ sample launchers, after SDK runtime discovery failed:.

  • The sample launchers and build_samples, after Sample Python setup failed:, when OVCLASH_OVSTAGE_PACKAGE_DIR is set. Without it they prepare the pin themselves; see Sample Python setup failed.

Cause: The SDK archive does not contain ovstage. Its requirements.txt pins the public PyPI wheel, which you install separately. The rest of the message says what was found instead.

Fix: Install the pin into the interpreter in use:

python -m pip install -r <sdk>/requirements.txt

Then make the tools use that interpreter, or name the installed package directly:

  • CMake: -DOVCLASH_PYTHON_EXECUTABLE=<absolute path to python>.

  • Python bindings: run your program with that interpreter.

  • Any of them: set OVCLASH_OVSTAGE_PACKAGE_DIR to an installed <site-packages>/ovstage of the pinned version.

The sample launchers and build_samples need no manual install. They start from the interpreter that PYTHON names, use it when it has the pin, and otherwise prepare a cached environment with it.

The message also tells these cases apart:

  • It names OVCLASH_OVSTAGE_PACKAGE_DIR. That setting is wrong. Correct it, or unset it to use the interpreter’s own ovstage.

  • It lists two or more versions. A stale ovstage-*.dist-info sits beside the current one, for example after pip install --target <dir> --upgrade across a pin change. Remove the stale ovstage-*.dist-info directories, then reinstall with python -m pip install --force-reinstall -r <sdk>/requirements.txt.

  • ... has no usable package directory <dir> (CMake) or ... has no complete native runtime in <dir> (Python bindings and launchers). The pinned version is recorded, but its files are incomplete. Run the same reinstall.

  • OVCLASH_OVSTAGE_PACKAGE_DIR=<value> ... cannot be resolved. The value is not a resolvable path, for example a symbolic link loop. Set the variable to the absolute path of an existing ovstage package directory of the pinned version, or unset it.

No Python interpreter qualifies for the ovstage check#

Symptom: find_package(ovclash) reports the package as not found with a message that starts:

This SDK reads its installed ovstage==<pin> dependency with Python >= 3.10, ...

Cause: The config found no interpreter to read the installed ovstage with. The text after the shared start tells the two cases apart:

  • When the message continues , but OVCLASH_PYTHON_EXECUTABLE=<value> (<source>), the value you set is not the absolute path of a working Python 3.10 or newer.

  • When it continues , and none was found:, the variable is not set. The message then lists what was tried, in this order:

    • a Python3_EXECUTABLE that does not qualify, when one is set

    • the first python3 or python on the search path, or the fact that there is none

Fix: Either way, set OVCLASH_PYTHON_EXECUTABLE to the absolute path of the interpreter that has the SDK archive’s requirements.txt installed. A relative path or a bare name such as python3.12 is refused. From the source directory of your CMake project:

cmake -S . -B build "-Dovclash_DIR=<sdk>/lib/cmake/ovclash" \
    "-DOVCLASH_PYTHON_EXECUTABLE=<absolute path to python>"

The config does not run FindPython3. A Python3_EXECUTABLE that your project selected for itself is therefore passed over when it does not qualify; that is not an error.

ovx header not found#

Symptom: find_package(ovclash CONFIG) reports the package as not found, with this reason:

ovx/string_types.h (or ovx/types.h) was not found, and <ovclash/ovclash.h> includes it.

Cause: ovclash does not ship this ovx header, one of the C headers of the ovstage package (the ovx headers). It is in the include/ directory of the installed ovstage wheel or of the ovstage SDK. The config also searches the include/ directory of the separately installed ovstage package.

Fix: Do one of these, then configure again:

  • Set OVCLASH_OVX_INCLUDE_DIR (a CMake or an environment variable) to that directory.

  • Set the OVCLASH_OVSTAGE_ROOT environment variable to the ovstage root.

  • If the header comes from compiler flags that CMake cannot see, set OVCLASH_ALLOW_MISSING_OVX=ON to accept the package anyway.

Linking describes how the config finds the ovx headers.

OVCLASH_OVX_INCLUDE_DIR names the wrong directory#

Symptom: Configure stops with:

OVCLASH_OVX_INCLUDE_DIR does not contain ovx/string_types.h or ovx/types.h: <dir>

Cause: OVCLASH_OVX_INCLUDE_DIR names a directory without either header.

Fix: Name the directory that contains ovx/: typically <ovstage>/include, not <ovstage>/include/ovx.

Opening stages and running queries#

A failed call looks successful#

Symptom: A call “succeeded” but nothing happened, or a failure went unnoticed.

Cause: ovclash_result_t is a struct, and OVCLASH_STATUS_SUCCESS is 0. A test of the struct or of the status for truthiness reads the opposite of what it means. ovclash_suite_result_t is a distinct type with its own OVCLASH_SUITE_STATUS_* enum.

Fix:

  • In C, test r.status != OVCLASH_STATUS_SUCCESS. Do not mix the canonical and Suite status enums. The check() helper under First checks shows the pattern.

  • In the Python ctypes bindings, an ovclash_suite_result_t is truthy only on success. An ovclash_result_t is truthy for success and error alike, so compare its .status.

  • Read ovclash_get_last_error(ctx) right after a failure. The text is sticky across most calls, so a non-empty string does not prove that the last call failed.

See Error text. Status results describes the result structs.

Zero overlaps, or a scoped run traverses the whole stage#

Symptom: A run reports zero overlaps with a success status: get_overlap_count() returns 0, or python -m ovclash prints "overlap_count": 0. Or a run that should be scoped traverses the whole stage.

Cause and fix: Check these causes in order.

  • Scope and full-scene state. An empty scope selects the whole stage, by full-scene traversal, only while OVCLASH_SETTINGS_FLAG_FULL_SCENE is set. With the flag cleared it selects nothing, and the run still succeeds. A fresh context starts with the flag set. On the canonical API:

    • A non-empty ovclash_set_scope_paths scope (or a ClashRuntime.set_scope scope) clears the flag. The legacy ovclash_set_scope does not.

    • Clearing the scope, opening a stage or attaching an ovstage stage does not set it again.

    • In C, call ovclash_set_full_scene(context, true). That call also clears the scope, so apply settings first and the scope last.

    • With Python ClashRuntime, call both set_scope([], []) and set_run_settings(runtime.get_run_settings(), enable_full_scene=True) before rebuilding the pipeline. Without the base argument, every other RunSettings field returns to its default.

    • After open_stage(), call set_scope() again for a scoped run, or make the same set_run_settings call to traverse the whole new stage.

    The Suite API (ovclash_suite_* and Python ClashDetection) differs. It restores full-scene traversal when the scope becomes empty, or when a stage is opened or attached, as long as its settings in effect enable it. See Setting a scope.

  • Cancellation. A cancelled run can report zero overlaps with a success status. Check the finish status. Read ovclash_async_is_cancelled before ovclash_finish_pipeline clears the flag. See Cancellation.

  • Geometry the run does not select. Point clouds take part only when enabled (ovclash_set_point_clouds, Python RunSettings.enable_point_clouds); they are off by default. Invisible prims are skipped while ovclash_set_ignore_invisible_prims is on, which is the default.

  • Dropped meshes. A mesh that PhysX cannot cook is dropped without failing the run. See Detect dropped meshes.

This Python sequence returns runtime, a ClashRuntime after a scoped run, to full-scene traversal:

runtime.set_scope([], [])
runtime.set_run_settings(runtime.get_run_settings(), enable_full_scene=True)
runtime.run_pipeline()  # rebuilds the pipeline over the whole stage

Invalid prim path in scope#

Symptom: Setting a scope fails with one of:

Invalid prim path in scope: <path>
Scope path entry is empty

Cause: Every scope entry of ovclash_set_scope_paths (Python ClashRuntime.set_scope, Suite ovclash_suite_set_scope and ClashDetection.set_scope_paths) must be an absolute prim path, such as /World/Robot. In Git Bash on Windows, the shell rewrites an argument that starts with / into a Windows path before python -m ovclash sees it, so --scope-a /World/Robot arrives as a file-system path.

Fix: Pass absolute prim paths. In Git Bash, from the directory that holds scene.usda, set MSYS_NO_PATHCONV=1 for the command:

MSYS_NO_PATHCONV=1 python -m ovclash scene.usda --scope-a /World/Robot

Overlap indices change between runs#

Symptom: Two runs over the same stage with the same settings return the same overlaps at different indices.

Cause: The overlap index is an identifier, not a rank, and the order is not part of the contract.

Fix: Match overlaps by name0/name1 or by clashHash from ovclash_get_overlap_data. Sort in your own code when you need a stable order. See Key overlaps by prim pair and Overlap index order is not contractual.

Pipeline creation rejects the sample range#

Symptom: ovclash_create_pipeline (Suite ovclash_suite_create_pipeline, Python create_pipeline()) fails with an error that contains one of:

dynamic sample schedule requires finite times and a non-negative rate
dynamic sample schedule cannot represent inclusive samples plus fixed phases in uint32_t
dynamic sample schedule does not progress at binary64 precision
dynamic sample schedule produced a nonfinite in-range time

Cause: Creating the pipeline builds the sample times. It starts at the start time and adds 1.0/timeCodesPerSecond until the next time exceeds the end time. It rejects:

  • a start or end time or a rate that is not finite, and a negative rate;

  • a range with more samples than the pipeline can hold, together with its 7 fixed steps, in a uint32_t step count;

  • a step so small relative to the times that adding it no longer changes the time at double precision.

A failed create keeps the previous pipeline and step count, and records the error.

Fix: Pass finite times and a non-negative rate. Times are in seconds, and the rate is the query’s samples per second, not the stage’s time-code rate; a range given in time codes can multiply the sample count. Narrow the range or lower the rate. See Dynamic runs.

Out of memory#

Symptom: A call fails with an error that ends in Out of memory (std::bad_alloc), for example Async clash pipeline failed: Out of memory (std::bad_alloc) from ovclash_finish_pipeline. ovclash_is_out_of_memory then reports true for that context.

Cause: An allocation failed during the call or the run. The flag stays set for the context.

Fix: Shrink the problem: scope the query, lower the sample count of a dynamic run, and use any_hit or triangle_limit when you do not need every triangle pair. Call ovclash_release_memory between queries in a long-lived process. See Performance.

Call rejected while an async pipeline is active#

Symptom:

<function> is not allowed while an async pipeline handle is active; finish or cancel the async pipeline first

The Python wrappers raise RuntimeError with a message that ends in finish or cancel the active async pipeline first.

Cause: A handle from ovclash_run_pipeline_async is still live. The context rejects almost every other call until the run is finished.

Fix:

  • Canonical C layer: only ovclash_finish_pipeline lifts the guard; ovclash_cancel_pipeline alone does not. Call ovclash_finish_pipeline exactly once, also after a cancel. The call frees the handle, so set your pointer to NULL.

  • Suite C layer: ovclash_suite_async_finish or ovclash_suite_async_cancel lifts the guard. ovclash_suite_async_destroy then releases the handle.

  • Python: call finish(), or cancel(), which also finishes the run. Or use the AsyncPipeline as a context manager.

Asynchronous Pipelines lists the calls that stay legal during a run.

Call rejected while a Suite fetch or cursor is alive#

Symptom: One of these messages:

<function> is not allowed while a fetch handle is alive; destroy the fetch first
<function> is not allowed while an async fetch handle is alive; destroy the fetch first
<function> is not allowed while a cursor is alive; destroy all cursors first

Cause: A live fetch-and-save operation or data cursor reserves its runtime or store. The reservation rejects lifecycle changes and, for a fetch, most writes.

Fix: Destroy the fetch or cursor handles, then retry. In Python, close the fetch iterator or AsyncFetchAndSave first. See Suite fetch and cursor lifetime.

Result details are stale#

Symptom:

<function>: result details are stale because their mesh selection was replaced; run the pipeline again

Cause: The results were read after their mesh selection went away. ovclash_open_stage replaced the stage, or a failed open dropped it. The mesh-selection step of a new run, or a failed ovclash_get_prim_matrix read, also retires the selection. See Reading a transform.

The counts survive, but the per-pair details do not.

Fix: Run the pipeline again on the current stage, to completion, before you read overlap details. Do not replace the stage between the run and the reads.

Reading a prim transform fails#

Symptom: ovclash_get_prim_matrix (Suite Python ClashDetection.get_prim_matrix) fails with one of:

Failed to query prim transform: <path>
USD time code cannot be represented as finite population seconds

Cause:

  • Failed to query prim transform means that the prim does not exist in the open stage, or that the read yielded no matrix. A missing prim leaves the results intact.

  • The time argument is a USD time code, not seconds. ovclash divides it by the stage’s effective rate: timeCodesPerSecond, else framesPerSecond, else 24. It rejects a time code whose result overflows, and a nonzero time code that becomes zero seconds.

Fix: Pass the absolute path of an existing prim, and a time code in the stage’s own range. The C function of the Suite API is ovclash_suite_get_prim_matrix.

Matrix decomposition failed#

Symptom: A run, or an immediate depth or depenetration query, fails with an error that contains one of:

Matrix decomposition requires 16 doubles
Matrix decomposition requires finite values within float range
Matrix decomposition row magnitude exceeds float range
Matrix decomposition produced an invalid translation
Matrix decomposition produced an invalid scale
Matrix decomposition produced an invalid rotation
Matrix decomposition produced an invalid pose or scale

Cause: ovclash splits each mesh’s world transform into a PhysX pose and a scale, in single precision. A transform with an element that is not finite or exceeds the float range, or whose split yields an invalid translation, rotation or scale, is rejected rather than corrected. The check leaves every valid transform unchanged. Immediate depth and depenetration queries check the matrices you pass before they read the stage, so an invalid caller matrix reports this message even when a path would also fail. In the OVCLASH comparison mode that ovclash_ovstage_set_matrix_decomposition selects, a matrix with collinear rows also fails.

Fix: Find the prim whose world transform is degenerate or out of range, and correct it in the stage, or leave it out of the scope. Pass finite matrices within the float range to the immediate queries.

Unexpected tensor type for a mesh attribute#

Symptom: Finding meshes... (step 1) fails with:

ovstage attribute has unexpected tensor dtype for <attribute> (code=<DLPack type code>, bits=<bits>, lanes=<lanes>)

Cause: ovclash reads mesh data as typed arrays and accepts only these element types. Data of another type is rejected, never reinterpreted.

Attribute

Required type

Mesh points

float32

faceVertexIndices, faceVertexCounts, holeIndices

int32

World and local transform matrices

float64, 16 values per row

omni:resetXformStack

8-bit bool

The common case is a mesh that authors double3[] points, which reports for points (code=2, bits=64, lanes=3).

Fix: Author mesh points as point3f[] and the topology arrays as int[].

Ambiguous prototype association#

Symptom:

Ambiguous prototype association for instance root: <root>

Cause: While it resolves scene-graph instancing, ovclash found an instance root, a prim that USD instancing replaces with a shared prototype subtree, that the runtime associates with two prototypes. It does not guess which one is right, and the run stops.

Fix: No setting bypasses the check. Keep the stage that reproduces it, and collect the facts in Collecting diagnostics for a bug report.

Attached stage geometry is incomplete#

Symptom:

Attached ovstage mesh topology is unavailable at Default; the owner must supply complete geometry

Cause: A run, or an immediate depth or depenetration query, on a stage attached with ovclash_ovstage_attach_stage (Python attach_ovstage()) found a mesh without points at the Default time, the USD time code that holds the values authored without time samples. For a stage it opens from a file, ovclash recovers such a mesh’s points and topology from its earliest authored samples. For a caller-owned attached stage it does not, with or without a composition, the description of the USD sources that the owner composed the Stage from: Default geometry always comes from the owner’s Stage. Engine-evaluated time describes compositions.

Fix: Supply complete Default-time points and topology for every mesh of the attached stage, or open the stage file with ovclash_open_stage instead. See The owner’s duties while attached.

Messages about an attached stage or an owner operation#

Symptom: A message that names an attached ovstage stage, its binding descriptor or an owner operation, for example:

clash runtime reentry from an ovstage owner operation is prohibited

Cause and fix: Messages lists each of these messages with its cause. clash runtime reentry from an ovstage owner operation is prohibited means that a clash call ran inside an owner-operation callback (ovclash_ovstage_run_owner_operation, ovclash_suite_run_ovstage_owner_operation or Python run_ovstage_owner_operation()) or inside an evaluate_time callback. Owner callbacks may nest owner work, but they must not reenter a clash runtime: return from the callback first, then make the clash call.

An attachment with a composition opens nothing when it attaches. A composition that ovstage cannot replay, or units or a time-code rate that differ from the binding, fail its first finite-time read, with a message that starts with ovstage composition or Attached ovstage composition.

Unknown encoded path#

Symptom:

Unknown encoded scope path; encode paths with ovclash_sdf_path_to_int first
Unknown encoded mesh path; encode paths with ovclash_sdf_path_to_int first

Cause: ovclash_set_scope (scope paths) and ovclash_imm_compute_max_local_depth / ovclash_imm_depenetrate_meshes (mesh paths) take encoded uint64 ids. The loaded library keeps its own id registry, so an id from anywhere else is unknown.

Fix: Encode each path with ovclash_sdf_path_to_int from the same loaded library, in the same process. For a scope, use ovclash_set_scope_paths instead: it takes path strings and needs no encoding. See The legacy encoded-id scope.

Debug overlap meshes are not supported#

Symptom:

ovclash_create_overlap_meshes is not supported by the ovstage backend

Cause: Debug overlap-mesh creation is Kit-only. ovclash_create_overlap_meshes always returns OVCLASH_STATUS_ERROR, and ovclash_release_overlap_meshes does nothing. Both remain only for compatibility of the C ABI.

Fix: Use ovclash_create_overlap_report_ex for overlap geometry. It reports colliding faces, outline segments and colliding point indices.

A setting or call succeeds but changes nothing#

Symptom: A setting is accepted, or a call returns success, but results do not change.

Cause: Some inputs exist only for compatibility with the Kit clash interface:

  • The ROI paths, region-of-interest paths (ovclash_suite_query_set_roi_include_path / ovclash_suite_query_set_roi_exclude_path, and the --roi-include / --roi-exclude options of the clash_suite_api samples) are stored and round-tripped. No query reads them.

  • ovclash_delete_duplicate_meshes returns success and deletes nothing.

  • use_usdrt is inert: USDRT, Kit’s runtime scene representation, is not part of ovclash.

Fix: To restrict a run, pass an explicit A/B scope to ovclash_set_scope_paths (or ClashRuntime.set_scope). Limitations lists every such input with its replacement.

Opening a stage stalls on an unreachable omniverse:// host#

Symptom: Opening a stage waits a long time on an unreachable omniverse:// host before its assets fail.

Cause: The runtime’s omni client, the client library through which the ovstage runtime reaches omniverse:// hosts, keeps reconnecting to that host. There are two reasons:

  • OVCLASH_OMNI_CLIENT_RETRY_MAX_MS is set to a positive value. The client then retries for that many milliseconds.

  • ovclash has not found the runtime’s omni client yet. Until it does, it cannot apply the window, not even the default 0, so the runtime’s own reconnect window applies. When the variable is set, stderr then shows this line once per process:

    ovclash: OVCLASH_OMNI_CLIENT_RETRY_MAX_MS has no effect: the ovstage runtime's omni client was not found

    ovclash looks for the client again each time it creates an ovstage instance, and on each ovclash_ovstage_run_owner_operation call.

Fix: Leave OVCLASH_OMNI_CLIENT_RETRY_MAX_MS unset, or set it to 0. Payloads, references and MDL (Material Definition Language) assets on an unreachable host then fail at once, and their geometry is missing from the results. Set a positive value (for example 120000) only when waiting through a short outage of the Nucleus server, which serves the omniverse:// URLs, is better than results without those assets.

ovclash applies the value once per process, when it first finds the client. The setting then holds for every caller that shares that client. An invalid value is reported on stderr (ovclash: ignoring invalid OVCLASH_OMNI_CLIENT_RETRY_MAX_MS="<value>") and treated as 0.

Building and running the shipped samples#

Samples describes the launchers, their runtime selection and the variables they read.

C/C++ samples missing from the wheel#

Symptom: A C/C++ sample cannot be built from the wheel.

Cause: The wheel ships only the Python samples and their launchers.

Fix: Use the SDK archive for the C/C++ samples. Building the C++ samples describes how to build them.

Sample Python setup failed#

Symptom: A sample launcher from an SDK archive or the wheel, or build_samples with an SDK archive, stops with:

Sample Python setup failed: <reason>

On a first run it can follow Preparing isolated ovstage==<pin> sample environment at <dir> and pip’s output. On Debian or Ubuntu without the python3-venv package, when the launch interpreter has no pip 22.3 or newer, a first run instead stops right after that line with the system’s own message that ensurepip is not available, which names the package to install, and no Sample Python setup failed: line.

Cause: The launchers and build_samples start from the interpreter that PYTHON names, python3 on Linux and python on Windows by default. When the exact ovstage pin is already available to it, they use it; a wheel’s launchers also find an ovstage installed beside the wheel. Otherwise they create a per-user cached virtual environment and install the pin into it with pip: %LOCALAPPDATA%\ovclash\samples\python\<key> on Windows, ${XDG_CACHE_HOME:-~/.cache}/ovclash/samples/python/<key> on Linux. The setup fails when:

  • pip cannot download the pinned wheel, for example offline or behind a blocked index. <reason> starts with Could not install ovstage==<pin> into <dir>:, and the pip output that precedes it says why.

  • The interpreter cannot create a virtual environment with pip. With pip 22.3 or newer in the launch interpreter, setup installs into the environment with that pip. Otherwise the environment must bootstrap pip, and Debian and Ubuntu ship ensurepip in the separate python3-venv package, so their system python3 stops with the message that the symptom describes until that package, or pip 22.3 or newer, is installed.

  • In an SDK archive, OVCLASH_OVSTAGE_PACKAGE_DIR is set but names no complete installation of the pinned version. With it set, no cached environment is prepared, and <reason> is the selection error described in The installed ovstage does not match the SDK.

  • The wheel’s own site directory holds an ovstage of another version, or an incomplete one. The samples import it first, so a cached environment cannot replace it. <reason> starts with The ovclash wheel requires ovstage==<pin>, but its site directory <site> holds and names what it found there.

  • The metadata names the pinned ovstage, but an import would load another one. <reason> is `The samples import ovstage from , not from the ovstage== installation at

    .`, or contains it.

  • A directory on the cache path is a symbolic link or junction (must not be a link or reparse point), or the cache root is not an absolute path.

Fix:

  • Let pip reach the pinned wheel, for example through a mirror named by PIP_INDEX_URL or a pip configuration file, then run again. Later runs reuse the cached environment.

  • On Debian or Ubuntu, install python3-venv (for example sudo apt-get install python3-venv), or set PYTHON to an interpreter that can create virtual environments.

  • In an SDK archive without network access, install the pin from a local wheel file, for example python -m pip install --target <dir> <ovstage wheel>, where <dir> is a new directory and <ovstage wheel> the path of the wheel file of the pinned version for your platform and Python. Then set OVCLASH_OVSTAGE_PACKAGE_DIR to <dir>/ovstage. pip refuses a wheel file built for another platform or Python version; download the matching file. Setting PYTHON to an interpreter that already has the pin works too.

  • The launchers ignore an inherited PYTHONPATH, so an ovstage that only PYTHONPATH reaches is never used. In an SDK archive, name it with OVCLASH_OVSTAGE_PACKAGE_DIR instead. The wheel ignores that variable: install the pin beside the wheel, as installing ovclash with its dependencies does, remove the mismatched ovstage there, or install ovclash into a clean environment.

  • Replace a linked cache directory with a real one, or point LOCALAPPDATA (Windows) or XDG_CACHE_HOME (Linux) at an absolute directory without links.

Sample Python setup helper not found#

Symptom: A packaged Python sample launcher, or a copy of one, exits with status 1:

Sample Python setup helper not found at "<install>/samples/sample_python.py" or "<samples>/sample_python.py".

Cause: Packaged Python launchers prepare their interpreter with samples/sample_python.py. They take it from the install root that --install-root or OVCLASH_INSTALL_ROOT selects, else from their own samples directory. Every SDK archive and wheel ships it. The launcher was copied out of its package, and the selected install root does not hold the helper either.

Fix: Run the launcher from its SDK archive or wheel, or pass --install-root with the SDK archive it should use.

SDK sample build cache cannot be selected#

Symptom: On Windows, build_samples.bat or a C++ sample launcher of an extracted SDK archive warns, and then builds anyway:

Could not select the short SDK sample build cache; building in "<dir>". A deep SDK path can exceed the Windows path length limit there. Set OVCLASH_SAMPLE_BUILD_ROOT to a short writable directory.

A later compiler or linker error about a path that is too long, or a Could not create sample build root error, can follow.

Cause: Without OVCLASH_SAMPLE_BUILD_ROOT or --build-root, an extracted Windows SDK archive builds its C++ samples in a per-user cache, %LOCALAPPDATA%\ovclash\samples\<SDK-path hash> (under %TEMP% when LOCALAPPDATA is unset), to keep compiler paths short. PowerShell computes that path. The warning means that powershell.exe is missing, blocked or limited to ConstrainedLanguage mode, or that neither LOCALAPPDATA nor TEMP names an absolute directory. The script then falls back to <dir>, a build directory inside the SDK archive root. That works only when the SDK archive root is writable and its path is short enough for the compiler.

Fix: Set OVCLASH_SAMPLE_BUILD_ROOT to a short, writable directory, or pass --build-root DIR to build_samples.bat.

Sample build root cannot be created#

Symptom: On Windows:

Could not create sample build root: "<dir>"

On Linux, a mkdir or marker-file write error such as Permission denied or Read-only file system.

Cause: The build root is not writable. A Linux SDK archive builds its samples in a build directory inside the SDK archive root by default, which is not writable when, for example, the SDK archive was extracted to a read-only location. An extracted Windows SDK archive defaults to a per-user cache instead; there the message names that cache, an explicit root, or the fallback of SDK sample build cache cannot be selected.

Fix: Set OVCLASH_SAMPLE_BUILD_ROOT to a writable directory, or pass --build-root DIR to build_samples. A relative value is anchored to the SDK archive root. Each sample builds in <build-root>/<sample>. On Linux, from the extracted SDK archive root:

./samples/build_samples.sh --build-root "$HOME/ovclash-sample-build"

Unsafe sample build root#

Symptom:

Unsafe sample build root: <dir> ...

Cause: build_samples refuses a build root that could hold other data:

  • Both scripts refuse the parent directory of the default build root.

  • Both refuse an existing, non-empty directory without the .ovclash-sample-build-root marker. The scripts write that marker into each build root they use. The default build root is exempt from this rule.

  • build_samples.sh also refuses a filesystem root, and the SDK archive root or one of its ancestors.

  • build_samples.bat also refuses the default build root when it or its parent directory is a junction or a symbolic link.

Fix: Point the build root at a new or empty directory.
