KPI baselines and budget packages#

This page uses the terms of the KPI glossary. A budget is the warning limit and the failure limit of one workload and required metric for one CPU model. A package is one sealed .kpi-budget.json file with the budgets of one backend, platform and CPU model. A baseline is the output of a complete collection: its generated series and packages. Check mode reads the packages of its backend and platform from a catalog folder and compares each measurement with their budgets.

There are two ways to create a package:

  • --mode collect-baseline is the normal way. It measures complete Release campaigns, selects the closest stable set and generates the packages. They carry an automated-generation attestation: a generation record that names the selected campaigns and their content hashes instead of a human approval.

  • budget create is the manual way. You collect calibration evidence yourself and approve the package locally. See offline budget recording.

The budget formulas and a worked example are in KPI sampling. Run every command from ovclash/. In the Python commands, $PY (%PY% in cmd.exe) is the KPI input Python defined in the quick start.

A baseline goes through five steps:

1. Collect   run_kpi --mode collect-baseline                writes <output>/public/baseline/
2. Review    $PY -m benchmarks.kpi baseline-series review     replays it and prints review.txt
3. Try       run_kpi --budgets <series>/baselines/{backend}/{platform}   (optional check run)
4. Install   copy baselines/<backend>/<platform>/*.kpi-budget.json into
             benchmarks/kpi/baselines/<backend>/<platform>/
5. Commit    check mode now finds coverage for that CPU model

Measurement and baseline rules#

A package enforces its budgets only when all of these hold:

Requirement

Rule

Complete Release campaigns

Every campaign measured all nine workloads with the release profile, and every workload ended stable: one warm-up, then at least three measured runs whose required metrics pass the noise gate. Calibration export already requires this. Adaptive Release sampling gives the run and retry limits

Clean producer

A validated clean Release build with a passing validation receipt of the same build; see calibration evidence

Independent campaigns

No two campaigns share a campaign ID, a child execution, a child token or a raw observation receipt

One identity per CPU model

All pooled campaigns share the build, runtime, source and measurement identity, the workload contracts, the required metrics, the acquisition policy, the CPU accounting counters and the CPU model. A generated package also requires the same cohort apart from the reported processor string and the CPU scope, so its campaigns may run on different pools of the model. The inputs of a budget create package share one identical cohort, CPU scope included; see evidence requirements

Pooled stability

For every workload and metric, all pooled values together pass the noise gate: 3 * MAD, three times the median absolute deviation, is within the noise limit of their median

Activation

A generated package carries a validated generation attestation. A budget create package carries a local approval. A package with neither is a proposal and enforces nothing

These never create or replace a package:

  • the public record measurements.json, which is a numeric diagnostic;

  • a smoke, incomplete, failed or interrupted campaign, which exports no calibration;

  • a green or nonblocking CI job, a successful work audit or one qualified row;

  • an ovstage measurement for the OpenUSD backend, or the reverse.

Runner and storage labels#

Every cohort records a runner class and a storage class. They describe the machine and its disk, and a package covers only runs with the same pair. Both come from closed lists, the calibration vocabulary in benchmarks/kpi/calibration.py (RUNNER_CLASSES and STORAGE_CLASSES):

Label

Values

Default without the option or variable

Runner class (--runner-class, OVCLASH_KPI_RUNNER_CLASS)

local-review, ci-linux-x86_64, ci-linux-aarch64, ci-windows-x86_64, and three classes of the project’s own CI machines that RUNNER_CLASSES lists

ci-<os>-<architecture> in a CI job, for example ci-linux-x86_64; local-review otherwise

Storage class (--storage-class, OVCLASH_KPI_STORAGE_CLASS)

local-ssd, ci-local-disk, unclassified-local-disk, disk

ci-local-disk in a CI job; unclassified-local-disk otherwise

"$PY" -I -B scripts/kpi_ci.py --help prints both lists. Run KPI in another CI system explains when a run counts as a CI job. The labels have these effects:

  • Matching. Budgets apply only to observations with the same runner class and storage class. A package collected locally (local-review, unclassified-local-disk) covers only local checks with those labels, never a CI job that records other labels. After a CI system changes the labels it sets, collect new baselines under the new labels.

  • Calibration export. Export accepts only the listed values. Packages are built from calibration evidence, so no package carries another label.

  • Check mode. A check accepts any label. Under a label outside the lists it finds no compatible budgets and ends with exit 3 before fixture generation.

  • Collection. A collection rejects a label outside the lists before preparation, with exit 4.

A package with local labels and a package with CI labels for the same CPU model cannot share a catalog folder; see install or replace CPU-model budgets.

Collect a baseline#

Before you begin:

  • Commit your changes. Release preparation rejects a build of uncommitted source.

  • Use a machine whose process affinity holds at least four usable physical cores of one CPU model. Otherwise the collection stops with exit 3; see collection status and exit codes.

  • Choose an --output that does not exist yet.

--mode collect-baseline ignores all existing budgets. It runs complete Release campaigns until it can select --baseline-campaigns N campaigns per CPU model whose pooled values pass the noise gate. Without --inputs or --dist, the launcher first prepares the default Release inputs when they are missing, invalid or not built from the checked-out source; see automatic preparation.

Windows:

run_kpi.bat --mode collect-baseline --baseline-campaigns 3 --backend ovstage --collection-seconds 13800 --output _build/kpi-baseline-01

Linux x86-64 and AArch64:

bash ./run_kpi.sh --mode collect-baseline --baseline-campaigns 3 --backend ovstage --collection-seconds 13800 --output _build/kpi-baseline-01

Use --backend openusd for the OpenUSD reference backend. Choose a new --output for every run: the public output must not exist, and outputs lists the staging and lock files that an abrupt exit can leave beside it.

The collection succeeded when it exits 0, the last line of public/progress.log starts with Exit 0 | collection_complete and public/baseline/ exists. Any other result names its cause in that line and in public/status.json; see collection status and exit codes and, for a failed preparation, Troubleshooting.

A collection treats these options differently from a check. Command-line options lists every option and its default.

Each run measures only the CPU models of the machine it runs on; another CPU model needs another run on another machine.

How a collection runs#

The driver scripts/kpi_ci.py hands a collection to the collector scripts/kpi_collect.py, which runs these steps in order. A Failed phase: line names the step by the code name in parentheses.

  1. Configuration (configuration). It checks the campaign count, the allowance, the CI job deadline, the admission policy and the CPU domain, the labels and the required-model list. It rejects outputs inside --inputs or --dist, and it creates the public output, which must not exist. A failure here writes no file and exits 4; see rejected input.

  2. Release preparation (Release preparation). It binds the validated Release SDK archive, wheel, runtime and validation receipt once, and rejects a build of uncommitted source. It observes the CPU pools of this machine and logs every CPU model it can measure.

  3. Fixture generation (immutable fixture generation). It generates the three bundles once and checks their pins; see representative fixture stages.

  4. Campaign collection (campaign collection). It runs campaigns one after another. Each campaign calls the controller command run --mode collect-baseline --profile release in a fresh private execution tree, with a campaign deadline from the time left (see deadline). After a successful campaign it exports the campaign’s calibration.json, replays it independently and selects a qualifying set for every CPU model that has one. Failures inside a campaign name campaign execution, calibration export, independent calibration validation or private execution cleanup. A selection failure names campaign selection.

  5. Baseline generation and publication (baseline generation and publication). When every model qualifies, it replays every eligible campaign again, writes the series in a hidden staging directory and renames it to baseline/ in one step.

  6. Collection result. It writes the final status.json and the last progress.log line.

Inside a campaign, a workload whose series fails for a verified noise or CPU cause restarts alone, at most ten times. Check mode never restarts a workload. See workload restarts.

Campaign selection#

After each eligible campaign, the collector groups the eligible campaigns by CPU model. For every set of exactly N campaigns of one model, it computes a score per workload and metric:

score = (largest campaign median - smallest campaign median) / median of the N medians / noise limit

The noise limit is the metric’s limit in the noise gate: 0.25 for load_seconds and 0.15 for every other required metric. A score of 1.0 means that the spread of the campaign medians equals the noise limit.

  1. Sets rank by their largest score, then by the sum of their scores, then by their sorted campaign IDs.

  2. The collector takes the best-ranked set whose pooled values pass the noise gate. The gate pools every value of the N campaigns and requires 3 * MAD within the noise limit of the median.

  3. The score only ranks the sets. A set with a score above 1.0 can still pass the gate.

Every metric uses the same selected campaigns, and each campaign contributes all of its values. Metrics are never selected separately, and no favorable subset of values is chosen. The selection policy is closest-three-campaigns-v1 for N = 3 and closest-n-campaigns-v1 for a larger N.

Example. Three campaigns A, B and C have the medians 100, 101 and 102 seconds for every time metric, and three values per campaign:

load_seconds        (102 - 100) / 101 / 0.25 = 0.079
operation_seconds   (102 - 100) / 101 / 0.15 = 0.132
set score           largest 0.132; sum 4.277 over the 47 metrics (memory metrics do not vary here)
pooled gate         MAD 1.0, 3 * MAD = 3.0 <= 15% of 101: stable

The pooled values give the budget of the worked example: N = 3.0, a warning limit of 109.05 and a failure limit of 114.1.

Replace C with an outlier campaign O whose medians are 200 seconds. The set A, B, O scores 6.6, but its pooled MAD is still 1.0, so it passes the gate. Its largest deviation is 99, so N = 99, the warning limit is 205.05 and the failure limit is 210.1. When A, B, C and O are all candidates, the collector selects A, B and C, because that set ranks first. The collector stops as soon as one set qualifies, so a run whose first three eligible campaigns are A, O and B publishes the wide budgets. Check the scores in review and install a generated series before you install.

These numbers come from the synthetic test campaigns of tests/python_tests/kpi_baseline_fixture.py.

Disposition

Stops with 3 (collection_insufficient_physical_cores)

Any other result: a product failure (1), other insufficient evidence (3), or a harness, export or replay failure (4)

fatal

Stops with that exit (collection_fatal_campaign)

A campaign is retryable only when its workflow receipt passed, its inputs stayed unchanged and its source is verified and clean. Every other executed attempt of its final series must be a qualified success or a verified pre-run CPU rejection. A spent shared CPU-wait allowance, which the whole campaign shares, stops the campaign, and the collector retries it as cpu_contention. A workload that used all its restarts without a stable result also ends the campaign with a retryable cause.

Deadline#

The deadline is --collection-seconds after the collector starts. When the CI context supplies the job timeout and start time, the deadline is also at least 300 seconds before the job deadline, the start time plus the timeout. Those 300 seconds are left for uploading the output. The context reads them from the CI provider, or from the provider-neutral OVCLASH_CI_JOB_TIMEOUT (seconds) and OVCLASH_CI_JOB_STARTED_AT (an ISO 8601 time with a time zone); see Run KPI in another CI system. When only one of the two values is set, or either cannot be parsed, the collection is rejected before preparation.

For a job with a four-hour timeout (14,400 seconds) that started at 08:00:00 UTC and a 13,800-second allowance:

Collection starts

Job-based stop

08:04:00 (240 s of setup)

11:55:00

11:54:00

11:54:00, the full 13,800 seconds

08:10:00 (600 s of setup)

11:55:00

12:00:00

11:55:00, only 13,500 seconds

So with these values, up to 300 seconds of job setup still leave the full allowance. Inside that window, the collector keeps these reserves:

Check

Rule

Before fixture generation

More than 330 seconds must remain: 300 for cleanup and 30 for publication

New campaign

Starts only while more than 330 seconds remain

Campaign deadline

--job-seconds is the time left minus the 30-second publication reserve. The controller keeps its own 300-second cleanup reserve inside it; see deadlines

Evaluation

An eligible campaign is evaluated only while more than 2 * (sum of measured replay times) + 30 seconds remain. Otherwise it is retained with the ledger reason selection_deadline, and collection stops with 3

Generation

Generation replays every eligible campaign again and must finish 30 seconds before the deadline. The final rename must happen before the deadline

The deadline lines:

progress.log line

When

An eligible campaign reached the evaluation reserve (selection_deadline)

Campaign collection ended at the deadline: no time for another campaign, a campaign deadline, or the evaluation reserve

Collection deadline reached; no baseline generated.

The deadline came before fixture generation, during generation or before the final rename

The completed campaigns, their records and their calibration exports stay in the public output. No baseline/ is written.

Collection status and exit codes#

The final progress.log line and status.json record the collector’s own result. Read them whenever the process exit code is not available as is, for example on a CI system that reports every nonzero Windows exit as 1. The final line has this form:

Exit <code> | <reason> | requested <N> per CPU model | eligible <E> | attempts <A>

Exit

reason

Meaning

0

collection_complete

Every observed and required CPU model has a qualifying set, and baseline/ was published

3

collection_deadline

The allowance or the CI job deadline ended collection before every model qualified

3

collection_required_model_unavailable

Every observed model qualified, but each remaining required model is absent on this machine. The collection cannot move to another machine

3

collection_insufficient_physical_cores

Fewer than four usable physical cores are in the process affinity, found before fixture generation or inside a campaign

3

collection_cpu_model_unavailable

1, 3 or 4

collection_fatal_campaign

The last campaign verdict cannot be retried

4

4

A preparation, generation or publication failure, or a failed final status write

The collector never returns 76; exit 76 describes the check-mode code. In CI, a collection also needs the actual job ID; without it, the collection stops after fixture generation with collection_harness_failure.

Failed phases. A failed phase logs Failed phase: <phase> | <kind> | <exception class>. The kind is one of cancellation, process cleanup unverified, required input missing, input or output access denied, input identity or evidence validation failed or unexpected harness exception. On Windows, a private path past MAX_PATH logs the kind Windows private KPI paths exceed MAX_PATH; set TMPDIR, TEMP and TMP to a shorter folder instead; see private execution tree. When the exception message is fixed text from the KPI or shared tooling sources, or from scripts/kpi_ci.py or scripts/kpi_collect.py, a second line names the check. A message that carries a path, a value or other runtime text is never logged. For example:

Failed phase: independent calibration validation | input identity or evidence validation failed | ValueError
Failure detail: calibration requires three observations of every frozen workload

Review and install a generated series#

Review replays every retained campaign and repeats the selection. It then checks that the packages and review.txt are exactly what that replay produces.

Before you begin: you need the baseline/ directory of a complete collection (exit 0, collection_complete) with series.json, review.txt, evidence/ and baselines/ together and unchanged, and $PY from the quick start. The commands use the --output of the collection example. To see the packages work before you install them, you can also run a check against them first; see try the packages before installing.

  1. Get the complete baseline/ directory: <output>/public/baseline of the collection, or the same directory from the CI job that ran it. A copy that misses a file, or holds a changed or extra one, fails the review with exit 4; review results lists the causes.

  2. Run the review.

    Linux:

    "$PY" -B -m benchmarks.kpi baseline-series review --input _build/kpi-baseline-01/public/baseline

    Windows (cmd.exe):

    "%PY%" -B -m benchmarks.kpi baseline-series review --input _build/kpi-baseline-01/public/baseline

    It prints the review text and exits 0. The text equals review.txt.

  3. Check the CPU models in the review: its CPU models: count and one CPU MODEL section per model that you expect. A model that is not there needs a collection on a machine with that CPU model.

  4. Read the campaign counts in the last line of progress.log, Exit 0 | collection_complete | requested <N> per CPU model | eligible <E> | attempts <A>. Each attempt beyond the eligible campaigns was a retryable campaign, and the Retry: line after it in progress.log names the cause, such as Retry: cpu contention.

  5. Read the Limiting metric: lines of progress.log, if any. Each names a metric that kept the candidates of one CPU model from passing the pooled noise gate together.

  6. Check the two scores of each model in the review. A largest score above 1.0 widens both limits of the budget by the distance to the farthest campaign; see the campaign selection example.

  7. Install the packages; see install or replace CPU-model budgets.

  8. Keep the downloaded artifact unchanged for later audits: its review records name the generated files.

Review results#

The review fails, prints kpi baseline-series: retained evidence validation failed on stderr and exits 4 when anything differs:

  • a package, review.txt or a calibration file was changed;

  • the directory holds a file that series.json does not declare, such as a copied status.json or progress.log;

  • series.json or a retained input changes while the replay runs;

  • the series is incomplete or does not record its campaign count.

A series that names a .kpi-budget.zip package, the removed package shape of budget packages, prints a second line with the removal message.

Budget packages#

Catalogs and --budgets accept only the ovclash-kpi-compact-budget-package-v1 format, schema version 1. A package is one plain JSON file named <name>.kpi-budget.json. It holds the budgets, not the measurements.

The bytes are sealed. A package must be exactly what the writer produces:

  • sorted keys and one-space indentation;

  • UTF-8 without a byte-order mark;

  • LF line endings and one final newline;

  • no duplicate fields and no NaN or infinity;

  • at most 4 MiB.

A reformatted or CRLF copy is rejected with compact package is not in its sealed .kpi-budget.json form, even when it decodes to the same document.

A .kpi-budget.zip file is the removed package shape. It is rejected with the .kpi-budget.zip package shape was removed; KPI budget packages are plain .kpi-budget.json files. A --budgets path with that suffix, or a catalog folder that holds such a file, fails the check with exit 4.

How check mode matches a package#

A package covers a CPU model only when both of its compatibility digests match the observed run:

  • cpu_model_sha256 is the SHA-256 of the CPU model key, model_key: its schema version, the CPU domain, platform, architecture, processor identity, core class and SMT width. This digest is the model ID, and a generated package uses it as its file name.

  • absolute_pre_scope_sha256 covers the rest of the cohort, without the reported processor string and the CPU scope: platform, architecture, backend, runner class, storage class, interpreter, load and admission policy and CPU domain. On Windows it also covers the windows-pdh-direct-accounting-v2 counter contract and the collection-bracketed-cpu-accounting-envelope-v2 envelope contract.

The CPU placement may differ: a run on any pool of the same CPU model matches. A CPU model without a matching package has no coverage and no fallback to another model.

A candidate is then compared with each row as described in budget limits. Without complete coverage, the launchers stop before fixture generation with exit 3; mode and lookup lines shows the lookup lines.

Offline budget recording#

collect-baseline is the normal way to create packages. Offline budget recording is the manual alternative: you collect calibration evidence yourself, review it with budget create and approve the package locally.

budget create reads calibration evidence in the ovclash-kpi-calibration-evidence-v11 contract, which carries privacy-safe calibration from complete Release campaigns of the shared launchers under the current acquisition policy. Readers reject any other calibration version or acquisition policy. Public numerical diagnostics alone cannot be passed to budget create --artifacts.

budget create accepts 1 to 100 intact calibration directories or local calibration ZIPs after one --artifacts option. Each input holds exactly one calibration.json. A directory or ZIP without one is rejected with baseline campaign requires portable calibration evidence. The command verifies every workload and metric observation offline, prints one review table and asks for local approval. It writes one sealed .kpi-budget.json package in the ovclash-kpi-compact-budget-package-v1 format with the approved-cpu-model-limits-v2 contract; see budget packages. The package holds the reviewed budgets, not the measurements or the runtime. The command needs no CI service and runs no native workload.

Evidence requirements#

Calibration evidence gives the conditions under which a run exports calibration, what the export holds and what readers check. Pass these extracted directories:

  • the calibration directory of a --profile release check run;

  • the public/campaigns/<NNNN>/calibration directory of each collection campaign that ended with exit 0 and a verified drain;

  • the same directories from a CI job artifact.

budget create runs those reader checks offline on every input. Readers do not trust a stored qualification flag or projected budget. Content hashes and sizes record what the producer validated, and readers cannot rehash binaries absent from the artifact.

All inputs of one package must share one producer (the build, runtime, source and measurement identity), one workload contract and sampling policy, and one identical cohort and compatibility binding, CPU scope included. Every input therefore ran in the same verified four-core pool: retry-v2 observations may use different CPU IDs only within that pool. A generated package is less strict; its campaigns may come from different pools of one CPU model (see measurement and baseline rules). Never pool backends, platforms, CPU models, admission policies, CPU-domain versions or runtimes: ovstage budgets cannot qualify OpenUSD measurements, even on the same CPU. Duplicate input files and repeated campaigns or child executions are rejected; they are not new observations.

Measurement identity hashes the measurement sources (see measurement identity). Pool only campaigns that ran from the same sources. The cohort also records the CPU quota hierarchy of the Linux control groups (cgroups, the kernel’s per-process-group resource limits), without paths. On one Linux host, a desktop terminal, a systemd-run --user --scope unit and an SSH session give different hierarchies, so start every pooled local campaign the same way. budget create names the first differing part and up to three field levels, without values, on stderr and exits 4, for example:

KPI harness-failure: budget-create: artifacts differ in cohort field cpu_scope.cpu_constraints.quota_hierarchy

Collection plan and stopping rules#

Decide the number of campaigns and a finite attempt limit before you collect. One complete eligible Release campaign is enough for a proposal. Three observations per workload and three independent campaigns are different counts. More campaigns describe variability, but they never waive the noise gate. Do not continue collecting until a favorable result appears.

A machine can expose different core classes and SMT widths under one CPU model name. Keep campaigns of different classes apart: their differences establish no regression, noise estimate or budget. Include every eligible value of each campaign you use. Never trim slow values, and never fill missing cells from incomplete or incompatible evidence. A changed counter model, measurement source or workload needs a fresh collection.

Create and approve a package#

Before you begin: extract the calibration directories that meet the evidence requirements, and set $PY as in the quick start. Pass every retained campaign of one CPU model, not a favorable subset, and a fresh output name that ends in .kpi-budget.json. The first command reads the calibration of one check run; the second reads two campaigns of a collection.

For a noninteractive choice, add --approve or --no-approve. --approve still validates and prints the review, and it cannot approve an ineligible package. Approval is a local review assertion by the operator, not a CI signature. The package records reviewer: "identity-withheld" and the UTC review time, separate from created_at_utc. The command does not look up the local user. To approve a proposal later, run budget create again from the original inputs into a fresh output. Never edit budgets or approval JSON by hand.

The command succeeded when it exits 0 and prints Budget package written: with the path of the new package. On a failure it writes no package, prints one KPI <status>: budget-create: line with a fixed reason on stderr and exits nonzero, for example KPI harness-failure: budget-create: output already exists; choose a fresh .kpi-budget.json output (exit 4) or KPI insufficient-evidence: budget-create: required local evidence input is unavailable (exit 3).

Budgets follow the formulas in KPI sampling. Install the package as described in install or replace CPU-model budgets, or test it first as described in check against a local package.

Check against a local package#

Before you begin: the package must exist, and it must cover this machine’s CPU model with the same runner and storage labels and cohort that the check records; see how check mode matches a package.

The launchers and the controller accept --budgets with a catalog directory or one package file. A launcher with a single package, from ovclash/:

Linux:

bash ./run_kpi.sh --profile release --budgets _build/kpi/cpu-reviewed.kpi-budget.json --output _build/kpi-local-budget-check

Windows:

run_kpi.bat --profile release --budgets _build/kpi/cpu-reviewed.kpi-budget.json --output _build/kpi-local-budget-check

Check mode reads one catalog per backend and platform:

Platform

ovstage catalog

benchmarks/kpi/baselines/ovstage/linux/

benchmarks/kpi/baselines/openusd/linux/

benchmarks/kpi/baselines/openusd/windows/

Each folder is checked in with a .gitkeep and may be empty. No KPI command edits these folders.

Before you begin: review the series or create the package, and find any older package of the same CPU model in the target folder; the catalog rules reject two packages for one CPU model.

To install a reviewed series on Linux x86-64, from ovclash/:

cp _build/kpi-baseline-01/public/baseline/baselines/ovstage/linux/*.kpi-budget.json benchmarks/kpi/baselines/ovstage/linux/
git add benchmarks/kpi/baselines/ovstage/linux/

On Linux AArch64, from ovclash/:

cp _build/kpi-baseline-01/public/baseline/baselines/ovstage/aarch64/*.kpi-budget.json benchmarks/kpi/baselines/ovstage/aarch64/
git add benchmarks/kpi/baselines/ovstage/aarch64/

On Windows, from ovclash\:

copy _build\kpi-baseline-01\public\baseline\baselines\ovstage\windows\*.kpi-budget.json benchmarks\kpi\baselines\ovstage\windows\
git add benchmarks\kpi\baselines\ovstage\windows\

For the OpenUSD backend, replace ovstage with openusd in both paths of each command. Copy the files unchanged. ovclash/.gitattributes marks benchmarks/kpi/baselines/**/*.kpi-budget.json as text eol=lf, so every checkout keeps the sealed LF bytes. Check mode selects a package by the compatibility inside it, not by its file name, so an installed copy may be renamed if it keeps the .kpi-budget.json suffix. A package from budget create is installed the same way and may use any descriptive name that ends in .kpi-budget.json.

To confirm the installation, run a check without --budgets on a machine of that CPU model and with the package’s labels. Its lookup prints Baseline source: default and Baseline lookup: coverage found; performance comparison is pending. A folder that breaks a catalog rule fails the check with exit 4 instead.

Keep one package per CPU model in a folder, whatever its labels. Remove the older package of the same CPU model in the same change. Two packages with budgets for the same CPU model, workload and metric are rejected as ambiguous duplicate CPU-model workload/metric limits, even when their runner or storage labels differ. A package with local labels therefore cannot sit beside the CI package of the same model. Never let a package with local labels replace one with CI labels: CI checks of that model would lose their coverage. Packages of different CPU models coexist.

Catalog rules#

Check mode loads the whole folder before it measures:

  • It reads only files that end in .kpi-budget.json and ignores other files, except that a file of the removed .kpi-budget.zip shape fails the folder; see budget packages.

  • A folder holds at most 256 entries of any kind, at most 64 packages and at most 32 MiB in total. Each package is at most 4 MiB.

  • Neither the folder nor a package may be a link. Package names must differ by more than letter case.

  • Every package must be approved or generated, use the approved-cpu-model-limits-v2 or approved-cpu-model-limits-v1 contract and the current acquisition policy, and keep its sealed bytes.

  • No two packages may define budgets for the same CPU model, workload and metric.

  • The folder and every package are checked again after loading; a change during loading fails.

A folder that breaks one of these rules fails every check on that backend and platform with exit 4, whatever the observed CPU model, until it is fixed. A valid package that does not match the observed cohort only leaves its CPU model without coverage.

Stale packages#

Committed packages become stale when the measured work or the package rules change:

Change

Effect

A frozen workload, a bundle recipe or a new required metric

The workload digests no longer match: check mode finds no coverage and exits 3

The acquisition policy or the package format

The packages fail to load: every check on that backend and platform exits 4

CommittedCatalogTests in tests/python_tests/test_kpi_preflight.py then fails. Regenerate the affected packages from fresh campaigns, or remove them, in the same change. See refresh pinned fixture identities.
