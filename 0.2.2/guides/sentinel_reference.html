Sentinel reference#

This page lists every Sentinel command, option, environment variable, evidence file and verdict rule. The Sentinel guide explains how a run works and how to use it, and its glossary defines the Sentinel terms used here, such as driver, campaign child, cell and golden. Sentinel goldens owns the goldens commands.

Paths are relative to the ovclash directory. <evidence> is the evidence/ directory of one run, which the run prints on its Results: line.

Launchers#

test_sentinel.bat (Windows cmd.exe) and test_sentinel.sh (Linux) take the same arguments. They select a Python interpreter and run the driver, scripts/sentinel_ci.py, with every argument unchanged.

test_sentinel.bat [COMMAND] [OPTIONS]
./test_sentinel.sh [COMMAND] [OPTIONS]

  • With no command, the launcher runs run. A first argument that is a run option also means run, so test_sentinel.bat --backend openusd equals test_sentinel.bat run --backend openusd.

  • --version prints ovclash <VERSION> from the VERSION file without starting Python. It works alone, after a command (run --version) and after a goldens subcommand (goldens verify --version).

  • The launchers set PYTHONNOUSERSITE=1 and PYTHONUNBUFFERED=1 unless they are already set.

Python selection#

The launcher uses the first interpreter that exists:

  1. _build/deps/target-deps/python of the launcher’s own checkout.

  2. python-runtime/ of the portable input bundle that --inputs names. Without --inputs, the default bundle _build/portable-inputs/<backend>/<configuration> is tried.

  3. ovclash/_build/deps/target-deps/python of the tree that --source-root selects.

  4. Only for commands other than run: python-runtime/ of any staged bundle under _build/portable-inputs/{ovstage,openusd}/{Release,Debug}.

The launcher reads <backend> and <configuration> from --backend and --configuration, then from OVCLASH_VALIDATION_BACKEND and OVCLASH_VALIDATION_CONFIG, then uses ovstage and Release. The backend is ovstage or openusd, for the ovstage and OpenUSD builds.

When no interpreter exists:

Result

Any request with --help or -h

Prints the short overview shown at the end of Python selection and exits 0.

A command other than run

Prints Sentinel requires an existing build and Python runtime for this command. and exits 1.

run with an explicit --inputs

Prints Sentinel portable inputs lack a Python runtime; regenerate the selected bundle. and exits 1.

Runs the bootstrap build build_<backend> --release --validate (or --debug) in the source tree, then uses that tree’s interpreter.

The bootstrap build prints its output on the console and writes no Sentinel evidence. It ignores --preparation-timeout. If it fails, the launcher exits with the build’s exit code. If the build passes but provides no interpreter, the launcher prints Sentinel build did not provide its Python runtime. and exits 1. Like the automatic builds that Sentinel itself starts, the bootstrap build keeps the test_python_runtime validation step; see automatic input preparation.

The short overview, here from test_sentinel.sh:

Sentinel validates ovclash engine behavior and serialization.
Usage: ./test_sentinel.sh [run] [--backend ovstage|openusd] [--configuration Release|Debug] [--output PATH]
Defaults: run --backend ovstage --configuration Release, writing a new directory under _build/sentinel

Full command help is available after the first build provides Python.

run options#

After the run-start banner, run prints Sentinel settings: in both verbosity modes, before semantic startup checks, output-directory admission and preparation. Arguments: records command arguments as JSON; Environment:, when present, shows set variables from the validation, color, parallelism and CI-deadline allowlist. Effective settings: lists the resolved run options, including the CPU-bounded worker count and Configured campaign cap (seconds). That cap can shrink against the remaining CI budget and publication reserve. Repository inputs: names the case files, golden root, contracts and controller Python. If settings resolution or encoding fails, Settings unavailable gives only the exception type; raw arguments and allowlisted environment values remain visible and normal validation proceeds. See console output for the complete order and examples.

Rules:

  • Every timeout must be positive and finite. Otherwise the run fails with timeouts must be positive.

  • A backend or configuration from the environment that is not allowed fails with an argument error, for example OVCLASH_VALIDATION_BACKEND/--backend must be ovstage or openusd, not 'usd'.

  • When --engine-profile, OVCLASH_VALIDATION_ENGINE_PROFILE and OVCLASH_EQ_ENGINE_PROFILE set different values, the run fails with Conflicting validation input (conflict): ENGINE_PROFILE.

  • An explicit --output that exists and is not empty fails with Evidence directory is not empty: <path>; remove it or pass --output with a new directory.

  • A default results directory that already exists for the same second gets a -2, -3, … suffix.

  • The driver refuses to run with Python assertions disabled (python -O): CI gate requires assertions enabled.

Deadline budget#

Every run works inside one budget:

  • The outer budget is six hours. Fifteen minutes of it are reserved for publishing evidence.

  • The preparation phase covers startup input preparation and every control before the campaign. --preparation-timeout bounds it.

  • The campaign phase covers the campaign child. --differential-timeout bounds it.

  • Each command’s deadline is the smallest of its own deadline, the rest of its phase and the rest of the outer budget.

An exhausted phase fails with Validation preparation budget exhausted; publication reserve is protected (or campaign). gate-summary.json records the budget in deadline_budget.

Verdict rules#

A run passes only when all of these hold:

  1. Startup selected complete inputs, and every control before the campaign passed.

  2. The campaign child exited 0.

  3. differential/summary.json reports PASS with complete accounting: every required serialization comparison exactly once with zero differences, and a complete engine campaign (engine_gate_complete).

  4. The dataset matches the launched inventory: the profile’s seed count and all live cases.

  5. The installed runtime is unchanged between the first and the last check.

  6. Every owned process tree was drained.

Status fields keep the two kinds of evidence apart:

  • checks_status covers only independent checks: serialization and the engine cells’ semantic checks.

  • golden_status covers only golden comparisons. Its priority is INVALID > DIFFERENT > MISSING > PASS.

  • An engine cell whose independent checks pass is admitted even when its golden comparison fails. The run then fails at final accounting.

The driver sets checks_status to FAIL and records golden_update_error when the independent checks passed but the run is not a clean golden-only failure. A clean golden-only failure needs a MISSING or DIFFERENT golden status, every driver command passed, and the campaign child exited 1 within its deadline. A changed runtime identity also forces checks_status to FAIL. Only a run with checks_status: PASS can supply a golden proposal.
