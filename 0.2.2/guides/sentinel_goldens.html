Sentinel repository goldens#

Goldens are reviewed typed results that Sentinel compares with the output of the candidate, the installed SDK under test. They live in tests/sentinel/goldens/, together with historical SQLite databases that the current reader must still decode. Ordinary Sentinel runs read the catalog and never change it. Only the goldens commands on this page write it.

The Sentinel guide describes how a run uses goldens, and its glossary defines the Sentinel terms used here, such as case, variant, snapshot, cell, build tuple, shard and tuple file. The Sentinel reference describes the run’s evidence files. Paths on this page are relative to the ovclash directory.

What the ZIP files represent#

A golden is the reviewed expected result of one Sentinel case, variant and snapshot, for one set of frozen inputs and one build tuple. Sentinel captures the candidate’s typed result and compares it with that golden. Goldens are neither performance measurements nor the budgets of KPI, the performance benchmark.

The catalog keeps selection separate from storage:

Understand a golden failure#

Independent checks verify a case’s geometry or API contract, and serialization checks verify round trips. A golden comparison asks only whether the candidate still produces the reviewed typed result. Passing one kind of check does not excuse a failure in the other.

Golden status

Meaning

Next step

PASS

The candidate’s typed result matches the selected golden.

None for this snapshot. The run passes only when all its other checks pass too.

MISSING

No golden exists for this identity and build tuple.

Review the candidate run, then propose only the intended additions. Never copy another tuple’s golden.

DIFFERENT

A golden exists, and the typed contents differ.

Read the differences. Decide whether this is a regression or an intended behavior change before you accept a replacement.

INVALID

A bundle cannot be decoded or breaks the typed contract, for example with a missing or extra field.

Check invalid_side to find the malformed bundle. goldens propose rejects any run with an INVALID comparison, so no proposal can replace that bundle.

A run’s golden_status is its most severe comparison status, in the order INVALID, DIFFERENT, MISSING, PASS.

A golden-only failure prints no failed check line: every engine cell passes, and so does Engine completion. The Sentinel guide shows the console output. This script, run from the run’s results directory, prints the run’s statuses and every snapshot that did not pass:

import json

with open("evidence/gate-summary.json", encoding="utf-8") as stream:
    report = json.load(stream)
print("checks:", report.get("checks_status"), "goldens:", report.get("golden_status"))
print("golden update error:", report.get("golden_update_error"))
for snapshot in report.get("golden_snapshots", []):
    if snapshot["status"] != "PASS":
        cell = snapshot["cell"]
        print(snapshot["status"], cell["case_id"], cell["variant"], snapshot["snapshot"], len(snapshot["differences"]))

For a golden-only failure of a changed depth case, it prints lines like these, where <variant> is the variant ID and <count> the number of typed differences:

checks: PASS goldens: DIFFERENT
golden update error: None
DIFFERENT engine-options-depth <variant> snapshot_bundles.snapshot <count>

<evidence>/junit.xml, the CI test report, marks each engine cell whose golden status is not PASS as failed.

Comparison has no numerical tolerance. A changed nbCollidingSegments value or array shape is a change in correctness output, not noise. Each of the twelve build tuples has its own goldens, and a proposal covers only the tuple of the run it comes from. A new case therefore needs an accepted golden from a run of every tuple; see changes that affect tuples you cannot run.

Do not regenerate or accept every current output just to make a run pass. Review the frozen inputs and the implementation change, keep unaffected goldens, and use the proposal and acceptance workflow. A run whose only failures are MISSING or DIFFERENT comparisons can supply a proposal, and writes a proposal of its changed snapshots to golden-proposal/. That eligibility does not approve its output.

Catalog identity and storage#

A golden’s identity is its case ID, variant, snapshot, frozen inputs and build axes. Sentinel reads the candidate’s platform, architecture, backend and configuration from the verified build manifest and loads only the tuple file of that exact tuple. There is no fallback to another tuple or to current output. The twelve approved tuples are Windows x86-64, Linux x86-64 and Linux AArch64, each with both backends, ovstage and OpenUSD, in Release and Debug.

A tuple without a tuple file still runs every independent engine and serialization check, including the historical database reads. It records every golden comparison as MISSING, so the run fails until results for that tuple are accepted. A malformed catalog or an inconsistent selected shard fails the run before any comparison.

Input families store the approved inputs as facts. They do not follow later edits to tests/sentinel/engine_cases.json or to setting defaults. A changed input gives the candidate a new identity, which has no golden yet. Loading derives only three fields from saved values: seed from the fixture, and task_count and detection_mode from the settings. tests/sentinel/golden_inputs.py defines these derivations.

For canonical cells, the resolved_settings mapping is not part of the identity. A change that affects only the mapping therefore needs no new golden. The run still checks the mapping against the requested and effective native settings it captures. Suite cells, the cells of a case that drives the Suite API, keep resolved_suite in their identity.

FAMILY_CASES in tests/sentinel/golden_catalog.py assigns every case ID to an input family. Add a new case there before you accept its results. Otherwise goldens accept fails with Unmapped golden case: <case>.

The two native floating-point cases, engine-reports-floating-point and engine-reports-floating-point-kernel0, check all eight runtime snapshots. Each backend compares only four representatives with goldens: sync, alternate, oracle and matched. Independent checks require each of the other four snapshots to equal its representative; see the floating-point matrix. Snapshots with the same names in other cases are not aliases and keep their own comparisons. Reports list the runtime checks in snapshot_checks and required_snapshot_checks, and the golden comparisons in golden_snapshots and required_golden_snapshots.

Comparison extracts each ZIP into its own sentinel-golden-* directory under _build/test_tmp, or under OVCLASH_TEST_TEMP_ROOT when it is set. It removes only that directory afterwards. It compares the case list, record occurrences, ID and field policies, types, shapes, counts, nullness, parent identities and payload bits. For records with generated IDs, such as those read from a live fixture, the ID value is not compared, and each generated timestamp must lie inside the recorded generation window.

Storage rules:

  • Catalog metadata is JSON with LF line endings, below 1,048,576 bytes per file, stored in ordinary Git.

  • A publish writes each new or changed metadata file as compact, deterministic JSON. A file whose value does not change keeps its bytes, so an indented shard stays indented until its content changes.

  • Engine ZIPs are deterministic and stored as ordinary Git binary files. Payloads and historical databases keep their exact bytes.

  • Paths are relative to the catalog.

  • generated_by and the review reason are attribution only. They select no source checkout or SDK, and no fingerprint or receipt authenticates any file.

Propose and accept results#

Before you begin, you need the Python runtime of an existing build or staged portable input bundle; the goldens commands never start a build. Run them from ovclash, with test_sentinel.bat on Windows or ./test_sentinel.sh on Linux. Every example on this page uses test_sentinel.bat; on Linux, replace it with ./test_sentinel.sh and keep the arguments.

In the commands, RUN is the results directory or the report of a completed run, CASE an engine case ID such as engine-options-depth, PROPOSAL a new directory outside the catalog, such as _build/proposal-depth, and OTHER_PROPOSAL a second proposal, such as the one of another build tuple.

A run that fails only on MISSING or DIFFERENT comparisons has already written a proposal of those snapshots, and its console names the accept command for it; see the proposal of a golden-only failure. Use propose to select other snapshots or to propose from a saved run.

Windows (cmd.exe):

test_sentinel.bat goldens propose --from-run RUN --case CASE --output PROPOSAL
test_sentinel.bat goldens propose --from-run RUN --all --output PROPOSAL
test_sentinel.bat goldens propose --from-run RUN --changed --output PROPOSAL
test_sentinel.bat goldens accept --proposal PROPOSAL --reason "Reviewed intentional change"
test_sentinel.bat goldens accept --proposal PROPOSAL --proposal OTHER_PROPOSAL --reason "Reviewed intentional change"

Linux:

./test_sentinel.sh goldens propose --from-run RUN --case CASE --output PROPOSAL
./test_sentinel.sh goldens propose --from-run RUN --all --output PROPOSAL
./test_sentinel.sh goldens propose --from-run RUN --changed --output PROPOSAL
./test_sentinel.sh goldens accept --proposal PROPOSAL --reason "Reviewed intentional change"
./test_sentinel.sh goldens accept --proposal PROPOSAL --proposal OTHER_PROPOSAL --reason "Reviewed intentional change"

The three propose commands are alternatives: propose named cases, every eligible case, or only the MISSING and DIFFERENT snapshots. The two accept commands are alternatives too: accept one proposal, or several, such as one per build tuple, in one catalog update. A failed command prints Golden update failed: <error> and exits 1; invalid arguments exit 2.

Propose#

propose selects snapshots from a completed run and copies their typed bundles into a review directory. It never edits the catalog.

  • Repeat --case to select every snapshot of several cases, or use --all for every snapshot of every eligible case. --changed selects every MISSING and DIFFERENT snapshot and nothing that passed, so the accepted entries of unchanged snapshots keep their review reason; it fails when the run has no such snapshot.

  • --output must be a directory that does not exist yet, outside the catalog.

  • --from-run takes the combined report or a results directory. In a directory, it uses the first of evidence/gate-summary.json, gate-summary.json, summary.json, evidence/differential/summary.json and differential/summary.json that exists. When it selects a differential summary.json and an enclosing gate-summary.json exists, it uses that instead, so a child report cannot hide the controller’s failure. An engine-only report is not enough.

A run can supply a proposal only when all of these hold:

  • The run completed, and every serialization execution and planned engine cell passed its independent checks.

  • The runtime snapshot-check and golden-comparison ledgers agree between the cells, the engine report and the combined report.

  • Every golden comparison is PASS, MISSING or DIFFERENT, and the run status is PASS only when all of them are PASS.

  • Repeated inputs produced equal typed results.

Failed controls, timeouts, INVALID comparisons and incomplete runs are not eligible. When the independent checks pass but the run is still not eligible, evidence/gate-summary.json sets checks_status to FAIL and records the reason in golden_update_error. Floating-point proposals accept only the representative snapshots. eligible_run_snapshots in tests/sentinel/goldens.py holds the exact run checks.

When every independent check of a run passes and its only failures are MISSING or DIFFERENT comparisons, the run proposes those snapshots itself, as goldens propose --changed would, into golden-proposal/ beside evidence/ in its results directory. The verdict stays FAIL. After the Sentinel summary block the console prints the proposal’s path, its snapshot count per status and the accept command:

A proposal that cannot be written, for example because golden-proposal/ already exists, prints WARN Golden proposal not written: <error> and leaves the verdict unchanged. A proposal holds its own copy of every selected bundle, so another machine can accept it without the run’s evidence.

Accept#

Review summary.md, differences.json, the case behavior and the implementation change before you accept. accept takes one or more proposals, such as one per build tuple, and publishes them in one catalog update. It:

  • refuses an identity that two selected proposals both hold;

  • checks the typed structure of each bundle;

  • takes the catalog writer lock;

  • replaces the catalog entry with the same identity, or adds a new one;

  • records the review reason on every accepted entry;

  • records verified-source as generated_by.commit when the candidate was a verified clean build, whose 40-digit source revision only the proposal keeps; any other candidate identity, such as unversioned-sdk-sha256:<digest> of an unversioned SDK, is recorded as it is. A candidate revision that is an abbreviated commit ID (7 to 39 hexadecimal digits with at least one letter and one digit) is refused with Candidate revision must not be a commit ID; the catalog is published source before anything is written, as add-database refuses a commit-like writer revision;

  • reuses a ZIP that the catalog already references, or that this update already added, when its bundle manifest.json fields, records.jsonl bytes and payload bytes are identical;

  • otherwise writes the lowest unused result_NNN.zip in the case’s scenario folder.

It never overwrites a stored ZIP, never removes an unreferenced one and never changes historical databases. Unreferenced ZIPs are never reused. It prints the number of accepted entries and the catalog root:

{'updated': 4, 'manifest': '<ovclash>/tests/sentinel/goldens/manifest.json'}

Include the resulting catalog and data changes in normal code review. Proposals trust the local reports: they neither rerun semantic checks nor authenticate saved results directories.

Propose from a run on another machine#

A run on another machine, such as a CI job, can supply a proposal for its own tuple. Its MISSING or DIFFERENT comparisons fail the run, and its complete independent checks are the evidence that goldens propose needs. Do not copy another tuple’s goldens to make the first run pass. Before you begin, you need a local build or staged bundle whose Python runtime the goldens commands can use, and either the run’s golden-proposal/ directory or its complete evidence/ directory.

When the run left a golden-proposal/ directory, copy that directory and accept it as it is; it needs no relocation. Keep it with the proposals of the other affected tuples and accept them together.

To propose from the evidence instead, for example to select other snapshots:

  1. Copy the run’s complete evidence/ directory, including gate-summary.json, to the machine where you propose. Run Sentinel in CI lists what a CI job keeps. EVIDENCE is the copied directory. A copy without gate-summary.json or a recorded bundle makes goldens propose print Golden update failed: <error> and exit 1; copy the whole directory again.

  2. Find the recorded root. The report records absolute bundle paths from the machine that ran it. RECORDED_ROOT is the part of each actual path before its differential component. From the copied evidence/ directory, run this with any Python 3:

    import json
import re

with open("gate-summary.json", encoding="utf-8") as stream:
    actual = json.load(stream)["golden_snapshots"][0]["actual"]
print(re.split(r"[\\/]differential[\\/]", actual)[0])

    It prints RECORDED_ROOT.

  3. Propose from ovclash with the copied directory and its recorded root. Windows:

    test_sentinel.bat goldens propose --from-run EVIDENCE --original-run-root RECORDED_ROOT --case engine-options-depth --output _build/proposal-linux-ovstage-release

    Linux:

    ./test_sentinel.sh goldens propose --from-run EVIDENCE --original-run-root RECORDED_ROOT --case engine-options-depth --output _build/proposal-linux-ovstage-release

  4. Review summary.md and differences.json in the proposal directory.

  5. Accept the proposal with a reason that names the change.

  6. Repeat steps 1 to 5 for every affected tuple.

  7. Run goldens verify --report _build/goldens-verify.json.

The catalog is consistent when goldens verify prints a verification-only: PASS line; see verify and recover a catalog.

With --original-run-root:

  • --from-run must be the directory that contains the report.

  • Only bundle paths are remapped. Each recorded path must be absolute and lie under the original root, and its mapped path must stay inside the copied directory. Any mismatch fails without trying the original location.

  • Recorded POSIX, drive-letter and UNC (Windows network share) paths keep their own syntax, so a Linux run can be reviewed on Windows.

  • proposal.json records both roots in its relocation object.

Without --original-run-root, absolute actual paths are used as recorded, and relative ones resolve against the report’s directory.

Changes that affect tuples you cannot run#

Each of the twelve build tuples has its own tuple file, and a proposal covers only the tuple of the run it comes from. A change that alters a typed result, changes a frozen input or adds a case therefore needs an accepted result from a run of every affected tuple. When you can run all of them, follow propose and accept results for each.

When you can run only some of them, for example only Linux x86-64 ovstage Release, follow these steps. Before you begin, you need a source checkout of the change and, for each tuple that you can run, a local build or staged bundle whose Python runtime the goldens commands can use, as in propose and accept results.

  1. Run Sentinel on every affected tuple you can run.

  2. Collect the proposal of each run: the golden-proposal/ that a golden-only failure wrote, as in the proposal of a golden-only failure, or one you propose from the run, as in propose.

  3. Accept the reviewed proposals together in one accept, with one --proposal per run, as in accept.

  4. Leave the tuple files of the other tuples unchanged. Never copy, edit or derive their rows from a tuple you ran: Sentinel loads only the exact tuple’s file, and a copied row is no evidence for that tuple.

  5. Submit the change with the catalog updates of the tuples you ran.

  6. In the change description, name the tuples you ran and the tuples that still need results.

  7. In the change description, list the entries of each proposal’s summary.md, so that reviewers know which comparisons to expect on the other tuples.

Your part is complete when goldens verify prints a verification-only: PASS line and the change description names every tuple that still needs results.

Until a run of a remaining tuple supplies its results, Sentinel on that tuple still runs every independent check and records:

  • MISSING for a new case or a changed frozen input: the new identity has no golden yet;

  • DIFFERENT for an existing identity whose typed result changed.

Either status fails that tuple’s run, but the run stays eligible for a proposal when every independent check passed. Someone who can run the tuple then proposes from that run, reviews the differences against your description, accepts them and runs goldens verify. A run with a failed independent check or an INVALID comparison cannot supply a proposal: that is a defect to fix, not a result to accept.

Verify and recover a catalog#

Before you begin, you need the Python runtime of an existing build or staged portable input bundle, as for propose and accept results. The two commands are independent: verify checks the catalog, and recover finishes or undoes an interrupted publication. From ovclash:

Windows (cmd.exe):

test_sentinel.bat goldens verify --report _build/goldens-verify.json
test_sentinel.bat goldens recover

Linux:

./test_sentinel.sh goldens verify --report _build/goldens-verify.json
./test_sentinel.sh goldens recover

verify checks the complete catalog without changing it:

  • every shard and reference, every referenced typed bundle and the representative set of each floating-point case;

  • for each historical database: the declared schema, SQLite quick_check, the typed structure of the expected bundle and a readable live manifest;

  • that rewriting the catalog would change no reference or revision.

It runs no reader; the next normal run checks decoding. It writes only the --report JSON, which must be outside the catalog. A relative --report resolves against the current directory, and _build/ is ignored by Git. A passing check prints one line:

verification-only: PASS; engine 10164 -> 10164; retired 0; publication unchanged; report: <ovclash>/_build/goldens-verify.json

accept, add-database, migrate --write and compact --write are the only commands that publish catalog changes. Each of them:

  1. takes exclusive ownership through .catalog-writer.lock and creates .catalog-transaction/;

  2. reloads the complete catalog;

  3. renders the changed metadata, incrementing the revision of each changed shard by one;

  4. stages that metadata and backups of the replaced files in .catalog-transaction/;

  5. replaces manifest.json last, as the commit point.

Git ignores both the lock file and the transaction directory. A revision is a positive integer that keeps the root and its shards coherent. It is not a Git pin, a content hash or authentication. Readers reject a pending transaction and mismatched shard revisions.

After an interrupted publication, every read fails with Pending catalog transaction; run goldens recover --golden-root "<catalog>". recover then prints one outcome:

Outcome

Meaning

no pending transaction

Nothing to recover.

discarded incomplete preparation

The writer stopped before it journaled any change.

rolled back

The root was not replaced; the replaced files are restored.

committed

The root was replaced; only the cleanup is finished.

recover changes files only to finish or undo such a publication. Ordinary runs never write or recover the catalog.

goldens migrate converts a schema 1 catalog to schema 2. goldens compact converts loose engine bundle directories to ZIP archives. Both require --report and only audit unless --write is given. Review the audit report before you rerun with --write. accept, add-database and compact refuse a schema 1 catalog until migrate --write converts it. The repository catalog already uses schema 2 and ZIP storage, so these commands matter only for an older catalog. compact prints compaction: PASS; files <before> -> <after>; bytes <before> -> <after>; publication <state>; report: <path>.

Import historical databases#

Before you begin, you need a real database written by a historical writer, its reviewed decoded records as a typed bundle and a metadata file that describes both, and the Python runtime of an existing build or staged portable input bundle. In the command:

  • OLD.ovclashdb is the closed database file;

  • EXPECTED_BUNDLE is the typed bundle of its reviewed decoded records;

  • METADATA.json is the metadata file that this section describes;

  • FIXTURE is the new fixture ID, such as historical-synthetic;

  • VERSION is the writer’s ovclash version, such as 0.2.0;

  • REVISION is the writer revision, such as verified-source.

From ovclash, on Windows (cmd.exe):

test_sentinel.bat goldens add-database --database OLD.ovclashdb --expected EXPECTED_BUNDLE --metadata METADATA.json --fixture-id FIXTURE --writer-version VERSION --writer-revision REVISION --reason "Reviewed historical fixture"

On Linux:

./test_sentinel.sh goldens add-database --database OLD.ovclashdb --expected EXPECTED_BUNDLE --metadata METADATA.json --fixture-id FIXTURE --writer-version VERSION --writer-revision REVISION --reason "Reviewed historical fixture"

add-database checks the declared schema, runs SQLite quick_check and checks the typed structure of the expected bundle. It runs no historical writer or reader. The next normal run checks that the current reader decodes the database to the expected records. The writer revision is attribution only; a commit ID is refused. The command cannot replace an existing fixture ID. On success it prints {'imported': '<fixture id>', 'manifest': '<catalog>/manifest.json'}; a failure prints Golden update failed: <error> and exits 1.

The fixture folder is databases/<folder>/. <folder> is the fixture ID in lowercase, with every run of other characters replaced by _. For example, historical-synthetic is stored in databases/historical_synthetic/. When that folder is taken, a numeric suffix such as _002 is added, and existing fixtures stay where they are. The folder name is a storage location, not a comparison key.
