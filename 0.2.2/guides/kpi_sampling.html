KPI sampling#

This page owns the KPI sampling rules: how often the controller runs each workload, when its values count as stable, how the warning and failure limits of a budget follow from the values, and when baseline collection restarts a workload. The two Suite saves are the workloads that save their results through the Suite API.

benchmarks/kpi/noise_sampling.py defines the Release policy, the noise gate and the run, retry and restart limits; the source map lists the modules that apply them.

Related pages: KPI maintainer guide and its glossary, KPI CPU admission, KPI baselines and budget packages, KPI evidence, reports and verdicts.

Adaptive smoke#

Smoke becomes adaptive only when all of these hold:

  • The run uses recorded-contention admission (shared-runner-recorded-contention-v2), the default of the launchers; see admission policy and CPU domain.

  • A validated package with approved or generated budgets is selected.

  • At least one of its budgets matches the run’s cohort, a workload and a required metric.

Each workload then starts with one of two inventories:

Workload coverage

First inventory

One package covers every required metric with an active budget

One observation, which can expand to three

Anything less

Three observations

The single observation passes alone only when all of these hold:

  1. The same-build validation receipt passed.

  2. The attempt completed with exit 0 and passed its expected-work audit. Any earlier attempts of that cell were verified pre-run CPU-busy rejections.

  3. Every required metric has an active budget for the CPU model that the attempt actually ran on.

  4. Every value is strictly below its warning limit W.

Otherwise the controller adds two cells, so the workload has three observations in total. The first observation counts as one of the three. The median of the qualified observations then decides; see budget limits. Fewer than three qualified observations give insufficient evidence.

After the first observation of an adaptive workload, the console prints one of these lines:

Sampling:      single qualified observation; all approved metrics strictly below warning; variability unmeasured
Sampling:      expanding to three total observations; retain all values and compare the qualified median

When smoke is not adaptive, every workload runs once. One observation can never produce a verdict, so its comparisons report insufficient evidence. This happens, for example, in a direct python -m benchmarks.kpi run with its default strict admission or without --budgets; see run a campaign. The launchers never reach this case: they stop before measurement when compatible budgets are missing.

Adaptive Release sampling#

Release runs use the acquisition policy adaptive-release-warmup-robust-load25-noise15-retry10-runs10-restarts10-v10. Its name lists the fixed values:

Name part

Meaning

warmup

One retained warm-up run per workload series

robust

Stability is measured with the median absolute deviation (MAD)

load25, noise15

Noise limits: 25% for load_seconds, 15% for every other required metric

retry10

10 CPU retries per run

runs10

10 successful runs per workload series, warm-up included

restarts10

10 workload restarts per campaign in baseline collection

v10

The policy version

Calibration evidence and budget packages (acquisition_policy) record this name. Readers reject any other policy, so a policy change needs new packages.

Warm-up#

  • The first successful run of a series is the warm-up. A successful run has exit 0, qualified CPU and environment evidence, and a passing expected-work audit.

  • The warm-up is kept in the evidence and shown as Warm-up in the console. It is excluded from medians, MAD, noise and budgets.

  • CPU-rejected attempts before it are retries of the warm-up run. They never become the warm-up.

The noise gate#

After every successful run, the controller evaluates each required metric over all of its measured values. Required metrics lists them per workload.

B     = median of the measured values
MAD   = median of abs(x - B) over every measured value x
S     = 3 * MAD                     the stability value
noise = 100 * S / B                 the displayed percentage

load_seconds:          stable when S <= 0.25 * B
every other metric:    stable when S <= 0.15 * B

A metric passes when it has at least three measured values and its S is within its limit. The result is one decision per workload:

Decision

When

stable

At least four successful runs (the warm-up and three measured runs), and every required metric passes

attempt-limit

The tenth successful run ended without a stable decision

collect

Any other case. The controller runs the workload again

The inventory starts with three cells per workload. The warm-up uses one of them, so a fourth cell is always added. Each later collect decision adds one more cell. A new cell is inserted right after the current one and saved before its first attempt starts.

The gate follows these rules:

  • Each metric passes or fails on its own. A stable operation_seconds does not cover an unstable phase or memory metric.

  • Every valid value stays. No value is trimmed or clipped, and no favorable subset is chosen, neither for the gate nor for the budget limits.

  • The gate reads only the measured values, never the budgets. Sampling never repeats a workload to turn a warning or a regression into a pass.

  • A stable workload does not make a package. A package also needs compatible identity, a valid producer, verified cleanup, independent replay, and approval or validated generation; see KPI baselines and budget packages.

Note The 25% Load noise limit is unrelated to the 25% CPU-busy threshold of recorded-contention admission. The noise limit bounds the spread of measured Load times. The admission threshold bounds CPU load before an attempt.

Run, retry and attempt limits#

  • A series has at most 10 successful runs: one warm-up and up to nine measured runs.

  • Each run, the warm-up included, permits 10 CPU retries, so 11 attempts.

  • Rejected attempts use no run slot. A series therefore has at most 110 attempts.

  • The shared CPU-wait allowance and the campaign deadline can end retries sooner. Recovery lists the rejections that are retried.

Example: a workload that becomes stable#

The workload table example shows a Release workload from its first attempt to its stable result, and that section reads its rows. The noise of its PASSED line comes from the measured runs 2 to 4: the Capture/Save values 1.02, 1.03 and 1.01 give 3 * 0.01 / 1.02 = 2.94%, and the Load values 1.00, 1.02 and 0.99 give 3 * 0.01 / 1.00 = 3.00%.

After a stop, every remaining cell is recorded as unexecuted. The saved summary then gives this reason:

The campaign’s verdict is insufficient evidence (exit 3) unless a verdict with a higher priority applies; reports and verdicts gives the order. Calibration evidence needs every workload stable, so a stopped campaign exports none. When the driver checks it for export, it prints KPI campaign is ineligible for portable calibration; diagnostic verdict unchanged. In baseline collection, the noise, CPU retry and clock-alignment stops can restart the workload instead.

How a stop is explained#

A noise stop prints the run counts and a calculation block for one deciding metric. The deciding metric is the first required metric, in metric-ID order, with fewer than three values. When every metric has three values, it is the first metric above its limit. This example is console output for illustrative values:

  Campaign stopped: 10 successful runs used (1 warm-up, 9 measured); 12 total attempts; required metrics have not passed the noise checks (Load 25%; other metrics 15%); Operation noise 30.00% > 15%
  Operation: REJECTED: stability noise 30.00% > 15%
    median=6s; MAD=0.6s
    R=3*MAD=1.8s
    allowed R=0.9s (0.15*median)
    Noise=R/median*100=30.00% > 15%
    largest deviation=0.9s; retained and reported separately from stability.
    Budget allowance N=max(R, largest deviation) still includes every spike; warning=1.05*median+N, failure=1.10*median+N.
    MAD=median absolute deviation of all measured values. Values are rounded for display; the saved gate uses full precision.

  • R is the stability value S. allowed R is the limit times the median.

  • Displayed numbers are rounded. When a rounded percentage does not look above the limit, the line reads (rounded; exceeds 15% at full precision). The saved gate always uses full precision.

When the deciding metric has fewer than three values, no noise is calculated:

  Campaign stopped: 10 successful runs used (1 warm-up, 9 measured); 10 total attempts; fewer than 3 valid measurements for a required metric; OS peak resident: fewer than 3 valid measured values
  OS peak resident: insufficient measurements (2 / 3 valid values; fewer than 3 valid measurements); noise rejection is not established

The final summary repeats each workload’s saved decision in its Campaign summary (saved controller decisions) table; see the final summary.

Budget limits#

A budget package holds one warning limit and one failure limit per CPU model, workload and required metric. They are derived from all measured values of the selected evidence: every value of the selected campaigns for a generated package, every admitted observation for budget create. Warm-up values never enter. For one workload and metric with median B, MAD D and values x:

S = 3 * D                          stability value; gated by the noise limits
N = max(S, max(abs(x - B)), f * B) budget noise; keeps the largest deviation and the floor f
W = 1.05 * B + N                   warning limit
F = 1.10 * B + N                   failure limit

  • N is not a second stability gate. An isolated slow value can pass the noise gate, but it still widens both limits. It is never deleted or clipped.

  • The noise floor f is 0.30 for extraction_serialization_seconds (Suite serialization) and 0 for every other metric. A collection runs on one machine, so its values cannot show how far a metric moves between machines of the same CPU model. Suite serialization writes the result database, and its time varies between machines more than one collection’s spread shows. Its warning limit is therefore at least 1.35 * B and its failure limit at least 1.40 * B. The floor never affects the noise gate.

  • The floor belongs to the comparison contract approved-cpu-model-limits-v2, which every new package uses. A package of the earlier approved-cpu-model-limits-v1 contract stays valid and keeps its recorded limits, without the floor, until a new package replaces it.

  • An approved or generated budget also needs at least three values and S within the noise limit of its metric.

  • Package readers recompute N, W and F with the formulas of the package’s contract and reject a package whose limits differ; see package fields.

A candidate is judged by the median C of at least three qualified observations of the same workload and metric. In a Release check these are the workload’s measured runs; the warm-up never counts. The limits are inclusive:

Median

Result

Exit

C <= W

Pass

0

W < C <= F

Warning

0

C > F

Regression

2

  • A single observation can only pass, and only under adaptive smoke. It must be strictly below W. It never establishes a warning or a regression.

  • Fewer than three qualified observations otherwise give insufficient evidence (exit 3).

  • An unapproved package cannot enforce its budgets. Its comparisons stay insufficient evidence, and the record keeps the numeric result for review.

Worked example#

Nine pooled load_seconds values (seconds) from three selected campaigns:

100, 100, 100, 100, 101, 102, 102, 102, 102

B = 101.0                         the fifth of nine sorted values
D = 1.0                           deviations: 1, 1, 1, 1, 0, 1, 1, 1, 1
S = 3 * 1.0 = 3.0                 noise 3.0 / 101.0 = 2.97% <= 25%: stable
N = max(3.0, 1.0) = 3.0
W = 1.05 * 101.0 + 3.0 = 109.05
F = 1.10 * 101.0 + 3.0 = 114.1

A candidate median of 108 s passes, 112 s warns and 115 s is a regression. If the same values were operation_seconds, the 15% limit would apply, and 2.97% would still be stable.

Example: the Suite serialization floor#

Nine pooled extraction_serialization_seconds values (milliseconds), synthetic:

20.0, 20.1, 20.2, 20.3, 20.4, 20.5, 20.6, 20.7, 20.8

B = 20.4, D = 0.2
S = 0.6                           noise 2.9% <= 15%: stable
N = max(0.6, 0.4, 0.30 * 20.4) = 6.12
W = 1.05 * 20.4 + 6.12 = 27.54
F = 1.10 * 20.4 + 6.12 = 28.56

Without the floor, N would be 0.6 ms and the failure limit 23.04 ms, so a check that lands on a slower host of the same CPU model would report a regression without any code change.

Example: an isolated slow value#

Nine pooled operation_seconds values with one slow outlier:

2.00, 2.01, 2.02, 1.99, 2.00, 2.01, 1.98, 2.00, 2.60

B = 2.00, D = 0.01
S = 0.03                          noise 1.5% <= 15%: stable
N = max(0.03, 0.60) = 0.60        the outlier sets the budget noise
W = 1.05 * 2.00 + 0.60 = 2.70
F = 1.10 * 2.00 + 0.60 = 2.80

The outlier does not block stability, but it widens both limits by 0.60 s. Without it, N would be about 0.03 s.

Reproduce the arithmetic#

The gate and the limits are plain Python. Run this from ovclash/ with the KPI input Python $PY from the quick start. The snippet needs only the standard library and the checkout’s own modules, so any CPython 3.12 also runs it.

Linux, as a shell heredoc:

"$PY" -B - <<'EOF'
from benchmarks.kpi import baseline_selection, noise_sampling

policy = noise_sampling.CURRENT_POLICY
values = [100.0, 100.0, 100.0, 100.0, 101.0, 102.0, 102.0, 102.0, 102.0]
stats = baseline_selection.pooled_statistics(values, metric_id="load_seconds", acquisition_policy=policy)
print({key: stats[key] for key in ("median", "mad", "noise", "warning", "failure", "stable")})

gate = noise_sampling.evaluate_warmup(
    {"load_seconds": [1.00, 1.02, 0.99], "operation_seconds": [6.00, 6.90, 5.40]},
    attempt_count=4,
    run_count=4,
    policy=policy,
)
print(gate["decision"], [(row["metric"], round(row["noise_fraction"], 4), row["passes"]) for row in gate["metrics"]])
EOF

Windows (cmd.exe) has no heredoc: save the Python lines between <<'EOF' and EOF as a file in ovclash/, such as kpi_arithmetic.py, and run "%PY%" -B kpi_arithmetic.py.

Output:

{'median': 101.0, 'mad': 1.0, 'noise': 3.0, 'warning': 109.05, 'failure': 114.1, 'stable': True}
collect [('load_seconds', 0.03, True), ('operation_seconds', 0.3, False)]

The second gate has the warm-up and three measured runs, but operation_seconds has 30% noise, so the decision is collect.

Workload restarts in baseline collection#

A restart replaces only the failing workload’s current series with a new one in the same campaign. Earlier workloads keep their results, and later workloads run as usual.

Restarts happen only with --mode collect-baseline, the release profile and a campaign deadline. Every collector campaign has a deadline. A standalone python -m benchmarks.kpi run --mode collect-baseline --profile release also grants restarts, because --job-seconds defaults to 3300; --no-campaign-deadline turns them off. Check mode never restarts a workload: the same causes stop the campaign there. Deadlines describes the deadline and its cleanup reserve.

Restart causes#

Only these verified causes restart a workload:

cause

Stop

Condition

noise_exhaustion

Successful-run limit

Ten successful runs, every required metric has at least three values, and the gate is still not stable

cpu_contention

CPU retry limit

One run used its initial attempt and all ten retries. Every attempt of that run was a verified pre-run CPU-busy or counter rejection, and the last one was CPU-busy

cpu_counter_rejection

CPU retry limit

The same, but the last attempt was a strictly replayed pre-run Windows invalid_pdh_counter_delta rejection of a Performance Data Helper (PDH) counter

cpu_clock_alignment

A result that cannot be retried

A strictly replayed pre-run Windows pdh_clock_alignment_unsupported rejection: exit 3, no metrics and no work

Every earlier attempt of the series must also be a clean qualified measurement or a verified pre-run CPU rejection. In-operation CPU load never counts.

After a cpu_clock_alignment restart, the new series searches for a CPU placement from scratch. That search is charged to the shared CPU-wait allowance. The allowance, the pool and the cohort are never reset.

These outcomes never restart a workload. They end the campaign with their own verdict:

  • product failures (exit 1), harness failures (exit 4) and cancellation (exit 130);

  • operation watchdog timeouts and crashes;

  • in-operation CPU load and a cohort mismatch;

  • the shared CPU-wait allowance stop and the campaign deadline stop;

  • ten successful runs with fewer than three values for some required metric.

When a restart is refused#

The controller refuses a restart when:

  • the campaign was interrupted, or owned process cleanup could not be verified;

  • the campaign has reached its 300-second cleanup reserve before the deadline;

  • the shared CPU-wait allowance has no time left for another CPU check;

  • another campaign-level admission stop is active;

  • the workload has already used its ten restarts.

The allowance test looks only at the next check’s window, not at the new series’ placement search. If that search then uses up the allowance, the new series ends at the CPU-wait allowance stop. The collector then retries the campaign as cpu_contention.

A refused restart ends the campaign. The collector classifies the campaign as described in when collection continues and stops.

The restart limit#

A workload restarts at most ten times per campaign, all causes combined. It therefore has at most eleven series, numbered 0 to 10, of at most 110 attempts each.

When the limit refuses a verified cause, the stop of series 10 stands. The collector classifies the campaign by that cause and starts another campaign while time remains. Earlier eligible campaigns stay candidates. The incomplete campaign contributes no values to a package.

A new series#

When the controller grants a restart of series k:

  1. It drops the never-started cells of series k and saves three new cells for series k+1 before the next attempt starts.

  2. Series k+1 takes a new warm-up. Its samples, runs and attempts count from the start.

  3. Its attempt IDs insert -r{k+1} after the workload ID. Workload IDs do not change.

For example, a noise exhaustion that ends at benchmark-body-representative-static-009-0 (sample 9, first attempt) is followed by benchmark-body-representative-static-r1-000-0.

What counts after a restart#

Only the final series counts:

  • Superseded series stay in the private execution tree, the console log and the public measurements.json. Their observations are qualified: false.

  • Sample counts, the noise gate, the scorecard and the comparisons use the final series only.

  • A product, harness or cancellation failure in any series still fails the workload.

  • calibration.export exports only each workload’s final series; its sampling rows carry no series or restarts field. It also drops the rejected CPU placements of superseded series from the selection ledger that it exports, the campaign’s cpu-selection.json; successful placements stay. The exported calibration validates like a campaign without restarts, so superseded values never reach a budget.

The calibration reader cannot check why a series was superseded. The controller verifies every cause before it grants a restart, and the public record keeps the restart records for review.

Console and log lines#

A granted restart prints the cause and the start of the new series. These lines come from the console code; the noise values are illustrative.

Restarting this workload only (restart 1): noise limits not met at the successful-run limit (10 successful runs); Operation noise 30.00% > 15%.
Earlier runs stay retained but are excluded; the new series starts with a new warm-up.

A CPU retry restart first prints the Recovery: line of the exhausted run; see when a Release campaign stops. For example:

Recovery: CPU contention retry allowance exhausted (10/10); insufficient evidence (exit 3); <seconds>s remaining
Restarting this workload only (restart 2): CPU busy through every retry of one run (initial attempt plus 10 retries).
Earlier runs stay retained but are excluded; the new series starts with a new warm-up.

Each cause has a fixed label:

cause

Console label

noise_exhaustion

noise limits not met at the successful-run limit

cpu_contention

CPU busy through every retry of one run

cpu_counter_rejection

CPU counter samples invalid through every retry of one run

cpu_clock_alignment

pre-run CPU clock alignment rejected

A refusal at the restart limit prints this line before the workload’s Campaign stopped line:

Restart limit reached (10 restarts): noise limits not met at the successful-run limit; this workload is not restarted again.

The final summary lists the restart history under the workload:

restart 1 after noise limits not met at the successful-run limit (10 successful runs, 12 attempts); the new series began with a new warm-up
restart 2 after CPU busy through every retry of one run (3 successful runs, 14 attempts); the new series began with a new warm-up

When a workload’s final series is series 10 and is not stable, the history ends with restart limit used up (10 restarts); no further restart was available. That line names no cause: the saved records do not show whether series 10 ended at a refused verified cause or at a stop that is never restarted.

When the collector retries such a campaign, it logs the cause and the used-up restart limit in public/progress.log; see when collection continues and stops.

The campaign’s private attempts.jsonl journal records each grant as a restarted event with the workload ID, the new series, the cause, the stop and the terminal attempt ID. The row caps bound how many attempts and cells a campaign with restarts can record.

Restart records#

A restart record holds the final gate counts of the superseded series. Every field is required:

Field

Type

Required

Default or values

Description

cause

string

Yes

noise_exhaustion, cpu_contention, cpu_counter_rejection or cpu_clock_alignment

The verified restart cause

series

integer

Yes

0 to 9

The superseded series

attempt_count, run_count, qualified_count

integer

Yes

The superseded series’ final gate counts, as in a workloads row

terminal_attempt_id

string

Yes

An attempt ID

The attempt that ended the superseded series

Inventory cells and attempts of series 1 or later carry series: k. The original series never carries a series field. Readers reject:

  • an explicit series: 0;

  • a series above the workload’s final series or above the restart limit;

  • a number of restart records that differs from the final series number.
