KPI frozen contracts and maintenance#

This page is for maintainers who change KPI workloads, the bundle generator (benchmarks/kpi/reference_fixtures/), contract files or measurement code. It covers the contract files that freeze the nine workloads, the Linux AArch64 qualification files, pin refresh, the validation receipts KPI accepts, the measurement identity, the tests and goldens, the source map and the reviewed static-analysis annotations. The KPI glossary defines the KPI terms used here, such as workload, base workload, bundle, budget, package, validation receipt, controller and driver.

KPI workloads and metrics describes what each workload measures and lists its expected values. Representative fixture stages generates and inspects the bundles. Consumer terms such as backend, ovstage, OpenUSD, SDK archive and Suite API keep their consumer meaning.

Run the examples on this page from ovclash/ with the Python test venv that --validate creates, a CPython 3.12 environment. This page calls it $TEST_PY:

TEST_PY=_build/deps/venv/python_tests/bin/python3

On Windows, use set "TEST_PY=_build\deps\venv\python_tests\Scripts\python.exe" and "%TEST_PY%". Save a multi-line snippet to a .py file in ovclash/ and run it with "%TEST_PY%" -B <file>, where <file> is the name you saved it under. $TEST_PY is not the KPI input Python $PY of the quick start. Generate bundles only with $PY, because the pins match only the bytes it writes.

Frozen workloads and profiles#

The contract files under benchmarks/kpi/ are the only authority for expected work. A candidate build (the build under measurement), a prepared run directory or a result receipt cannot replace them. No command writes them, CI included: a job reads them from its checkout, and a maintainer edits them from reviewed evidence, never from values learned in a candidate run.

Contract composition#

representative_workloads.frozen_contract() builds the contract for one runtime axis in this order:

  1. Read representative_expectations.json. Its source must equal the current recipe identity.

  2. Validate representative_extensions.json against the digest of the base contract. Append the three extension workload rows.

  3. On linux-aarch64 only, overlay the Cockpit Static and Clearance qualifications.

  4. Replace the extension’s 65-sample dynamic-depth row with the row derived from representative_depth.json.

  5. On linux-aarch64 only, overlay the depth report volume.

The runtime axis comes from the wheel tag of the build: win_amd64 is windows-x86_64, a Linux x86_64 tag is linux-x86_64, and a Linux aarch64 tag is linux-aarch64.

Run this check after every contract edit, from ovclash/ with $TEST_PY. It validates every file and binding, and it raises a ValueError with a fixed message at the first stale one:

"$TEST_PY" -B - <<'EOF'
from benchmarks.kpi import representative_workloads as rw

for axis in ("windows-x86_64", "linux-x86_64", "linux-aarch64"):
    contract, digest = rw.frozen_contract(kind=rw.CURRENT_FORMAT, runtime_axis=axis)
    workloads = sum(len(profile["queries"]) for profile in contract["profiles"])
    print(f"{axis:15} {workloads} workloads  {digest}")
EOF

A passing check prints one line per runtime axis and exits 0. With the current files, it prints the digests that tests/python_tests/test_kpi_representative_runtime_contract.py pins:

Preparation#

representative_workloads.prepare_manifest(destination, *, build_path) turns a build manifest into a prepared run. Generate the bundles shows how to call it. It never runs the product and never asks a candidate build for expected results. It:

  1. creates destination, which must not exist, and copies the build manifest into it;

  2. validates the build against the build checks of this section, including every file hash;

  3. derives the runtime axis and the frozen contract for it;

  4. writes copies of the three contract files. On Linux AArch64, the expectations copy carries the Cockpit Static qualification;

  5. generates the bundles body-representative, cockpit-representative and body-representative-depth. Each generated bundle.json SHA-256, closure digest (see bundle manifest and seal) and root.usda entry must equal its pin;

  6. reads the contract again. It must not have changed during generation;

  7. writes generation.json and the run manifest representative-workloads.json.

Private execution tree shows the resulting layout.

The build checks require:

  • an ovstage or openusd build with configuration Release and a dependency pin for that backend;

  • verified source (source.verified is true). A dirty source of uncommitted changes is measured only in a local diagnostic check; budget creation and calibration export require source.dirty to be false (see source identity);

  • installed provenance, the ovclash-build-provenance.json of the install tree, that matches the manifest’s source, backend, build type and backend version (see build provenance);

  • install and binding roots without undeclared native or binding modules;

  • installed native files that match the SDK archive byte for byte, bindings that match the wheel, and exactly one primary library shared by both.

The ovstage SDK archive does not contain the ovstage runtime files. For those files, KPI rebuilds ovclash-runtime-closure.json, ovclash-runtime-dependencies.json and requirements.txt from the installed bytes with the producer’s own serializer. The SDK archive members must have the same SHA-256. tests/python_tests/test_kpi_runtime_metadata_producer.py keeps that serializer equal to scripts/prepare_sdk.py.

During measurement, every child reports the native and binding modules it loaded, before and after the operation. Each must be a declared file of the build with its declared SHA-256, and the native list must include the primary ovclash library.

Workload digests#

Every workload row has a workload digest. Budgets, coverage and calibration match workloads by this digest. It covers the whole row except run provenance: the stage and bundle paths, the run manifest, the build digest and the measurement-identity hash are left out. So the same frozen workload compares different builds, and a code edit keeps installed packages usable. Packages identify a workload only by its ID and workload digest; they hold no producer revision and no measurement digest.

Each row binds the recipe identity, its bundle and entry digests, its settings, scope, timeline, expected work and the digest of its contract. A contract edit changes these digests:

Nine-workload contract#

The nine workloads form one frozen set. Eight run on the Body and Cockpit bundles. Dynamic depth runs on its own full-motion Body bundle. The nine workloads and their settings list their schedules and settings.

The run manifest has schema 3 and format ovclash-kpi-representative-run-v3; run admits no other manifest. Inside it, the six base workload rows keep the marker kind ovclash-kpi-representative-run-v2 and bind the base contract digest. The three extension rows carry ovclash-kpi-representative-run-v3. These are row kinds, not manifest formats. The extension rows never relabel the six base workloads.

Depth bundle#

benchmarks/kpi/representative_depth.py generates the depth bundle and derives its workload row. Its constants are pinned data: DURATION_SECONDS = 1.125, SAMPLES_PER_SECOND = 8.0 and the recipe identifier representative-depth-v1. The depth bundle uses the common recipe identity, like the other bundles. KPI checks it three times:

  • the fixture descriptor in representative_depth.json must match the constants, the bundle path and the current recipe source;

  • admission of a prepared run requires the recipe identifier, duration and probe rate in the bundle metadata.

Replay reads every row and checks it against the pair, sample and element membership. Then the SHA-256 of the whole stream must equal sha256. The digest covers every byte, so it also pins zero depths and the sign of a zero. Aggregate depth totals or approximate comparisons cannot replace this check. To read a retained stream, save this script as read_depth.py in the directory that holds benchmark-depth.bin, an attempt directory of a retained private execution tree (see attempt directories), and run it there with "$TEST_PY" -B read_depth.py, giving $TEST_PY as an absolute path. It needs only the Python standard library:

import struct
from pathlib import Path

data = Path("benchmark-depth.bin").read_bytes()
rows = list(struct.iter_unpack("<IIQf", data))  # (pair, sample, elements, depth)
print(len(rows), rows[0])

Depth timing#

MEDIUM computation runs inside the timed pipeline. The child copies the depth metadata after result_ready, outside timed report extraction and the operation and memory boundary. It requests no extra report payload. After the child’s cleanup, the controller reads and validates the real rows before it qualifies the observation. Calibration evidence carries receipts of the depth content (byte count and SHA-256), not the rows. Its offline reader checks those receipts and the work contract without rehashing absent rows.

Why Linux AArch64 has its own expectation files#

KPI work checks are exact: metadata and report volume must equal the frozen reference, with no tolerance. The native Linux AArch64 Release build finds the same pairs and samples as x86-64. For a few records, however, it reports slightly different element counts or report geometry, such as other outline segment counts. For the Cockpit Static borderline pair, the cause is architecture-specific SDK quaternion-to-matrix arithmetic.

The check is not loosened. Each difference was captured on AArch64, compared with the x86-64 reference and pinned exactly in an AArch64-only file. The review object of each file records the comparison evidence and the digests of the captured artifacts. Rules for these files:

  • Each file binds the contracts it overlays, so a changed reference invalidates it.

  • They name no commit, CI job or pipeline. The build and artifact digests identify the captures, and the loaders refuse any other review field.

  • x86-64 contracts and their digests never read them.

  • They supply no timing observation or budget (timing_baseline: false).

  • OpenUSD and ovstage results must be identical. One same-platform OpenUSD capture is the AArch64 reference, and the ovstage run must reproduce it.

  • Local Windows validation does not qualify Linux or AArch64.

Re-qualify Linux AArch64#

Re-qualify after a native change, or when an AArch64 KPI check reports a size or membership difference that x86-64 does not.

Before you begin, you need:

  • x86-64 still matching its reference. When it does not, the reference itself changed: that needs new reviewed references, as in refresh pinned fixture identities, not an AArch64 qualification. Stop here in that case.

  • A Linux AArch64 machine with a clean OpenUSD Release build and an ovstage Release build of the same committed source, each with its validated Release inputs; see prepare Release inputs. A build that fails stops the procedure; see troubleshooting.

  • $TEST_PY in ovclash/ of a checkout with that source.

Each kind of difference needs its own proof:

Difference

Proof

Only the Dynamic depth report volume, with identical expected.sha256 and membership

A volume-only qualification: the byte delta in the depth file’s review

Any other difference

A reviewed proof for each changed record, in the changed_metadata_rows and changed_report_rows of the Static and Clearance files; see AArch64 review fields

Two results stop the procedure, because nothing can be pinned:

  • Captures that disagree with each other. Investigate the nondeterminism instead.

  • An ovstage check that observes other values than the OpenUSD captures. Both backends must give identical results, so investigate the difference between them instead.

Then:

  1. Capture the affected workload with the OpenUSD build on the AArch64 machine at least three times.

  2. Check that all captures agree with each other.

  3. Compare the captures with the x86-64 reference.

  4. Record the proof that the difference needs, as the proof table of re-qualify Linux AArch64 gives it.

  5. Confirm that an AArch64 ovstage check observes the same values as the OpenUSD captures.

  6. Update the overlaid values in the AArch64 file.

  7. Update the file’s review: the scope of the capture, the build and artifact digests, the runs and the byte delta; AArch64 review fields lists every field. The file keeps sorted keys and two-space indentation.

  8. Run the contract check. It passes when it prints the three axis lines and exits 0; a ValueError names the stale binding.

  9. Re-pin the AArch64 digests in tests/python_tests/test_kpi_representative_runtime_contract.py.

  10. Run that test with "$TEST_PY" -B -m unittest discover -s tests/python_tests -t tests/python_tests -p test_kpi_representative_runtime_contract.py. The qualification is complete when it reports OK.

The AArch64 workload digests then change, so the AArch64 budgets of those workloads must be collected again.

Accepted signing skips#

A sign_sdk step with status SKIP and type validation-step in a PASS receipt is accepted in two cases:

  • Not applicable. One of these holds, and the summary lists the step in not_applicable_steps:

    • the bound closure has lib/libovclash.so and no .dll, .exe or .pyd file in its native or binding inventory;

    • the build is OpenUSD, and the receipt records signing_policy with mode auto or off and simulated: false, on any ref.

  • Permitted development skip. The closure contains PE files (Windows Portable Executable files: .dll, .exe or .pyd), and the receipt records signing_policy with protected_ref: false, mode auto or off, and simulated: false. The summary lists the step in permitted_skip_steps.

The measurement digest is checked in three places:

  • When the campaign ends, a changed digest adds exit 4 with Measurement implementation changed during the campaign.

  • Calibration export refuses a campaign whose sources changed while it ran: measurement source changed during the campaign.

  • Budget derivation requires one digest for all its observations. Calibration from before and after an edit cannot be pooled.

Any edit to a hashed file, even to a comment or a label, therefore starts a new measurement identity. These executed files are not hashed: the driver scripts scripts/kpi_*.py, and the SDK archive dependency contract scripts/runtime_dependencies.py, which build-manifest verification imports. Ordinary tests and dedicated workloads#

build_ovstage.* --validate and build_openusd.* --validate run the ordinary product checks. They do not run the full Body and Cockpit KPI workloads, full-profile bundle generation or the Sentinel checker tests. Small synthetic geometry, statistics, retries, formatting and bounded launcher and cleanup integrations stay in ordinary tests. Dedicated KPI runs measure the nine frozen workloads against their matching validated Release producer.

The opt-in target test_kpi_full_fixtures runs tests/kpi_tests/. The folder holds only these four checks; the ordinary KPI tests stay in tests/python_tests/ (see Tests and goldens). The four checks generate full profiles and compare their inventories:

  • the original and the cut body-representative, each with the pinned Body root.usda digest;

  • the Body fine cut;

  • the Cockpit mesh allocation against its triangle-budget search.

The tasks run one at a time with a 1,860-second timeout each. The target builds install_sdk first. validate_all never runs it. Run it from ovclash/. BUILD_DIR names an existing configured build tree, such as the Release tree of a build_ovstage --release build; see backends and trees.

Linux:

cmake -DBUILD_DIR=_build/compile/ovstage/ninja -DTARGET=test_kpi_full_fixtures -DCONFIG=Release -P scripts/build_target.cmake

Windows:

_build\deps\target-deps\cmake\bin\cmake.exe -DBUILD_DIR=_build/compile/ovstage/vs -DTARGET=test_kpi_full_fixtures -DCONFIG=Release -P scripts/build_target.cmake

The command exits 0 when the build and all four checks pass. It fails with:

  • No configured build tree at <path> (CMakeCache.txt is missing) when BUILD_DIR names no configured tree. Build that backend first, or name another tree.

  • Build failed (exit code: <code>) when install_sdk or one of the four checks fails, including a check that exceeds its timeout. Read the output printed before that line for the failure.

No ordinary test regenerates the real bundles, and no test compares the bundle digests with their pins. A check without compatible budget coverage stops before generation. After a change to the bundle generator, regenerate the three bundles with the KPI input Python $PY and compare their digests with the pins; see generate and retain stages.

Tests and goldens#

The KPI tests are tests/python_tests/test_kpi_*.py and tests/python_tests/test_reference_fixture_*.py. They are pure Python and need no native build. Platform-specific tests skip on other systems. The test_reference_fixture_*_native.py tests run only with OVCLASH_KPI_REFERENCE_GEOMETRY_NATIVE=1 and a configured runtime. Run them from ovclash/ with $TEST_PY:

"$TEST_PY" -B -m unittest discover -s tests/python_tests -t tests/python_tests -p "test_kpi_*.py"
"$TEST_PY" -B -m unittest discover -s tests/python_tests -t tests/python_tests -p "test_reference_fixture_*.py"

Each command reports OK when its tests pass. The full KPI set takes many minutes. While you iterate, run one module, for example -p test_kpi_representative_runtime_contract.py. Baseline collection tests lists the modules that cover the collection files, selection and publication.

Reviewed static-analysis annotations#

SonarQube is the static-analysis service that scans this code. A NOSONAR comment marks a line whose finding a reviewer accepted, so SonarQube does not report it; the rule key in parentheses names the accepted rule. The measurement-identity sources, and the benchmarks.backend_timings benchmark that shares their helpers, carry rule-specific annotations at reviewed operations, not file-wide exclusions. They document existing trust boundaries. They do not change runtime guards or claim that a finding was resolved on the SonarQube server.

Annotation and source

Reviewed boundary

NOSONAR(S2083) at load_json, sha256_file and the archive open in _archive_hashes in benchmarks/kpi/evidence.py, and at file_sha256 in benchmarks/kpi/operations.py

Read-only local files: operator-selected artifacts, controller-bound stage paths, owned outputs or contained package members. Build artifacts may live outside the manifest directory. Path normalization, containment and size and hash checks stay with their owning readers. The child matches its stage locator to the controller argument on its own

NOSONAR(S5042) at the tar reader in _archive_hashes in benchmarks/kpi/evidence.py

The reader bounds parser and metadata access, member count, declared and decoded bytes, and XZ decoder memory. It hashes members without extracting them to filesystem paths

NOSONAR(S2245) at _token and _triangles in benchmarks/kpi/reference_fixtures/plan_model.py

A seeded random.Random produces public fixture names and a repeatable triangle allocation. Neither creates secrets or makes security decisions

NOSONAR (pythonsecurity:S6680) at the attempt loop of iter_run_schedule in benchmarks/backend_timings/matrix.py, outside the measurement identity

_validate_schedule_capacity() bounds repeats to the uint32 run_ordinal domain before the loop starts

NOSONAR(S4828) at _PosixGroup.alive() and _PosixGroup.terminate() and in _owned_linux_child in tooling/process_tree.py

Signals reach only the dedicated process group that the owned child created, or the kernel-listed children of the Linux subreaper. Signal 0 only checks existence. No process is selected from command input or an unrelated inventory

NOSONAR(S5443) at _remove_linux_rstring in tooling/process_tree.py

The path names a Carbonite RString IPC object, a shared-memory name or semaphore (carb-RStringInternals-*) that the ovstage parser can leave behind, of one exact, exited, owned PID under /dev/shm. The function only unlinks it, and only when the effective user owns it

An annotation-only edit under benchmarks/kpi/ or tooling/ changes the measurement identity but not the nine workload digests. New annotations follow the Python code style.
